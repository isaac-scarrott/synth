## Experimental Tabs — the native port lands (off by default)

The single-strip Tabs view mode decided in the 2026-07-23 mock (ADR-0014's 2026-07-23 amendment,
`CONTEXT.md` **Tab**) is now implemented in the native SwiftUI app, gated behind the same
off-by-default global preference so a tabs-off build is byte-for-byte today's behaviour. It is a
faithful port of `working.html`, not a redesign — the store stays `branch → pane-tree → sessions`,
and every tabs-gated path keys off `AppStore.tabsMode`, so flipping the toggle re-renders the same
store losslessly with no migration.

**The flag.** `AppStore.tabsMode` — a persisted global preference mirroring the theme/sound prefs
(`UserDefaults`, key `synth-tabs`), off by default. An `@Observable` read, so the sidebar and content
re-render the instant it flips. Settings gains an **Experimental → Off/Tabs** segmented control
(global scope only, mirroring the Appearance control).

**Two-deep sidebar.** With tabs on, `BranchRow` drops its disclosure chevron, keeps its Reveal shut
(session rows + the split echo band leave the tree), and forces the branch roll-up visible even while
nominally expanded — the branch's only per-session signal. `peeking`/`isActivePill` are made
tabs-aware so the branch keeps its "you are here" pill when its sessions no longer show below it.

**One strip per branch (`TabStrip.swift`).** The horizontal twin of the sidebar rows: the branch's
sessions in order, the on-screen split's members bonded into a contiguous cluster at their first
member's position (styled like the sidebar's split band — rounded chips on `raised`, active member
accent-ringed), the rest lone tabs, then `+` and a right-aligned relocated PR chip. Selecting a lone
tab full-screens it (the durable split stays shown as the bonded cluster, stashed behind the
full-screen); selecting a member returns to the split. The per-pane header (`PaneHead`) is hidden in
tabs mode; when the sidebar is collapsed the strip carries the expand toggle past the traffic lights.
Reuses the sidebar's exact indicator chrome (`SessionIcon`/`StatusIndicator`/`OwnedIndicator`) — an
agent-owned browser wears its owner-mark; unread lands as a blue dot on the tab icon.

**Keyboard.** `⌘⇧[`/`⌘⇧]` and `⌃⇥`/`⌃⇧⇥` step the branch's tabs (`cycleTab`), `⌘1–9` selects the Nth
tab (`focusPane` tabs-aware), `⌘W` closes the active tab through the same confirm path as `⌘D`. The
⌘? shortcuts sheet inserts a **Tabs** category after General and rewrites the Split-layout rows tabs
changes (⌘⇧arrow becomes "Send tab", ⌘⇧U becomes "Merge pane"), so the sheet always matches reality.

**Drag.** A tab's unified drag mirrors the sidebar's `SessionRowDrag` on the horizontal strip:
over a pane → split it at the pointer; squarely over another tab → pair the two into a split; between
tabs → reorder the branch's sessions (horizontal twin of the reorder line); a split member dragged
back to the strip leaves its split. Reuses the same store ops (`dropZone`/`performDrop`,
`pairTarget`/`performPair`, `unsplitSession`) — which already enforce "a session lives in one leaf,
never duplicated" — plus a new horizontal `reorderTab`/`tabReorderLine`.

All slices runtime-verified by driving the built app (split-with-cluster, lone-tab-with-stashed-split,
settings toggle, `⌃⇥` cycling, the shortcuts Tabs group) and the tabs-off default confirmed unchanged.

## A worktree Delete can no longer fire from one stray keypress

The Command menu's confirm frames opened with their **first item pre-selected** (`push` → `query=""`
→ `didSet activeIndex=0`), and the native `confirmRemoveBranch` listed **"Delete worktree" (rm the
folder from disk) as that first item** — an order the `working.html` source of truth never had (it
leads with the non-destructive "Remove from sidebar"). The native port had silently inverted the two.
Net: opening the remove-worktree confirm and pressing **Enter once** deleted the checkout from disk,
and that confirm is reachable by `⌘D` on a branch row (the 2026-07-13 "close current context") as well
as ⌘K. This is not hypothetical — a real `holibob` worktree (`redesign-improvements`) was deleted this
way, renamed aside to `.deleting-…` by `detachWorktree` while its running processes carried on from
memory. (Recoverable precisely because phase-one is a rename, not an rm; the background rm / next-launch
`sweepDetachedWorktrees` is what makes it permanent.)

Fix, both layers: **a `.confirm` frame never opens on a destructive row.** The selection starts on the
frame's first non-`danger` item — Cancel for the remove/close confirms (so a reflexive Enter is a
no-op), while the one confirm whose lead item isn't destructive (the agent-worktree approval's
"Create") keeps its top row. Native: `PaletteModel.initialIndex(for:)` in `push`, plus the
`confirmRemoveBranch` order restored to match the design (Remove-from-sidebar before Delete-worktree,
so even a regressed default can't land on disk-deletion). Design: `paintList` starts a confirm on its
first non-danger row in both `working.html` and `big-picture-design.html` (invariant held). The
`sweepDetachedWorktrees` / `detachWorktree` machinery itself is unchanged — it did exactly what it was
told; the bug was telling it.

## Destructive mouse actions go instant, with an undo pill as the net

Closing a session or removing a project no longer stops to confirm. The gesture just does it — the
row soft-deletes immediately and an **undo pill** parks it at the bottom-centre for a window, draining
a countdown bar; until it empties the removal can be brought back. This replaces the old model where
*every* Close/Remove drilled into a ⌘K confirm frame (`requestDelete → confirmFrame`), a friction the
in-code comments already claimed didn't exist ("idle sessions go straight through" — the code never
implemented it). Speed is the product's first principle; a confirm on the most common gesture violated
it, and an undo net is the safer, faster trade.

**Decisions (settled with the user):**

- **Undo lives only for the window.** No archive/restore surface — when the bar empties the removal
  commits and the detached nodes are let go. The pill *is* the safety net, matching a browser's
  "reopen closed tab" feel, not a trash can.
- **Every close raises a pill**, including the frequent session close — consistency over quiet. One
  pill at a time; a new destructive action commits the previous one.
- **Undo = click the pill or ⌘↩** — the same chord that jumps a notification, which now prefers a
  pending undo when one is up and falls through to the notif deck otherwise.
- **Window = 8s** (`UNDO_MS`), longer than the 6s notification drain — destructive actions get extra
  reaction room. The pill pauses its countdown on hover so the cursor can reach *Undo* without the
  window closing under it.
- **The one action that still confirms is deleting a worktree.** Its two outcomes differ irreversibly
  — *Remove from sidebar* (folder + branch stay on disk) vs *Delete worktree* (rm the folder) — so the
  deliberate fork stays. But both arms then soft-delete with the same undo pill ("Removed …" /
  "Archived …"), so nothing is actually torn off disk until the window closes: the confirm picks the
  outcome, the pill guards the seconds after.

**How it's built (reuses existing grammar, no new machinery invented).** A `softRemove(unit, {label})`
replaces the old hard `removeUnit`: it snapshots the unit's DOM anchors (and, for a claude session, its
owned browsers via the ADR-0011 cascade) up front, runs the row-exit animation, detaches the nodes
keeping the refs alive, then settles the tree through the shared `settleAfterRemoval` (the old
removeUnit tail: roll-up, prune/reflow the layout, fall focus up the hierarchy). `pendingUndo.restore()`
slots every node back at its anchor and re-opens it if it was the open session; the commit path just
drops the refs. The pill is an actionable `.fb-toast--undo` that drains the **notif countdown bar**
(`.notif__timer` / `notif-drain`, `--life`) and commits on its `animationend` — bar and timer can't
disagree. Every delete gesture (kebab, tab ×, ⌘W, ⌘D, `d`, and the ⌘K Close/Remove items) funnels
through the one `requestDelete` choke point, so the whole surface changed at once.

Landed in both `working.html` and `big-picture-design.html` (the subset invariant holds — the two
still diff only by title + the browser/simulator demo rows). Runtime-verified by driving the design in
a Synth browser: instant close with the owned-browser cascade, undo via click **and** ⌘↩ both restore
the full set, auto-commit after the 8s window, the worktree fork still confirming, and a fork arm
soft-deleting with the right label. **Native app (`app/`) is out of scope for this design pass** — its
ports already mirror the non-blocking model; porting soft-delete+undo to SwiftUI is a follow-up.

## The native app lands the instant-actions + undo pill

The follow-up above is done — the SwiftUI app now behaves like `working.html`. The choke point
`AppStore.requestDelete` (kebab ×, tab ×, ⌘W, ⌘D, `d`) no longer opens a ⌘K confirm frame; a session
or project soft-deletes instantly and an 8s undo pill (`UndoPill.swift`, `AppStore.pendingUndo`) parks
it at the bottom-centre, draining the notification deck's countdown bar (`NotifTimerBar` grammar) and
pausing on hover. Click the pill or ⌘↩ to bring it back — the chord now beats the notif-deck jump —
else the bar empties and it commits. The ⌘K Close/Remove items reroute the same way.

The three soft mutators (`softCloseSession` / `softRemoveWorkspace` / `softRemoveBranch`) detach the
model reversibly and defer the two irreversible side-effects — `teardownSession` (the PTY/agent
process kill) and `deleteWorktreeFolder` (the on-disk `git worktree remove`) — into the pill's commit
closure, so an undo inside the window leaves processes and the checkout fully intact; `restore` slots
the rows back at their captured indices (a claude session brings its owned browsers with it). Only one
pill is live at a time — a fresh gesture commits the previous. Deleting a worktree keeps its deliberate
remove-from-sidebar / delete-worktree fork; both arms then soft-delete with the pill. The hard
`closeSession`/`removeBranch` stay for the non-gesture paths (a session exiting on its own, a
failed-create rollback); the vestigial `RowMenu` popover is untouched.

Runtime-verified by driving the built app over its control socket: `automation.requestDelete` on a
session left the palette closed (instant, no confirm) and the row gone, the undo pill rendered "Closed
…" with its bar, the owning claude's browser cascaded out with it, `automation.key` ⌘↩ restored the
set, the branch Remove still opened the `Remove main?` fork, and its "Remove from sidebar" arm
soft-deleted with a "Removed main" pill. `working.html` is untouched by the port.

## The undo folds into the notification deck (supersedes the bespoke pill above)

The two entries above shipped the undo as its own bottom-centre toast — `.fb-toast--undo` in the
design, `UndoPill.swift` in the app. That's a third toast primitive competing with the notification
deck, which already carries exactly what an undo needs: a glass card, a draining countdown bar, ⌘↩,
and click-to-act. UI is consistency, so the undo now **is** a notification: a session-less `.undo`
card raised into the same deck, same bottom-left corner, same chrome. The bespoke pill is deleted in
both files (`UndoPill.swift` gone; `.fb-toast--undo` CSS/JS gone).

- **Design (`working.html` + big-picture):** `softRemove` raises a synthetic session-less key into
  `notifState` with `kind: 'undo'`; `notifOrder`/`buildNotif`/`renderNotifs` render it as a
  `.notif--undo` card (undo glyph, "Closed …", the deck's `.notif__timer` bar, `⌘↩ undo` hint).
  Clicking the card or ⌘↩ restores; the bar's `animationend` commits. Ranked ahead of error/input/done
  so a just-triggered undo sits in front.
- **Native (`app/`):** a `.undo` case on `NotifKind`; `softDelete` appends a session-less `InAppNotif`
  (message = label, `iconPath` = `Phosphor.reset`, `life` = 8s) and arms it through the deck's own
  `armDoneToast` drain — whose expiry now runs the stored `undoActions[id].commit`. `NotifCard` renders
  `.undo` as a single-line card with the timer bar and an "undo" hint; the click and ⌘↩ resolve to
  `performUndo`. `pendingUndoNotif` gives ⌘↩ its undo-first priority. `InAppNotif` gained a per-instance
  `life` (the timer bar was hardwired to `doneLife`), so the 8s undo drains at the right rate.

A real consequence of reusing the deck: the undo now inherits the deck's drain brakes — it **pauses on
hover and while Synth is unfocused**, banking its life and resuming on return. That's stricter than the
old always-draining pill, and it's the right behaviour: your undo window waits for you, exactly like a
notification. Verified by driving the built app — the `.undo` card shows in the deck
(`automation.notifs` reports `kind: undo`), ⌘↩ restores it (rows return, deck empties), and a
focus-held drain commits (card auto-dismisses, sessions stay gone). Design verified in a Synth browser
(card in `.notifs`, click + ⌘↩ restore). Subset invariant intact.

## Close-session moves from ⌘D to ⌘W (supersedes the ⌘D binding above and in prior entries)

The verb that closes the current context — the focused sidebar row when the keyboard owns the
sidebar, else the open session — is now **⌘W**, not ⌘D. Nothing else about it changes: it's still the
instant soft-delete + undo-deck flow (no "are you sure" — the deliberate remove-from-sidebar /
delete-worktree fork stays the sole confirm, unchanged), still the one `requestDelete`/`closeContext`
choke point every gesture funnels through. Only the chord moved, so ⌘W now matches the muscle memory
of every tab/session app (⌘W = close this thing) and frees ⌘D. The bare sidebar `d` key is untouched.

**Design (`working.html` + big-picture).** The keydown handler that read `⌘D` now reads `⌘W`; the
tabs-mode `⌘W` branch (close the active tab) is unchanged and still wins first in tabs mode, so the
new binding is the everywhere-else path. Shortcuts sheet General row is `⌘W Close session`; the Tabs
group's `⌘W Close tab` drops its old `⌘D` alias; the ⌘K session **Close** item shows `⌘W`. Subset
invariant held (the two files still diff only by title + the browser/simulator demo rows).

**Native (`app/`).** `closeContext()` now returns `Bool` (did it close anything) so ⌘W can fall
through to the stock macOS ⌘W window-close only when there's genuinely nothing to close (nothing
focused, or Settings open) — mirroring the design's "preventDefault only when there's a row." Because
`WindowGroup` auto-provides a stock ⌘W "Close Window", the local key monitor now owns ⌘W in **all**
modes (the old handler was tabs-only) and consumes it before it reaches the menu, so a real close
never leaks to the window; the File-menu "Close Session" item is rebound to ⌘W for discoverability but
the monitor is the authoritative binding. `Shortcuts.swift`, the palette `Close` kbd hint, and the
`requestDelete`/`TabStrip`/`Palette` comments all track ⌘W. Builds clean.

## Tabs mode: the keyboard cursor is branches-only, stated outright (not inferred from CSS)

In Tabs mode the sidebar is 2-deep — sessions are tabs in the panes, not tree rows — so `J`/`K`
(and `↑`/`↓`) must walk repos and branches only, never a session. The native app (0.12.2) was
leaking the cursor into the now-hidden session rows: pressing `J`/`K` stepped through sessions you
can no longer see in the tree.

Root cause: keyboard-nav membership was never told about Tabs mode. `treeRows()` derived the
navigable list purely from *visual* visibility (`row.offsetParent === null`), and Tabs mode's
`.session { display:none }` only *happened* to make that true in the web prototype — the cursor
skipped sessions by luck, not by rule. Any render path that keeps the rows laid out (the native
app's, which doesn't hide sessions via an offsetParent-nulling `display:none`) has nothing telling
it those rows aren't part of the tree, so the cursor walks them.

Fix: encode the structural rule directly. `treeRows()` now drops `[data-session]` rows up front when
`tabsMode` is on, before the visibility filter — so "in Tabs mode the sidebar is branches-only" is a
stated invariant of the nav model, independent of whatever CSS happens to be hiding the rows. Landed
in both `working.html` and `big-picture-design.html` (subset invariant held — the two still diff only
by title + the browser/simulator demo rows). Verified by driving the design in a Synth browser: with
Tabs on and every repo expanded + a session open (peek active), `J`/`K` walk repos → branches →
Settings and never land on a session; with Tabs off the same tree still exposes all 8 session rows to
the cursor, so the default build is untouched. The native port (`AppStore.tabsMode` /
`SidebarNavigator`) is the follow-up that carries this rule into the app the user reported against.

## Tabs mode: the rest of the sidebar shortcuts stop toggling a branch's invisible disclosure

The same fix-the-cursor pass surfaced its siblings. In Tabs mode a branch is the deepest sidebar row
(its chevron is hidden — "nothing to disclose"), yet every disclosure-driven shortcut still treated a
branch as an expandable group and toggled its now-hidden session accordion: `→`/`←` "expanded"/
"collapsed" an invisible list instead of moving the cursor, `Tab` flipped it, and `Enter`/click did
too — each a silent no-visible-effect action, exactly the "few wrongs" reported.

Same root cause as the cursor leak: each path re-derived "is this an expandable group?" from the raw
`[data-toggle]` markup, which Tabs mode never updated. Fixed with one predicate both files now share —
`canDisclose(row)` = a `[data-toggle]` row that is *not* a branch while `tabsMode` is on (repo heads
still disclose their branches; branches no longer disclose sessions). Every disclosure path routes
through it: the click handler, `activateRow` (`Enter`/`Space`), `toggleGroup` (`Tab`, plus its keydown
guard so `Tab` on a branch is a clean default no-op), and the `←`/`→` repo-resolution. Activating a
branch — which used to toggle nothing visible — now does the useful thing: `openBranch(row)` brings
that branch's tabs on screen (its already-open session if it owns one, else its first) and moves focus
into the content pane, the sidebar's twin of clicking into the branch; an empty branch is a safe
no-op. `a`/`r`/`d` and `⇧J`/`⇧K` never keyed off disclosure, so they already worked and are unchanged.

Landed in both design files (subset invariant held). Driven-verified in a Synth browser, Tabs on:
`→`/`←` move the cursor down/up on a branch with zero disclosure churn; `Tab` on a branch is inert
while `Tab`/`Enter` on a repo head still expand/collapse it; `Enter`/click on a branch opens its tabs
and focuses content (empty branch no-ops); `r` opens the inline rename, `d` the remove-worktree
confirm, `⇧J`/`⇧K` reorder. Tabs off is byte-for-byte the old behaviour — `→`/`Tab`/`Enter` still
disclose a branch's sessions and `J`/`K` still walk into them. Native port carries `canDisclose` +
`openBranch` alongside the `treeRows` rule above.

## Every in-app notification stacks — nothing replaces (supersedes "one pill at a time")

In-app notifications now stack like a browser's: a new one joins the deck rather than evicting whatever
is still on screen, and each fades out on its own timer. This reverses the **"One pill at a time; a new
destructive action commits the previous one"** decision from the *Destructive mouse actions go instant*
entry above — the user's principle is that a notification should never silently swallow an earlier one
you haven't seen. Fixed at the two roots where a notification could replace rather than stack, both in
`working.html` and `big-picture-design.html` (subset invariant held — the two still diff only by title +
the browser/simulator demo rows):

- **Confirmation toasts (`.fb-toast` — "On it", "Handed to Mail").** `flashToast` opened by wiping every
  existing toast (`querySelectorAll('.fb-toast').forEach(remove)`) and shared a single module-level
  `toastTimer`, so a second toast both deleted the first's node and cancelled its dismissal — pure
  replace. Now toasts live in a lazily-created bottom-centre `.fb-toasts` flex column (`column-reverse`,
  so the newest slides in at the bottom and older ones ride up); each toast owns its own dismissal
  `setTimeout` and removes only itself. No shared timer, no eviction.
- **Delete/close undo cards.** The undo card already rendered through the notification deck, but its
  state was a single `pendingUndoKey`, and `softRemove` called `commitPendingUndo()` up front — so a
  second delete committed the first's undo before its 8s bar drained. This was the user's actual
  symptom ("delete a session… it didn't seem to stack"). Now `pendingUndos` is a `Set`; each removal
  parks its own card and each card commits/undoes its own key (the card's click → `performUndo(key)`,
  its bar's `animationend` → `commitPendingUndo(key)`). ⌘↩ still undoes, now targeting the front-most
  (newest) undo card. Several removals can wait for undo at once, each on its own countdown.

Design verified by driving it in a Synth browser: three feedback submits left three stacked "On it"
toasts co-resident (`column-reverse`, all faded in) instead of one; deleting two workspaces parked two
independent undo cards in the deck, and undoing the newest restored exactly that workspace while the
other card kept standing.

**Native app (`app/`) landed in the same change.** The Swift side only ever had the *undo* root — its
confirmation toasts already append to the shared deck (`notifs`), which stacks, so there was no
separate replace-on-toast primitive to fix. The undo was single via two things: `softDelete` opened
with `commitPendingUndo()` (evicting the previous), and undo resolution picked `notifs.first(kind: .undo)`.
The per-card drain machinery (`armDoneToast` / `undoActions` / `notifDismissTasks`, all keyed by notif
id) was already per-id and shipped, so stacking needed only: drop the `commitPendingUndo()` in
`softDelete`; replace the shared `resolveUndo`/`performUndo()`/`commitPendingUndo()` with a per-id
`performUndo(_ id:)` (card click → `performUndo(notif.id)`); and repoint `pendingUndoNotif` at the
front-most undo (`notifOrder.first { .undo }`) so ⌘↩ undoes the newest. `swift build` links clean;
change is a minimal, faithful mirror of the browser logic on top of the already-tested per-id drain.

## Tabs: double-click a tab to rename, right-click for its ⌘K menu

Two direct-manipulation gestures on the experimental Tabs strip, each the horizontal twin of a
gesture the sidebar row already has — so a tab is now as editable as the row it stands in for. Both
land only in tabs mode; tabs-off is untouched.

**Double-click → inline rename.** Double-clicking a tab's name swaps the label for an editable field
with the whole name preselected — ↵ commits, Esc reverts, clicking away commits — exactly the sidebar
row's `r` rename, keyed on the same `renamingRowID`/`renameText` store fields and the same global
Return/Esc monitor, so committing the open session's tab updates its pane title for free. Applies to
both a lone tab and a bonded split-member (cluster) chip.

**Right-click → the session's ⌘K frame.** Secondary-clicking a tab opens the command palette pinned
to that session — the same `openRowActions(.session)` the sidebar row's ⋯ kebab / right-click opens,
so a tab surfaces the exact grouped Session verbs (Rename / Close, plus the branch/project search
groups) with no bespoke per-tab menu to keep in sync.

**Design (`working.html` + big-picture).** A `startTabRename` mirrors `startRename` on the tab's
`.tab__name` (contentEditable, select-all, commit through `renameUnit` so the sidebar row + open pane
stay in sync); `content` gains `dblclick` → rename and `contextmenu` → `openRowActions` handlers, both
`tabsMode`-guarded. A click inside a renaming tab just moves the caret (the tab-open and tab-drag paths
skip a `.tab__name[contenteditable]`), so editing never re-opens or drags the tab. Subset invariant
held (the two files still diff only by title + the browser/simulator demo rows).

**Native (`app/`).** `TabChip`/`ClusterChip` gain a `renaming` branch that shows the sidebar's
`RenameField` (made internal) in place of the button, plus `.onDoubleClick { beginRename(.session) }`
and `.onSecondaryClick { openRowActions(.session) }`. A new `DoubleClickCatcher` — the double-click
twin of the existing `SecondaryClickCatcher` — is a transparent AppKit overlay whose `hitTest` claims
only the second click of a plain left double-click and declines everything else, so single-click open,
the tab drag (reorder / pair / split), and the close button all pass straight through. While a tab is
renaming its drag stands down (`highPriorityGesture … including: .subviews`), so drag-selecting the
name in the field never hijacks into a tab drag — the app twin of the mock's contentEditable guard.
Builds clean.
