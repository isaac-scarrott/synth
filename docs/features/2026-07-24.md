# 2026-07-24

- **Two perf follow-ups: feedback submit no longer freezes, palette builds its list once** — the
  feedback sheet's submit resolved its `feedback/<slug>` branch name via `GitService.allBranches`
  (a `git for-each-ref` over heads + remotes) synchronously on the main actor — hundreds of ms of
  freeze on a big/cold repo. Now the "On it" toast fires immediately and the name resolves off-main
  through the existing `runGit` chain (same shape as `addBranchFromPrompt`), with the pending row
  added when it's known. Separately, `PaletteOverlay` rebuilt its item list three times per render
  (`.isEmpty`, `.count`, and the `rows` getter, each re-running build + fuzzy + sort); it's computed
  once now. Both behaviour-preserving (palette open/filter/No-results/close driven); `working.html`
  untouched.

- **Scaling-perf pass: persistence, palette/drag scans, and browser-open moved off the main-thread hot
  path** — a `sample`-profiled + agent-audited sweep of the heavy subsystems (the same session that
  killed the autofill walk below) fixed three main-thread hazards that worsen with session count.
  (1) **Persistence off-main:** `saveNow()` built the whole tree into Codable structs, JSON-encoded
  it, and wrote a backup + primary atomically — synchronously on the main thread, on every ⇧J/⇧K
  reorder keystroke, every split, and every 4s autosave tick. Now the encode + diff + atomic write
  run on a serial background queue that owns `lastBytes`; `snapshot()` stays on the main actor; the
  terminate path uses a synchronous `flush()` so quitting never drops the last edit (verified: async
  reorder persists, and a reorder 0.3s before SIGTERM still lands). Reorder main-thread cost fell
  28ms→6ms on the 30-session tree, and it no longer scales with total state. (2) **O(N²)→O(N):** the
  ⌘K root/session search rebuilt every session's "workspace / branch" context by calling
  `store.branch(of:)`/`workspace(of:)` — full-tree scans — per session, per keystroke; now the
  enclosing loop's ws+br is threaded through, and `Layout.pairTarget` builds a `sessionID→branchID`
  map once per drag frame instead of scanning per candidate row. (3) **Browser open non-blocking:**
  `BrowserPane` built the engine synchronously inside its view body, so a CEF spawn (which pumps the
  main runloop) froze the app mid-open; the pane now paints a placeholder card and bootstraps the
  engine on the next runloop turn (reusing the non-focused-create deferral), with `controller(for:)`
  and every automation caller left on their synchronous contract. All three are behaviour-preserving
  and were driven-verified; `working.html` is untouched.

- **Every native text field focuses instantly — the password-autofill key-view walk is killed app-wide** —
  the same heuristic the ⌘K palette had to escape into its own `NSPanel`
  (`_showPasswordAutoFillIfNecessaryForView` → `NSHostingView._recursiveGatherAllKeyViewCandidates`
  → `FocusNavigator.allItems`, a per-node uncached protocol-conformance walk of the field's whole
  window) fired for **every** other field too: focusing them walked the entire main-window tree
  (sidebar rows + open panes) on the main thread. Profiled on the 30-session / 10-branch tree with
  `sample`: inline rename (`r`) cost **412ms** of main-thread CPU per focus and the feedback field
  (⌘⇧F) **358ms** — both dominated by a ~3600-sample gather subtree, scaling with the tree so it
  worsened as sessions piled up. Synth has no native password/username fields (rename, feedback,
  settings, palette, the browser omnibox are all plain text; web-content autofill lives inside
  CEF/WKWebView, untouched), so the heuristic only ever burned the walk and showed nothing. Fixed by
  replacing `-[NSAutoFillHeuristicController _showPasswordAutoFillIfNecessaryForView:withCompletionHandler:]`
  with a no-op at launch (`AutoFillSuppression.install()` from `applicationDidFinishLaunching`),
  guarded on the private symbols still existing so a future macOS just restores the old (slow) walk,
  never a crash. After: **rename 412ms → 3ms** (137×) and **feedback 358ms → 90ms** (residual is the
  sheet's own render, gather gone) — both now under the RAIL <50/<100ms interaction bars. One source
  fix covers rename, feedback, settings, the omnibox and the add-project sheet at once, and immunises
  future fields, where the palette needed a whole `NSPanel` to escape the same walk. Verified
  behaviourally: the palette still filters as you type (14→2 items) and an A/B on the same binary
  (autofill kept vs suppressed) showed identical field behaviour — the change is a pure perf no-op on
  editing, so `working.html` is unaffected.

- **⌘K palette opens instantly again — the ~240ms key-view stall is gone (native app)** — making
  the palette's search field first responder fires AppKit's password-autofill heuristic, which
  gathers every focusable key-view in the field's window (`_showPasswordAutoFillIfNecessaryForView`
  → `NSHostingView._recursiveGatherAllKeyViewCandidates` → `FocusNavigator.allItems`, a per-node
  uncached protocol-conformance walk). The key-view loop is per-window, so while the palette was a
  SwiftUI overlay on the main window that walk crossed the whole app tree — sidebar rows + every open
  pane — and cost ~250ms, widening as a session piled up. Fixed by hosting the palette in its own
  borderless child `NSPanel` (`PaletteHost` / `PalettePresenter`, driven by `store.palette`): the
  field's first-responder window is now the panel, whose tree is just the palette, so the gather sees
  a handful of nodes instead of hundreds. Measured on a 30-session / 10-branch tree with `sample`:
  the gather went from **1174 samples in the stack (~250–290ms of main-thread CPU per open) to zero**;
  the felt main-thread drift on open dropped from ~250ms to ~40ms. It's a standalone `NSPanel`, not a
  `addChildWindow` child, so the main window stays the *main* window (traffic lights keep their colour)
  while the panel merely takes *key* for text input — verified `rootIsMain` stays true with the
  palette open. Focus held over 25/25 driven opens on both empty and loaded trees; typing/filter,
  arrow-nav + Enter to run, Esc, ⌘K toggle, kebab drill and ⌘N all still drive the panel. Pure
  hosting change — `PaletteOverlay` and every palette interaction are untouched, so `working.html`
  is unaffected. Completes the "left standing" note on the focus fix below.

- **⌘K reliably focuses the palette input again** — opening the palette set focus on its
  SwiftUI `TextField` via `@FocusState` in `.onAppear`. Making any text field first responder
  triggers AppKit's password-autofill heuristic, which asks SwiftUI to gather every focusable
  key-view in the window (`_recursiveGatherAllKeyViewCandidates` → `FocusNavigator.allItems`), a
  main-thread traversal with an uncached protocol-conformance lookup per node. `sample` put it at
  ~240ms per open, and it scales with the view tree — so a long-running session that had piled up
  sessions and panes widened the window during which the `@FocusState` set silently never applied,
  leaving the input unfocused and dropping the keystrokes into the pane underneath. That regression
  grew as the app got more loaded, which is why it "used to work." Fixed by bridging the input from
  AppKit (`PaletteQueryField`, an `NSViewRepresentable`) and grabbing first responder imperatively
  with `makeFirstResponder` — immune to the starved SwiftUI focus cycle. Live filtering, the
  dash-spaces transform, frame-drill refocus, and rename-seed select-all are preserved. Driven-app
  verified across empty and heavily-loaded trees. Left standing: the ~240ms key-view traversal
  itself is inherent to SwiftUI computing the window's key-view loop on focus; killing it would mean
  isolating the palette in its own window or pruning focusable candidates — a larger change, not
  bundled here.
