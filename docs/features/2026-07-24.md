# 2026-07-24

- **⌘K palette opens instantly again — the ~240ms key-view stall is gone (native app)** — making
  the palette's search field first responder fires AppKit's password-autofill heuristic, which
  gathers every focusable key-view in the field's window (`_showPasswordAutoFillIfNecessaryForView`
  → `NSHostingView._recursiveGatherAllKeyViewCandidates` → `FocusNavigator.allItems`, a per-node
  uncached protocol-conformance walk). The key-view loop is per-window, so while the palette was a
  SwiftUI overlay on the main window that walk crossed the whole app tree — sidebar rows + every open
  pane — and cost ~250ms, widening as a session piled up. Fixed by hosting the palette in its own
  borderless child `NSPanel` (`PaletteHost` / `PalettePresenter`, driven by `store.palette`): the
  field's first-responder window is now the panel, whose tree is just the palette, so the gather sees
  a handful of nodes instead of hundreds. Measured on a 30-session / 10-branch tree with `sample`:
  the gather went from **1174 samples in the stack (~250–290ms of main-thread CPU per open) to zero**;
  the felt main-thread drift on open dropped from ~250ms to ~40ms. It's a standalone `NSPanel`, not a
  `addChildWindow` child, so the main window stays the *main* window (traffic lights keep their colour)
  while the panel merely takes *key* for text input — verified `rootIsMain` stays true with the
  palette open. Focus held over 25/25 driven opens on both empty and loaded trees; typing/filter,
  arrow-nav + Enter to run, Esc, ⌘K toggle, kebab drill and ⌘N all still drive the panel. Pure
  hosting change — `PaletteOverlay` and every palette interaction are untouched, so `working.html`
  is unaffected. Completes the "left standing" note on the focus fix below.

- **⌘K reliably focuses the palette input again** — opening the palette set focus on its
  SwiftUI `TextField` via `@FocusState` in `.onAppear`. Making any text field first responder
  triggers AppKit's password-autofill heuristic, which asks SwiftUI to gather every focusable
  key-view in the window (`_recursiveGatherAllKeyViewCandidates` → `FocusNavigator.allItems`), a
  main-thread traversal with an uncached protocol-conformance lookup per node. `sample` put it at
  ~240ms per open, and it scales with the view tree — so a long-running session that had piled up
  sessions and panes widened the window during which the `@FocusState` set silently never applied,
  leaving the input unfocused and dropping the keystrokes into the pane underneath. That regression
  grew as the app got more loaded, which is why it "used to work." Fixed by bridging the input from
  AppKit (`PaletteQueryField`, an `NSViewRepresentable`) and grabbing first responder imperatively
  with `makeFirstResponder` — immune to the starved SwiftUI focus cycle. Live filtering, the
  dash-spaces transform, frame-drill refocus, and rename-seed select-all are preserved. Driven-app
  verified across empty and heavily-loaded trees. Left standing: the ~240ms key-view traversal
  itself is inherent to SwiftUI computing the window's key-view loop on focus; killing it would mean
  isolating the palette in its own window or pruning focusable candidates — a larger change, not
  bundled here.
