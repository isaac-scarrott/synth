## The first tab's fill runs under the sidebar, not up against it

In tabs mode the strip's first tab meets the sidebar's rounded right edge (`--radius-panel`, 20px).
The tab's fill stopped square at that seam, leaving a wedge of panel colour between the straight
edge and the curve. At a glance the tab read as clipped — as if the sidebar had cut a corner off it.

The first attempt rounded the strip's own top-left with `--radius-app` so the fill flowed into a
radius of its own. It fixed the hard corner and nothing else: two curves with a gap between them
still show you exactly where the fill ends. The tab still looked like it stopped short.

What it should do is not end at all. The fill continues past the seam and the sidebar's corner is
what ends it — the tab reads as a surface the sidebar sits on top of, which is what the z-order
already says. Nothing about the sidebar changes; the occlusion does the work.

The mock can't do that with the tab alone. `.content` and `.tabstrip__tabs` both clip their
overflow, so a negative margin on `.tab:first-child` gets cut at the same seam it's trying to cross.
So the run-on is a bare `.tab-bleed` block inside `.app`, 20px wide at the sidebar's trailing edge,
and `.sidebar` takes `position: relative; z-index: 1` so it stacks over it. Two mutually exclusive
states — open, and hovered-while-not-open — so the cascade resolves the bleed exactly as the tab's
own background resolves.

Native has no such clip: SwiftUI doesn't clip to bounds and `RootView` already gives the sidebar
`.zIndex(1)`, so the run-on hangs off the tab itself as a leading background offset by
`-Theme.radiusPanel`. That's the better shape, and it's why `TabChip` now routes its background
through a single `fill` property that the run-on also reads. Active, hover and the run-on are one
expression — they can't drift apart as states get added.

One knock-on, an old divergence the fix surfaced. `.tab:hover` out-specified `.tab--active` (0,2,0
against 0,1,0), so in the mock hovering the open tab washed its raised fill back down to the hover
tint; Swift, which branches on `isActive` first, never did. Settled in Swift's favour — an open tab
holding its fill under the pointer is the correct read, since the wash means "you could open this"
and there's nothing to open. Scoped to `.tabstrip__tabs > .tab:not(.tab--active):hover` so a
cluster's chips, which carry their own fill and never took the wash, stay untouched.

Verification worth recording: the native hover state could not be driven. A synthetic `mouseMoved`
posted straight to the pid — the technique that works for keys on a window parked on another Space
— doesn't reach an inactive window's `NSTrackingArea`, so `.onHover` never fires and the screenshot
comes back un-hovered. Both mock states were confirmed with a real CDP cursor; the native hover
rests on the single-`fill` structure instead of a pixel.

## Device previews are drawn from real hardware, and show the page as the phone's browser would

Both surfaces that draw a phone — the simulator session and the browser's device mode — drew a
generic black rounded rectangle: one fixed 232×476 box with a screen on it (the wrong aspect for
any shipping iPhone), and a frame with a decorative pill floating near the top. Nothing accounted
for the hardware. The simulator had no cutout at all and put the device's own name where iOS puts
the battery. Device mode had an island, but the page ran under it as if it weren't there, with no
status bar, no Safari, and no home indicator — so it answered "how wide is this page" and not the
question you open it for, which is what the thing looks like on the phone.

Both now render from one device model. Every number in it is the hardware's own, in the points the
device reports: bezel per edge, body and screen corner radii, status-bar height and inset, home
indicator. Because the frame lays out at true viewport size and only then scales to fit the pane,
those proportions survive at any pane width — the bezel-to-screen ratio stays the real one instead
of a constant that looks right at one size. The bezel is stored per edge rather than as a shorthand
because rotating has to walk each edge one place round: an SE's tall forehead ends up on the left,
not still on top, and the same rotation carries the island, the home button and every side button
with it. Side buttons are hardware, so they're on the rail, and only the Pro-era iPhones get an
action button.

The bigger change is that the screen now draws what the device draws. A page on a phone renders
inside Safari, so Safari is there: the tab bar at the bottom in portrait, folded into a single top
bar in landscape with the status bar dropped, which is what iOS actually does — the page's usable
height moves with the rotation, and you can see it move. iPad Safari keeps its bar and tab strip on
top; Android gets Chrome's single top bar and a gesture pill; the SE gets a home button and no
indicator to draw. The status bar carries the real trio (cellular, wifi, battery) and parts around
the island. Landscape insets the page clear of the island the way the safe area does.

The simulator is a booted device running an app, not a page, so it gets an app's chrome instead —
large title, tab bar, home indicator — and its device comes from the session's own name, so an
iPhone we don't carry in the fleet still boots on iPhone hardware rather than a guess.

The device screen is deliberately always light, in both themes: it's a separate machine showing a
light page, and following the app's appearance would be claiming something about the page that
isn't true. Safari's bar dropped its `backdrop-filter` — there's nothing behind it to blur in a
mock, and the filter broke the screen's corner clipping, leaving grey wedges in the two bottom
corners of every phone.

### The native port, and what it costs the page

`DeviceMode.swift` carries the same model the mock does — per-edge bezel, radii, status-bar
metrics, home indicator — and `DeviceChrome.swift` draws the hardware and the device's own browser
around the live engine view. Every metric is a device point times the stage's fit scale, so the
frame stays crisp at any fit instead of rasterising through a `scaleEffect`.

The consequence the mock could dodge and the app can't: with Safari's bars drawn, the page cannot
also have the space they occupy. So the CDP override now emulates `pageViewport` — the screen minus
the device browser's bars — and the strip's readout reports it. iPhone 16 reads 393 × 694 instead of
393 × 852, the SE 375 × 554 (a real SE gives Safari 553). That is the point of the change rather
than a side effect: at the old full-screen height a `100vh` hero passed a check no iPhone ever gives
that much room for, and device mode said it was fine. `browser.deviceMode` follows — `viewport` is
what the page gets, and a new `screen` carries the hardware size for anyone who wants both.

Two deliberate divergences from working.html. The status-bar trio is drawn from the mock's own SVG
rather than SF Symbols, so the shapes are the same glyphs and not lookalikes (the rule Phosphor.swift
already sets for the app's own icons). And landscape does *not* inset the page clear of the island
the way the mock's `.devui__page` does: a real iPhone hands the page the full width and leaves the
inset to `env(safe-area-inset-*)`, so cropping it here would hide exactly the bug the preview exists
to show. The island overlaps the page, as it does on the device.

Verified by driving the built app over the control socket: iPhone 16 portrait and landscape, SE,
Galaxy S25 Ultra, iPad mini, and the exit back to the full-pane engine, each screenshot in-process.
A `100vh` block in the test page lands exactly on the drawn page area, which is the proof that the
emulated viewport and the chrome agree.

## ⌘K search ranks flat — the best match is the top row

Typing into ⌘K used to bucket the results — Actions, Sessions, Branches, Projects — score each
bucket, then list the winning bucket *whole* before the next one's first row. The group with the
best single item led, and everything else it held came along with it. So the row you typed for
could be the best match in the palette and still sit six rows down, under five weaker siblings that
happened to share its heading. The ranking was honest per group and a lie overall, and it punished
exactly the query the palette is for: you know the name, you type it, you press ↵.

A query now drops grouping entirely. One list, every candidate scored against the same query, best
first, no headings and no dividers. Nothing about the scoring changed — an exact label still beats a
prefix, a prefix still beats a loose subsequence, and a ctx-path hit still can't outrank a label —
it just isn't partitioned before it's applied any more. Ties fall back to build order (actions,
then sessions, branches, projects), which is the old most-local-first instinct kept as a tiebreak
rather than as a wall.

Losing the headings costs nothing, because a row already says what it is: the icon carries the
type — branch glyph, session glyph, project chip — and the ctx path carries where it lives, so the
three `main` branches read as `synth`, `aviator-api`, `web-dashboard` without a "Branches" label
above them. The heading was spending a row to repeat what the row already showed.

Cold ⌘K is untouched. With no query there is no ranking to get wrong, and its groups are doing a
different job — Recent, then the context actions labelled by the scope they target — so they stay.
Grouping is now what the palette shows when it's telling you what's here, not when it's answering
a question you asked.

## Native port: ⌘K search ranks flat, and scoring reaches label-boost parity

The flat-ranking entry above, in the app. `PaletteModel.items` drops the per-group
bucket-and-sort for one flat scored list — best match first, `(score, build order)` as an explicit
sort key so the most-local-first tiebreak doesn't hang on sort stability — and strips `group`/`sec`
from the survivors so the view's header/divider sectioning renders nothing while a query is live.
The root frame's search branch loses its dead "Actions / Sessions / Branches / Projects" labels;
the cold frame keeps its groups untouched.

Porting it surfaced a scoring gap the buckets had been hiding: the native matcher had no
exact-label (+1000) or prefix (+200) boost and folded the context path in at −2 instead of −6 —
inside a group of siblings that barely mattered, but in one flat list it decides the top row.
`itemScore` now ports working.html's exactly, so typing a name lands on that name natively too.

En route: `automation.screenshot` now prefers a visible NSPanel (the ⌘K palette floats in its own
panel above the main window), because every palette-open capture it ever took showed no palette —
the evidence verb was blind to the one surface most worth evidencing. Verified against the built
app over the control socket: `main` → the three `main` branch rows lead; `dev` → `dev server` top;
`set` → Settings via the prefix boost; cold root still grouped. Screenshots confirm no headings
under a query.
