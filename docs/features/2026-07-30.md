# 2026-07-30

## A session reaps what left its process group, by the stamp in the environment

Closing a session has always reaped its process *group*: `killpg` on the private, `setsid`'d group
the login leader creates, which is the right unit for everything the shell runs in the foreground.
It is the wrong unit for anything that leaves the group deliberately. Claude Code's Bash tool
`setsid`s its background shells, so a dev server an agent starts is outside the group from the
moment it launches; when the shell that spawned it exits, it reparents to launchd and stops being
reachable by ancestry too. `killpg` can't find it, `TerminalManager.shutdownAll` can't find it, and
`InstanceRegistry.reapOrphanedSessionTrees` — which insists on a `/usr/bin/login` leader running a
`synth-login-<pid>.sh` script — can't recognise it. It outlives the row, the window, and the app,
and on a machine that stays up for a week it outlives everything but a reboot.

Measured on one ordinary day: **3.6 GB across 34 processes** sitting outside the reach of their own
sessions' groups, one session fragmented across eight groups, plus a day-old `pnpm dev:production`
tree still running for an instance that had been dead for two days.

What survives all three moves — leaving the group, reparenting, and the owning Synth exiting — is
`SYNTH_SESSION_ID`, which `HookEnvironment.decorate` already stamps into every PTY and every child
inherits. It is a property of the process image rather than of a relationship that can be broken,
which is exactly why it still answers when nothing else does. `SessionProcesses` reads it back out
of `KERN_PROCARGS2` and reaps by it, after the group signal and never instead of it.

Three things the obvious version gets wrong.

**A stamp can be unreadable, and it's the big ones that lose it.** `setproctitle` overwrites the
region `KERN_PROCARGS2` reads: Next.js renames itself to `next-server (v14.2.8)` and takes its own
environment with it, so the heaviest process in the tree is the one that cannot say who it belongs
to. Those are recovered from the nearest ancestor that still can — for a renamed server, the
launcher that forked it. On the measured machine that recovered 22 of 151 attributed processes.

**Carrying the stamp is not the same as being the session's work.** Anything launched from a Synth
terminal inherits the environment and keeps it for life. The machine this was written on had a
sixteen-day-old OrbStack carrying a session id from an instance eight generations dead, `setsid`'d
to its own group and reparented to launchd — by stamp and by ancestry indistinguishable from a
leaked dev server. The first draft would have killed it. What separates them is where they work: the
dev servers sit in `…/Synth/worktrees/<repo>/<branch>/…` and OrbStack sits in `/`. So a process is
reaped only when its cwd is inside a folder Synth created. That is positive evidence rather than a
blocklist of things not to kill, because a list of applications that daemonise is only ever as
complete as the last one someone hit. A dev server started in a checkout Synth doesn't manage is
missed, and that is the right way to be wrong: the cost is memory still held, not a process the user
wanted.

**One sweep is not cheap and both callers arrive in bursts.** Reading every process's environment and
then every survivor's cwd costs ~80 ms, quitting closes every session at once, and the pressure
source re-fires for as long as the machine is tight. Requests coalesce on a serial queue behind a
250 ms window, so a quit's worth of closes is one sweep rather than one each.

**A session id does not name a single lifetime.** `softReopenSession` tears a row down and then
restores the *same* `Session` object — same id — so the reap scheduled for the agent that quit would
have found the reopened one wearing its stamp and killed it. Only processes that started *before*
the row closed are reaped, taken from the kernel's `p_starttime`, which closes the pid-reuse hole in
the same move.

Two kinds of process can never be attributed, both by the kernel's choice rather than ours. A
SIP-protected platform binary has its environment stripped from `KERN_PROCARGS2` outright —
`/bin/sleep` reports no environment at all — and a `setproctitle` renamer has overwritten the region
it lived in. The second is recovered from its nearest stamped ancestor; the first cannot be, and
doesn't need to be, since every dev server worth reclaiming is a user binary.

Gate: `t21_escaped_reap`, which has to work to mean anything. A bare `sleep 900 &` is reaped by zsh
itself on exit, so a test built on it passes identically with this code deleted; `/bin/sleep` carries
no stamp to find, and a copy of it won't run at all. So the gate uses `nohup … & disown` on a user
binary, and asserts against the reaper's own log line rather than against the process merely being
gone — "gone" is precisely what the weaker version proved.

Two entry points beyond session close. At launch, anything stamped by an instance that is no longer
running is reaped — the pid in `SYNTH_SOCKET_PATH` makes "orphan" decidable rather than guessed, so
a live sibling instance is never touched. And a memory-pressure source runs that same orphan sweep
while we're up, since instances die while we're running and nothing else would reclaim them until
the next cold start. Pressure reclaims **orphans only, never a live session's processes** — a dev
server belonging to a row the user still has open is theirs, and the system asking for memory back
is not permission to stop it.

Quit is deliberately unchanged: the process is gone before the coalescing window elapses, so a quit
leaks its escapees exactly as it did before. They are caught at the next launch instead, by which
point this instance is dead and they are orphans by definition.

Channel isolation falls out of `AppSupport.dir`: Dev only ever reaps inside Dev's worktree root, and
a harness instance under `SYNTH_SUPPORT_DIR` can't reach the real one's processes at all.

Nothing about this is visible. No UI, no setting, no notification — a row closes and the things it
started stop, which is what closing a row already claimed to do.
