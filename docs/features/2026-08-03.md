# 2026-08-03


## An archived branch always has a way back

Archive was sold as reversible: put a worktree away, and pull it back from ⌘K → Archived when you
want it. Three separate gaps meant a branch could go in and never come out — reported from the real
thing, on `hol-519-…` in the holibob repo, as "I can't add it back, it doesn't show up".

An archived row does not leave `Workspace.branches`. It stays, with `archivedAt` set, so the Archived
list can reach it while `visibleRows` keeps it out of the tree. That one design choice — right in
itself — is what the three gaps grew out of, because every other surface kept treating the row as if
it were live.

**The picker hid it.** ⌘K → New branch filtered its offers against *every* row in the workspace, not
just the live ones. So an archived branch's name was taken: it wasn't in the sidebar, and it wasn't in
the one frame that adds a branch. The "New branch “x”" fallback didn't rescue it either — that only
appears when no git ref of that name exists, and the ref was right there. Typing the exact branch name
returned an empty frame. Now the filter reads `liveBranches`, and an archived match is offered wearing
the archive glyph and its "archived 3d ago" age, so picking it reads as putting the row back rather
than making a second one.

**Restore gave up when the folder was gone.** The sweeper holds a reclaimable folder aside as
`.archived-<name>-<epoch>` and the reaper deletes it once the hold expires. `restoreArchivedBranch`
handled the hold (a rename back) and returned `false` for the reap — and the one caller discarded the
Bool, so ⌘K closed and nothing happened. A silent no-op on the only route back. It doesn't decline
any more: **the branch is a git ref and the checkout is derived from it**, so a row whose folder is
gone gets the worktree cut again at its old path and waits pending exactly like a fresh create. The
reaper prunes as it deletes, so a plain `worktree add` is enough. No session template runs — a restore
that spawned sessions the archived row never had would be a create wearing its name.

**Restart forgot it.** `restore(from:)` drops any branch whose folder is *confirmed missing* (the
parent exists, the folder doesn't) on the reasonable theory that the user deleted the checkout outside
Synth. For an archived row the folder's absence is not evidence of anything — it is the sweeper doing
its job. So the next launch dropped the row: the Archived list forgot the branch, and a folder still
on hold was orphaned with nothing but the reaper's clock left to touch it. Archive state now survives
launch regardless of what is on disk; only live rows are reconciled against it.

What these have in common is worth keeping: the *branch* is the durable thing, the *folder* is a
cache. Every place that read the folder's absence as the branch's absence was wrong, and each one
individually stranded work. The lasting rule is that no gate on the restore path may end in "can't" —
at worst it costs a checkout.

Gate: `t9_archive` grew nine checks — the picker offers an archived branch (once, as a restore, no
create fallback) and picking it puts the row back; and after the reaper has taken a folder, the row is
still archived across a relaunch, restore returns it to the tree, and the re-cut worktree is a real
registered checkout of the branch.

*Rejected:* a "this branch is archived, unarchive it?" confirm in the picker (the pick already says
what it does, and archive is not destructive); dropping the reaped row from the store so the name
frees up in the picker (it loses the row's age and its remembered layout for no gain, and the ledger
of what you archived is the feature); an error toast on a failed restore (the failure was avoidable —
fixing it beats reporting it).

## A toast's × is where you aimed, not where the card ends

Reported against the update toast — "there's a close icon on the top right if you hover, but clicking
it does not close" — and it was every toast, because they all ride the one `NotifCard` chassis.

The card is a big target on purpose: its body carries the primary action, and `contentShape` gives
that tap gesture the rounded rect to answer for. The × is a `Button` in a `topTrailing` overlay,
hung 6pt past the corner so it never moves the layout. Both true, and in the wrong order — the
`contentShape` sat **above** the overlay, and a content shape confines everything beneath it. The ×
was beneath it. So the disc's live area was reduced to the thin crescent where an 18pt circle laps a
13pt corner radius: its centre answered nothing, and the pointer that was standing on the glyph was
standing outside the only shape that could hear it. Driving the pre-fix build proves it — a click on
the disc's centre does nothing at all, 3pt down and left of centre dismisses.

That is the whole complaint. A control that works only if you aim at its inside edge reads as broken
first and finicky second, which is exactly the order the report arrived in. The fix is the order:
the card's hit shape and its tap gesture are pinned under the × overlay, so the × keeps its own
clicks and the body keeps the rest.

Since it was undersized anyway — 18pt, half of it hanging off a corner, revealed on hover — the
target now reaches 3pt past the disc it draws. It has to be real padding: an *overlaid* wider circle
is not hit-tested outside its parent's 18pt frame, which is why the call site offsets by 9 (6 for the
overhang, 3 for the ring) to leave the disc itself on the design's -6/-6. `working.html` gets the
same invisible ring as `.notif__x::before`, so the spec still describes what ships.

Gate: SwiftUI hit-testing can't be driven by a real pointer on a window nobody is looking at, so
this was proven by posting synthetic clicks into the running app: the × centre dismisses without
firing the card's action (`installRequested` stays false), a point 11pt out — past the old 18pt disc,
inside the new ring — dismisses too, 14pt out correctly does not, and the card's own Restart button
still runs the action. The same battery against the pre-fix build fails at the disc's centre.

*Rejected:* pulling the × inside the card (it would move the layout and lose the corner the design
puts it on); dropping the card-body tap so the × has no competition (the body being a big target is
the feature); an `allowsHitTesting` patch on the overlay (the order was the bug — masking it with a
second modifier leaves the next person the same trap).

## Geist, and a type scale with six steps instead of twelve

Synth's type was the system face — `-apple-system` / SF Pro Text, SF Mono — and it had never been
designed so much as accumulated. Twelve distinct sizes lived between 9px and 15px, most of them half
a pixel apart (9, 9.5, 10, 10.5, 11, 11.5, 12, 12.5, 13, 13.5, 14, 15). Steps that small are not
a hierarchy; they are noise that reads as one undifferentiated grey mass. Eighteen rules carried
negative `letter-spacing` on top, tuned by eye against SF Pro.

The face is now **Geist** + **Geist Mono** (Vercel, OFL), self-hosted as the variable TTFs rather
than named cuts, because the `wght` axis is the whole point — see below. The web design files load
them from Google Fonts; the app registers the bundled TTFs with CoreText.

**The scale is six steps, each at least 1px apart:** 10 (micro-labels, badges) · 11 (meta) · 12
(body, session names) · 13 (labels, titles) · 14 (headings, dialog titles) · 15 (⌘K input). The floor
came up from 9px, body from 11.5. All eighteen negative-tracking rules are gone: they were SF Pro
calibration, and Geist sets ~2.3% narrower than SF Pro at the same size, so keeping them landed ~4%
tighter than the design intended. Positive tracking on uppercase micro-labels stays — that is real
typography, not compensation.

Leading opened to 1.5–1.65, which Geist needs on its own terms: its line box is **10% taller than SF
Pro's at the same size** (16.25pt vs 14.72pt at 12.5px), almost entirely a deeper descender. Its cap
height and x-height are, contrary to expectation, within a hair of SF Pro's — so this was never about
apparent size, only vertical room. Containers grew to match (rows 28→30, `.set-row__head` 22→24,
`.set-code--flags` 40→44, the round badges squared up).

*Rejected:* keeping SF Pro and only retuning tracking (the density was the actual complaint, not the
face); Geist for sans with SF Mono retained (splits the family for no gain); a 12px floor and 16px
body, matching Vercel's own marketing site (that is a page you read, not chrome you work inside — the
sidebar would hold a third fewer rows).

## Weight is an axis, not seven names

The reason the fonts ship as variable TTFs: **working.html leans on 450, 550 and 570**, and
SwiftUI's `Font.Weight` cannot name them. `.medium` is 500 and `.semibold` is 600, so every one of
those had been rounding to the wrong side since the app was written — the notification title read
600 where the design says 570, the ambient one 500 where it says 550. A 20-unit distinction had
become a 100-unit one; settings rows, dialog buttons and the ⌘K label were all a step light.

Call sites now pass the CSS number verbatim — `.sans(13, 550)` *is* `font-size: 13px; font-weight:
550` — and `Typography.swift` instances the `wght` axis through CoreText. Verified against the built
`.app`: 450/500/550/570/600 resolve to five distinct widths, the odd ones as genuinely interpolated
instances (`Geist-Regular_wght2260000`), not snapped to the nearest cut.

`Typography.swift` is also where a trap got closed. **Geist's default figures are proportional**, and
by a wide margin — `'111'` sets barely half the width of `'000'`. Seven sites relied on
`.monospacedDigit()`, which knows how to ask the *system* face for tabular figures and is not
guaranteed on a custom family. `Font.sans(_:_:tabular:)` applies the `tnum` feature explicitly,
standing in for the design's `font-variant-numeric: tabular-nums`. Session counts, timestamps and
zoom readouts would otherwise have jittered as they ticked.

## What the audit found on the way

Porting the scale meant reading all 139 font call sites against the CSS, which turned up three
defects that had nothing to do with the typeface:

- **The device status bar keyed size and weight off different conditions.** working.html says 15/600,
  dropping to 13/500 on Android (`.devui__status` / `.dev--android .devui__status`) — one condition,
  both axes. The app hung the *size* off `isTablet` and only the weight off Android, so an iPad's
  bar was sized like Android's and an Android phone's like iOS's.
- **The scratch-terminal confirm buttons had no font at all.** They carried `.dialog__btn`'s padding
  and fill but inherited the system face — the one thing in that sheet still not Geist.
- **The pane header title was a step behind everything else**, because the rescale pass matched bare
  literals and its size was a ternary (`tightTitle ? 12.5 : 13`). The six-step scale collapses that
  pair into one size, so `tightTitle` now drives spacing only.

Two SwiftUI-specific gaps, both invisible in the CSS: `.kerning()` and `.lineSpacing()` are absolute
points, so neither follows a size change on its own — every value had to be recomputed as `em × size`
and `size × (ratio − 1.3)`. And SwiftUI gives a custom font its *natural* line box, so the design's
`line-height` does not arrive for free; only 7 sites in the app actually wrap, because sessions are
`TerminalHost` and the chat view in the design is a mock of what the TUI draws inside a terminal.

The simulated phone (`.devui__*` / `DeviceChrome.swift`) is deliberately untouched by all of this. It
renders a device's own iOS or Android chrome, not Synth's, and rescaling it would make the mock wrong.

Both design files (subset invariant held) and the native app. Verified by a programmatic overflow
sweep across the base view, settings at four scroll positions, ⌘K, chat and dark theme: zero clipped
elements. It caught one clip a visual pass would have missed — `.set-code--flags` had a hard
`height: 40px` and needed 47.

## Stem darkening off — the designs were never asking for heavier text

`html, body { -webkit-font-smoothing: antialiased }` had been in the design files all along, and it
turns out to have been doing more than naming an antialiasing mode. Both sides were already
grayscale-antialiasing the same way — subpixel left macOS in Mojave, so there was never an
LCD-fringing difference to reconcile. What that declaration *also* switches off is **stem darkening**,
the dilation CoreGraphics applies on top of antialiasing. The app overrode nothing anywhere (no code,
no `Info.plist` key, no `AppleFontSmoothing` default), so it got the OS default: darkening on.

Measured on the real AppKit drawing path — an `NSHostingView` in a window, captured through its own
`cacheDisplay`, so whatever decision CoreAnimation makes is what the number reflects — darkening is
worth **11–15% more ink** at our sizes (14.9% at weight 400, ~12% at 550). Mean ink for "Session
template" at Geist 12/550 came back at 5.6683, an exact match to the darkening-on reference against
4.9886 off. So identical typeface and identical nominal weights were rendering ~12% heavier in the app
than in the design, which is precisely the "chunkier, less delicate" read that survived the tracking,
leading and pane-title fixes.

`Typography.matchDesignFontSmoothing()` sets `AppleFontSmoothing` to 0, called from `SynthMain` ahead
of `SynthApp.main()` — before the first glyph, and so before AppKit caches the value. It has to be the
persistent domain rather than `register(defaults:)`: CoreGraphics reads the key through CFPreferences,
which never consults NSUserDefaults' volatile registration domain. Verified by re-running the same
measurement with the call in place: 4.9886, exactly the off reference.

Two things this deliberately does not yet do. The designs run **two** smoothing tiers, not one — chrome
thin, and `auto` restored on exactly three surfaces (`.term`, `.set-code`, `.scr__body`) where heavier
is wanted. Of those, `.term` and `.scr__body` are Ghostty in the app and render on the GPU regardless,
but `.set-code` is a native `TextEditor` that belongs to the heavy tier and currently shares the thin
one. And thinning is not free at the bottom of the scale: the pullback put micro-labels at 10px, where
12% less ink is a legibility cost rather than a refinement. Both are open, and both want eyes on the
running app rather than another measurement.

## The design files stop depending on the network

Geist arrived via a Google Fonts `<link>`, which made the two design files quietly conditional on
connectivity: offline, `@font-face` never resolves, the stack falls through to SF Pro, and the file
still renders — just not as the design. A design file you can review and be wrong about is worse than
one that fails loudly. Both now carry an inline `@font-face` pair pointing at `fonts/` beside them
(the variable woff2s, ~70KB each, OFL alongside), with `font-display: block` rather than `swap`: for a
file whose whole purpose is to be looked at, a flash of the wrong typeface is the failure mode, not
the mitigation. Verified with zero requests to `fonts.googleapis.com` / `fonts.gstatic.com` and the
`wght` axis still interpolating — six distinct widths across 400/450/500/550/570/600.

## Two dialog surfaces that had never matched

Both flagged during the type audit and left for a decision, now taken:

- **`.field label`** was sentence-case 11/500, where the design says **10/600 uppercase on 0.05em**.
  It had been reading as a smaller copy of the row label rather than the tracked micro-label every
  other section header in the app wears.
- **The dialog action buttons** carried no font, so they sat in the system face. They now take
  `.dialog__btn`'s 13/550 — set on the actions row rather than by restyling the buttons. The design
  draws a flat pill, but these are a sheet's default and cancel actions, and on macOS the native
  styles carry the accent fill and focus ring that say so. Matching the type without discarding that
  is the closer reading of the design's intent.

*Deliberately not done:* giving `.set-code` its own smoothing tier. The designs restore `auto` on
three surfaces and the app can only run one, but per-view stem darkening has no clean SwiftUI seam —
`AppleFontSmoothing` is process-wide, read by CoreGraphics — and the payoff is unverified. It stays
recorded rather than worked around. The scale's 10px floor also stays: thinner ink there was the one
change this session that could plausibly have cost legibility, and it survived review.
## A project is a git repository, or it isn't a project

Reported as a dead end: add a folder that isn't a git repo, it lands in the sidebar looking fine,
then "New branch" fails on `fatal: not a git repository` — and there is nothing you can do about it
from inside Synth. The refusal was written into the code on purpose ("a non-repo folder yields a
branchless workspace"), which made the folder picker's own message, "Choose a repository folder", a
description of what to look for rather than a requirement.

A panel of five (developer-tool design, error and recovery design, scope discipline, macOS platform
conventions, first-run journey) was asked the open question — including whether plain folders should
be supported and whether to offer `git init`. It was unanimous on the first thing and nearly
unanimous on the second, and it moved the diagnosis twice.

**Every branch is a git worktree, so a folder that can't host a branch can't be a project.** A
branchless project can hold no branch, therefore no session: it is a row that occupies space and
does nothing. Supporting plain folders as a second kind of project would mean a tier the sidebar
skips, sessions hanging off a project directly, and a not-applicable path in every branch-shaped
feature — PR badges, the archive sweeper, `defaultBase`, ⌘K's "New branch off main", the synth-app
`worktree_create` verb — forever. A tool built on worktrees requiring a repo is a statement, not a
limitation.

**The check is "does this folder have a branch", not "is this a git repo".** Four different folders
produced the same branchless project, and the likeliest of them is a repo: `git init` with no commit
yet. `refs/heads` is empty, `defaultBase` falls through to `"HEAD"`, and `git worktree add -b x
<path> HEAD` dies on `invalid reference: HEAD` — so the folder is a dead end even though every
"is this a repo" test passes. A bare repo and a project whose branches were all archived read empty
too. Gating on the branch list covers all four; gating on repo-ness would have shipped the bug again
under a new error message.

**A subdirectory of a repo was accepted, and that was worse than the dead end.** `--is-inside-work-tree`
is true for any descendant, so picking `repo/app/Sources` gave a project named "Sources" whose branch
row pointed at the repo root while `worktreeRoot` hashed the subpath — one repo, two projects, two
unrelated worktree roots, and a later `worktree add` for a branch the other already has dies on
"already checked out". Silently half-working beats loudly broken, badly. The pick is resolved with
`--show-toplevel` now, which also collapses the symlink, `/tmp`-vs-`/private/tmp` and case-only
spellings that hashed apart for one repo — so re-adding a project you already have reveals the one
you have instead of making a second.

**The refusal happens in the picker, while it is still open.** `NSOpenPanelDelegate.panel(_:validate:)`
runs once on Add, throws, and leaves the panel on the folder you were looking at — so the correction,
walk up a level and take the repo, is one click away with your attention still on the choice.
`shouldEnable` was the obvious alternative and is wrong twice: every ancestor of a repo is itself a
non-repo, so `~` and `~/code` would grey out on the way to the thing you came for, and it re-probes
every listed folder on every scroll. It is a filesystem probe, not a git call — `validate:` runs on
the main thread under a modal panel, where one spawn against a stale network mount would beachball
the app — and it tests for `.git` *existing*, not being a directory, because `.git` is a file inside
a linked worktree. Behind it, the same decision is made again where the project is actually created,
so the invariant holds for callers that never touch a panel.

***Rejected:* offering `git init`.** The panel split 4–1 against, and the argument that settles it is
that the person who lands here has usually picked the *wrong folder* — the parent of their repo,
Downloads, `~/code` — so a one-click Initialize makes a slip permanent and leaves a stray `.git` in
their home directory they won't find for a year. It also wouldn't work: `init` alone leaves
`refs/heads` empty, so to honour the offer Synth would have to author the first commit too, deciding
what goes in it, in a folder that may hold `node_modules` and no `.gitignore`. Never-leave-the-app
earns its keep for the loop you are in ten times an hour, not for a once-per-project setup step a
developer with a terminal open does faster than they can decide whether to trust the button. VS Code
and Zed do accept-then-offer-init, and it works there because a repo-less folder is still fully
usable as an editor; here it can host nothing.

**A Retry button is a claim that identical input could produce a different output.** The failure card
offered one on a create that could never succeed, so pressing it failed identically, forever — while
`materialize`'s own comment said an offer that can't be honoured is worse than none. Repeatability is
a property of the call site; transience is a property of the failure, and the code only asked the
first. Rather than classify git's whole vocabulary, the second identical failure — same project,
branch and reason — now answers it and the card stops inviting the click; a different reason is asked
afresh, and a branch that materialises earns its offer back. That covers the causes nobody has
enumerated yet, which is the point.

Two smaller things fall out. "No worktrees yet" is now **"No branches yet"** — it was the one word in
the flow naming an implementation detail, sitting under a row whose action is "New branch", and it
was also the line that told you a dead project was normal. And the unfocused Notification Center post
carried the whole git dump, which Notification Center truncates and won't let you copy; it carries the
same one line the card shows, with the full text still in the log.

Gate: `t23_projectgate` (19 checks, including the picker's four misclicks and the retry cap).

## Synth 0.23.0 shipped (build 478)

A minor, and the headline is one people will see before they read anything: Synth is set in **Geist**
now, on a scale of six sizes instead of twelve, with the designs' own tracking, leading and weights
rather than a calibration for the system face — including stem darkening off, which is where the
last ~12% of extra ink went. The other four user-facing changes are all the same kind of thing,
a promise the app was making and not keeping. Closing a session hands you its neighbour **in the
same branch** rather than popping to whatever you last looked at, which could be another repo
entirely. An archived branch always has a way back, on all three routes that previously dead-ended.
A project has to be a git repository with a branch, refused at the picker instead of landing fine
and failing later, and a subdirectory now resolves to the repository root. And a notification's ×
closes it wherever you click the ×, not only on the crescent where it lapped the card's corner
radius.

Two invisible fixes ride along and are in the changelog anyway, because both are things a user
noticed the *absence* of: a session now reaps the processes that escaped its process group (an
agent's detached dev server had been outliving the session, the app and reboots — 3.6 GB across 34
processes, measured), and `PRService` no longer sets `Process.currentDirectoryURL` to a path that
does not exist, which threw an uncatchable `NSException` and so crashed Synth on launch for anyone
whose project folder had been moved or unmounted.

Left out of the changelog on purpose: the variable-weight axis plumbing, the three type-audit
defects, the vendored design fonts, and the two dialog surfaces that had never matched the design —
they are all how the typeface change was made correct, not separate things to read about.

Notarized and stapled in both shapes, verified the way an outsider gets them: downloaded
credential-less from the public bucket, quarantine set as a browser would, `spctl` accepts the dmg
and the zip's app as *Notarized Developer ID*, and the app **inside** the mounted image staples on
its own (`stapler validate` on both). Bundle reads 0.23.0 / 478, and the bundled `CHANGELOG.json`
leads with 0.23.0 and its seven entries, so Synth → Changelog shows this release.

The appcast's newest item is `sparkle:version` 478 / `0.23.0`, all 18 enclosures across its three
items EdDSA-signed, five deltas against builds 458/433/425/418/413 — **1.1M** from the previous
build against a 131M full download.

`generate_appcast` repeated the benign `old_updates/` collision warnings from the last two releases
(superseded `Synth272-*`/`Synth293-*` deltas whose names already exist there). It is housekeeping on
files no published item references; nothing in the feed depends on it.

The landing page was untouched since v0.22.0 and its Download button points at the stable
`Synth.dmg` alias this release republished, so no site repo push was needed.

## …and stem darkening back on: the menu bar is not ours to restyle

Reverses the decision two sections up, same day. `AppleFontSmoothing` is read by CoreGraphics
**per process**, so switching it off did not thin "the app's chrome" — it thinned everything Synth
draws, and that includes its own menu bar. A menu that renders ~12% lighter than every other
application's is not a closer match to the design; it is Synth failing to look like a Mac app in the
one place the OS sets the vocabulary. `working.html` does not model the menu bar and never had an
opinion about it: `-webkit-font-smoothing: antialiased` was a statement about Synth's own surfaces,
and reading it as a statement about the process was the error.

There is no seam to scope it with — the same wall that stopped `.set-code` getting its own tier. The
override is gone rather than narrowed, and the ~12% ink gap between app chrome and the design files is
back and now documented as a known, accepted divergence rather than a bug to chase. It is the cost of
the app's text being drawn by AppKit instead of WebKit, and the menu bar is worth more than closing it.

Two things this cost extra, both worth remembering. The preference **persists** — deleting the code
leaves the key in `~/Library/Preferences`, so the app keeps rendering thin until the key is deleted
too; code removal alone is not a revert for anything written through `UserDefaults`. And the domain is
**shared across worktrees**: every dev build carries `CFBundleName` "Synth Dev", so an instance from
another checkout that still has the override rewrites the key for all of them. That is what made this
look unfixable for a few minutes — the binary was clean and the key kept coming back.

## The simulator is a session, and its screen comes from the device's framebuffer

CONTEXT.md has called the simulator a session type since the vocabulary was written, and the designs
have carried an iPhone row with a drawn device frame since before 0.18.0. Neither was backed by a line
of Swift. Now a simulator session boots a device from the installed fleet, streams its screen live into
a pane, lets you tap and type into it, and lets Claude act on that same screen through a
`synth-simulator` MCP server.

The architecture and its rationale are ADR-0015. The short version: the pixels come from the device's
own `IOSurface`, read in-process off `SimDevice.io`'s display port and handed to an
`AVSampleBufferDisplayLayer`. **Simulator.app is never launched.** Mirroring its window with
ScreenCaptureKit — the obvious-looking route — was rejected: it dies when that window is minimised or
on another Space, it needs a Screen Recording grant, and input would have to go back through
`CGEventPostToPid`, which delivers clicks and keys to a background app but silently **drops mouse-move
and scroll**, so hover and panning would only work by stealing focus. Xcode 27 also replaces
Simulator.app with Device Hub, which is exactly the shift that killed RocketSim's window-anchored
design. Reading the framebuffer is untouched by all of it.

This is private API, knowingly. Every shipping implementation of this uses the same route — Meta's idb,
Anthropic's own simulator pane in Claude Code Desktop, NativeScript's SimDeck, the Software Mansion
binary behind Radon IDE and Maestro Viewer — because Apple has shipped no alternative: no public frame
callback, no touch-injection verb in `simctl` at any version, no streaming or embedding API. Xcode 27
gave *agents* simulator control through Apple's own MCP server, but only with Xcode.app running and the
project open, and still no way to put a live device inside another app's window. Distribution was tested
rather than assumed: a Developer ID-signed, hardened-runtime binary with **zero entitlements** loads both
frameworks and drives a device, because Library Validation admits them as Apple-signed, and notarization
does not inspect for private API. The cost is that Synth can never go to the Mac App Store, where App
Review does scan for it. Everything private is resolved by name at runtime and never linked, so a moved
framework or renamed selector degrades instead of failing to launch.

**v1 attaches and drives; it does not build your app.** The terminal already running `npm run ios` or
`xcodebuild` is not something Synth needs to own to be useful. Owning the build loop — scheme detection,
error surfacing, the long tail of RN/Expo/Tuist/SPM shapes — is a project in its own right and is
deferred, not rejected. Synth owns the surface, not the content, which is the line the browser already
draws.

**A session claims a device from the fleet and boots it; the last session to let go shuts it down.**
Devices are machine-global state, so two branches picking the same model share one device and its app
state. Cloning per branch is the more principled answer and is deliberately not v1: it costs a full
device directory per clone and would need its own sweeper, the way `ArchiveSweeper` tends worktrees. The
persisted field is the UDID, so nothing blocks it later. Simulator sessions get **no** `ownerSessionID`
— unlike browsers, because ownership encodes exclusive lifecycle control and a device is shared state the
user also drives. An agent tidying up after itself must not shut down a device you are looking at, so
release is by reference count.

The live screen sits inside the hardware frame 0.18.0 introduced — body, per-edge bezel, radii, side
buttons, shadow — with the device resolved from the booted device's real model identifier rather than
parsed out of the session's name, and the screen size taken from what the device reports so a 402×874
framebuffer is never stretched into a 393×852 frame. **Our drawn status bar comes out**: iOS renders its
own status bar, island treatment and home indicator into the framebuffer, so drawing ours would double
them. `DeviceFrame` became generic over its screen content to make room for this, which also moved the
browser's software chrome into a `BrowserDeviceScreen` — the mock has had exactly this factoring
(`deviceHTML(d, land, screenHTML)`) all along.

Claude drives it through a second Node stdio MCP server beside `synth-browser`, with 13 tools. **Every
verb goes over the control socket** — there is no CDP-equivalent second channel, because the app holds
the warm HID session and the framebuffer, and routing through it keeps the invariant that a tool call
runs the same function the UI runs. The tool vocabulary follows the convention that converged across idb,
mobile-mcp, AXe, Argent and Maestro rather than inventing one: **observe structurally, act by
coordinate**, all coordinates normalised 0..1 from the top-left. `simulator_describe` — the accessibility
tree, which needs no test runner — is shaped for but not in this slice.

### Measured, because the numbers were the whole question

At 1179×2556 against a page repainting every frame: **50.9 fps mean, gap p50 16.96 ms** (a clean 60Hz
modal cadence), **our own cost 22 µs per frame** — 0.13% of a 16.7 ms budget. A static screen produces
one frame in five seconds, because frames are pushed on the device's damage callback rather than a timer.
Tap-to-visible-change is **59–70 ms**. We are not the bottleneck, so the pane can feel native.

### What only showed up by running it

- A booted device exposes **two** ports with `portIdentifier == "com.apple.framebuffer.display"`, same
  proxy class and same proxy UUID — and the first is inert, 0×0 with a nil surface. Selecting the first
  descriptor that conforms to the display protocols, which is the obvious implementation, binds to a
  display that never delivers a frame.
- Selectors are case-sensitive and CoreSimulator does not spell things the way Swift would: `SimDevice`'s
  identifier selector is **`UDID`**. Letting Swift synthesise `udid` made `respondsToSelector:` false for
  every device, so lookup failed with "no device with that UDID" while naming a booted device sitting
  right there.
- **Claiming a device boots it, and a boot takes ~20 s, so the pane's first attach races it.** An
  unbooted device publishes no display, which read as "the live path is unavailable" and degraded a
  session permanently that would have worked a moment later. "Booted" is also a device state, not a
  promise the display is publishing — the framebuffer arrives after it. So boot state decides what the
  user is *told*, never whether to stop trying.
- A restored session holds a UDID but no claim, so **opening the pane is what puts a session back on a
  device**. Nothing else was going to boot it.
- The first `CVPixelBufferCreateWithIOSurface` costs 11–28 ms against 22 µs steady state, so it is primed
  off the first frame or opening a pane hitches. Damage callbacks burst — two inside the same nanosecond
  — so work is coalesced to a frame interval rather than done per callback.
- **A frame is a live view of the device's surface, not a snapshot.** Two frames captured seconds apart
  share one buffer and compare byte-identical, so anything needing a still — the screenshot verb above
  all — copies at capture time. Diffing two retained frames to detect change always answers "no".
- `teardownSession` released the device but never terminated the manager, leaking a framebuffer
  registration and an Indigo session onto a device being shut down under it.

## The simulator's screen can be read as text, not just seen

`simulator_describe` reads the frontmost app's accessibility tree off a booted device — roles, labels,
accessibility identifiers, values and enabled/focused state, one element per line, each with its frame's
centre in the same normalised 0..1 coordinates `simulator_tap` takes. Discovery through `describe`, action
through `tap` at an element's centre. This completes the observe rung the previous entry shaped for and
deferred; the tool vocabulary is unchanged, so nothing about the MCP surface moved except one addition.

**Why it matters is cost.** Settings' root screen is a 1069-byte tree against a 219 KB PNG — 205× on the
wire, and roughly 300 tokens against ~1,500 for the image once it is downscaled. The tree also carries what
a screenshot cannot: `#com.apple.settings.general` next to the row labelled "General", so a tap is aimed
rather than guessed. An agent that screenshots to find out what is on screen is paying five times over for
a worse answer.

**No XCTest runner and no injected bundle**, for the reason Indigo HID has neither: the device is read from
outside, so it works on any app including ones we did not build. `-[SimDevice
sendAccessibilityRequestAsync:completionQueue:completionHandler:]` is the XPC channel to the guest's
accessibility server, and `AXPTranslator` (AccessibilityPlatformTranslation.framework, which SimulatorKit
already links) turns its opaque responses into an element tree answering the ordinary NSAccessibility
selectors. Out of Simulator.app the translator has no idea which device a request belongs to, so we install
our own `bridgeTokenDelegate`.

There are two request kinds and both are needed. The **frontmost-application** walk is the whole screen.
The **point hit test** (`objectAtPoint:displayId:bridgeDelegateToken:`) reaches what the walk cannot:
SwiftUI tab bars, nav bars and toolbars routinely enumerate as childless containers (idb#767), and
SpringBoard's status bar is not in the app's tree at all — hit-testing the status bar returns
`Mobile Service / No signal` where the walk returns nothing.

### What only showed up by running it

- **`AXPTranslator` has a single `bridgeTokenDelegate` slot per process**, so there is exactly one
  dispatcher and requests are told apart by a per-call token. Two panes on two devices would otherwise
  answer for each other. The slot is also re-asserted per call, because nothing stops another framework in
  the process from taking it.
- **The translator re-reads `bridgeDelegateToken` off every translation object it touches.** A child that
  was not stamped makes its own sub-request, which routes nowhere and reads back as empty — so the subtree
  is stamped in a pass of its own before anything is read. This is the failure that looks like a working
  implementation returning a screen with three things on it.
- **`mainScreenScale` is not a `double`, despite reading like one.** Messaging it as one returns whatever
  was in the floating-point register — a NaN that propagated into every coordinate and finally trapped in
  `Int(_:)`. Both screen-geometry properties are read by key instead, because KVC boxes by the method's
  real type encoding, which is the only way to be right about a property whose type is not ours to know.
- **`AXPMacPlatformElement` inherits most accessibility properties from AppKit's `NSObject
  (NSAccessibility)` category, but not all of them.** `accessibilityEnabled`, `accessibilityHidden` and
  `accessibilityTraits` have no selector here, and `valueForKey:` on an absent key raises an ObjC exception
  a Swift caller cannot catch. Every read is guarded by `respondsToSelector:` first.
- **The framework binary lives only in the dyld shared cache**, so the path never exists on disk and a
  `fileExists` precondition rejects a framework that loads perfectly. dlopen is the only test there is.
- `simctl launch` on an app that is already running foregrounds it without resetting it, so the
  self-check's "deterministic start state" was whatever the previous run had navigated to.

**A degraded session has no accessibility at all, and says so.** `simctl` has no verb that reads a tree at
any version, so unlike the screen there is nothing to fall back to — the verb refuses and carries the
reason. Answering with an empty tree would read as "the screen has nothing on it", which is the one wrong
answer available.

**Forward compatibility, written but not testable here:** iOS 26.5 and later cache the guest's
accessibility preferences at boot, so `IgnoreAXServerEntitlements`, `AutomationEnabled`,
`AccessibilityEnabled` and `ApplicationAccessibilityEnabled` have to be in the device's
`com.apple.Accessibility.plist` *before* `simctl boot` — a post-boot write is read by nobody. It is written
on the boot path, gated on runtime version, and merged into the existing file rather than over it. Verified
on iOS 18.4, which needs none of it.

## The simulator session is finished: input you can actually use, a fallback that has been run, and a type that stops lying

The two entries above built the surface and made it readable. This is what was still missing to call it done.

**Typing had no delete, escape or arrows.** `type(text:)` mapped letters, digits, punctuation, return, tab
and space, and threw on everything else — so backspace in the pane silently did nothing, which is most of
what typing on a device actually involves. AppKit hands those keys over in `NSEvent.characters` exactly like
letters, so the pane forwarding characters verbatim was right; the mapping table was short. This fixes
`simulator_type` for agents at the same time.

**There was no scrolling at all.** Trackpad and wheel scrolling now become a touch drag rather than a
synthesised scroll event, because the guest interprets a drag as a swipe natively and a trackpad's
began/changed/ended phases map onto touch down/move/up exactly. Deltas accumulate into a running finger
position, so a long scroll is one continuous touch instead of a burst of taps. A legacy wheel, which
reports no phase, flicks as a short discrete drag.

**The pane has chrome.** Device name, runtime, and Home and Lock buttons — neither reachable any other way,
because the side buttons on the drawn frame are hardware, not controls.

**`simulator_terminate` completes the lifecycle set.** Launching an app that is already running foregrounds
it without resetting it, so an agent had no way to reach a known starting state; it would describe whatever
the last run had navigated to. Kept as its own verb rather than a `relaunch` flag, because "stop this app"
is independently useful and terminate/launch is the pairing the converged vocabulary already uses. Fifteen
tools now.

**The degraded path has been run, not just written.** `SYNTH_SIM_FORCE_DEGRADED` disables the framebuffer,
Indigo HID and accessibility together — deliberately all three, because the failure the fallback exists for
is an Xcode release moving the private frameworks, which takes every one out at once. A seam that only
disabled the screen would rehearse a scenario that does not happen. The self-check inverts its expectations
under it: the source must degrade, name what it lost and what it fell back to, keep showing the screen via
`simctl` polling, and refuse the capabilities that have no fallback out loud. Running it immediately found
that input was *not* being declared degraded — because opening the Indigo session is asynchronous, so
`degradation` read straight after `start()` is a half-built answer. The pane already coped by watching
`onDegradationChange`; a synchronous reader has to wait.

**`BrowserDevice` is now `HardwareDevice`.** It models drawn hardware for two surfaces — the browser's
device mode, whose viewport it emulates over CDP, and the simulator pane, which wraps a real device's
framebuffer in it — so the browser-specific name had stopped being true. The browser's own software chrome
stays `BrowserDeviceScreen`, which a simulator never uses.

**The self-check also guards persistence now**, including the line that would fail silently:
`SessionKind.init?(rawValue:)` maps anything unrecognised to an agent id, so a missing case decodes every
persisted simulator as a bogus agent on the next launch rather than erroring. Plus the UDID surviving a
snapshot round-trip, and a pre-simulator snapshot still decoding, since the field is additive and
`schemaVersion` stays 1.

### Verified end to end

The real ⌘K route creates a session and boots its device; the pane draws the live screen inside the
hardware frame; and the agent path — spawned the way Claude Code spawns it, stdio JSON-RPC from the
worktree's own `.mcp.json` — runs terminate → launch → describe → tap at the centre `describe` reported →
describe again, and lands on the screen it aimed at. Same `sessionId` throughout, which is the point: the
agent is acting on the screen the user is looking at, not a private copy of it.

The self-check passes in both modes on iPhone 16 and iPhone 16 Pro: live (60Hz cadence, 18 µs per frame,
59–78 ms tap-to-visible-change, accessibility tree round-tripping through a tap) and forced-degraded.

## What an unbiased reviewer found, and what it changed

The feature was handed to a reviewer with no stake in it, told to assume every user turns the
Experimental toggle on, and deliberately not told what its author thought was wrong. It built
instrumented copies of the package to force failures and returned **do not ship**, with five findings
marked as the gate. All five are now closed. Two things are worth recording.

**The private-API layer was the part that held up.** Patching a scratch copy so `SimulatorKit` resolved
to a moved path — the Xcode 27 relocation, simulated — left screen and accessibility *live*, with only
input degrading and naming the exact path it tried. Renaming the display selectors dropped it to `simctl`
polling and it still delivered frames, taps and trees. No crash either time. That was the residual risk
nobody could discharge from one machine, and it is now evidenced rather than argued.

**Everything serious was in the app integration around it**, and the worst was measured, not inferred:
the attach path called the device catalog — three `simctl` spawns plus a plist read per installed device,
~350 ms — from `init`, `start()`, `attach()` and `isBooted`, on the main actor, on a one-second retry tick
for the whole boot. **76% of the main thread blocked** for the length of a cold boot, in an app whose first
stated principle is that chained shortcuts feel instant. The fleet now caches device geometry and serves
single-device lookups; no pane path shells out on the main actor.

The other four: input verbs answered `ok` for taps that never left the process (they all throw now, and
the pane shows the refusal); a shut-down device kept serving its last frame as a fresh screenshot, because
the IOSurface stays mapped after the device dies (liveness is asked of CoreSimulator before a frame is
handed out); devices Synth booted were never released; and three threads shared one strong reference to the
HID client, which is a double-release in an app hosting the user's terminals.

### Three bugs the fixes themselves introduced, and how they surfaced

Worth writing down because each was caught by a test rather than by review.

**Scrolling was inverted.** The scroll-to-touch translation subtracted the y delta where it should have
added: AppKit reports `scrollingDeltaY > 0` when content should move down, which on a touchscreen is a
finger moving down. Invisible reading the code, immediately wrong in the hand. It was caught by a
self-check assertion that synthesises the events AppKit would deliver and asserts a known row actually
moved up the screen — which also caught two mistakes in the test itself first: `setIntegerValueField` on
`fixedPtDeltaAxis1` writes raw 16.16 fixed-point bits, so −60 asked for −0.0009 of a pixel; and
`CGEvent.location` is top-left origin while `NSEvent` flips it, so the synthetic finger landed in the
navigation bar where a drag correctly scrolls nothing.

**Releasing devices on quit does not work, because quit is not guaranteed to happen.** A `willTerminate`
handler was written, wired, and then demonstrated not to run: the signal source that routes SIGTERM
through `NSApp.terminate` is installed by the CEF supervisor, so a bare signal with no browser session
ever having initialised CEF kills the process with no handler at all. SIGKILL and crashes are worse.
Claims are therefore *recorded* when made and reconciled on the next launch — the way the browser already
sweeps profile directories orphaned by a dead instance. Verified the only way that means anything: claim a
device, `kill -9` the app, relaunch, device shut down. Only devices this app claimed are ever touched.

**A cached read is fine for what you tell the user and not for what you do.** Gating the claim on a cached
`isBooted` meant a cache briefly stale in the "booted" direction skipped the claim entirely — so nothing
booted the device, the pane retried for ninety seconds, and then reported a device that had never been
asked to start. The claim is idempotent, so it is now unconditional.

### Where it stands

`--simulator-check` passes in both modes — **29 assertions live, zero failures**, and forced-degradation
green — on iPhone 16 and iPhone 16 Pro. Memory flat at 175–176 MB across six minutes of continuous 60Hz
streaming. Two concurrent sessions on two devices each describe their own geometry and take their own taps.
The agent path runs terminate → launch → describe → tap at the reported centre → describe on the same
session the user is looking at. The feature ships behind an Experimental toggle, off by default, with its
MCP server registered only when the toggle is on and a full Xcode is present — both directions verified.

## Rotation, and a comment mode that is written but withheld

**The device rotates, not just the drawn frame.** `simctl` has no orientation verb at any version and
`devicectl`'s exists only on Xcode 27, so this is the private path or nothing: a raw `mach_msg` to the
device's `PurpleWorkspacePort`, with the wire format read out of Simulator.app's own
`gsEventsSendOrientation:` rather than guessed. Shake goes via `postDarwinNotification`, proved end to end
by watching `notifyutil` inside the guest. There is a Rotate control in the pane, a `simulator_rotate`
tool taking an enum of the four orientations (never a number — an unbounded numeric argument reaching Swift
has already been a crash vector here once), and `simulator_shake`.

Three things that turned out not to be true, each of which would have produced a plausible-looking wrong
implementation:

- **The framebuffer does not resize when the device rotates.** It stays 1179×2556 in every orientation; iOS
  draws its rotated interface sideways into the same surface, and Simulator.app rotates its own view to
  match. So the pane rotates its layer and un-rotates every pointer coordinate, and the check asserts on
  accessibility geometry rather than on a size that never swaps.
- **There is no read-back.** `SimScreenProperties.uiOrientation` exists and answers 0 in every orientation,
  so orientation is write-only: `source.orientation` is what Synth last set. A device another branch
  rotated reads as portrait here — wrong drawn chrome, never a wrong device — and attach deliberately does
  not force portrait, because that would rotate a device someone else is looking at.
- **Settings is portrait-only on iPhone** and ignores the event. Verifying rotation against it would have
  "proved" a working mechanism broken; Safari rotates instantly. An app refusing to rotate is also the one
  failure this verb cannot report, and both the control reply and the tool description say so.

Rotation exposed a real bug one layer up: **the accessibility tree was not orientation-aware.** AXP reports
frames in the *interface's* space, so while landscape a tree still normalising against the portrait profile
divided by the wrong axis — an element 778pt across a screen the profile calls 402pt wide, i.e. a centre of
1.93, which `tap` then refuses for being outside 0..1. Loud rather than 90° wrong, but wrong. The reader now
transposes with the orientation, and the check asserts both halves of the contract: the point size
transposes, *and* every element falls inside it, so describe→tap round-trips in landscape. The assertion
that shipped with rotation had encoded the bug as expected behaviour — it asserted an element centre lands
*outside* the screen — which is a good reminder that a passing test can be pinning the wrong thing.

**Comment mode is implemented and deliberately not offered.** Clicking something on the device and sending
it to the owning agent works as far as it goes: the mode toggles, the click resolves the accessibility
element under it (`General (com.apple.settings.general)` — label plus the identifier that is greppable in
the app's own source), evidence is captured at click time rather than at send time because the frame is a
live view of the surface, and delivery reaches the right rung and adopts the row. The delivery ladder was
extracted into `CommentDelivery` and is now shared with the browser rather than copied, because it is a
security boundary — subject-controlled text is pasted into a TUI, so it may only ever reach a
supervisor-confirmed live agent — and the browser's own comment mode was re-driven afterwards to prove the
extraction changed nothing.

But **delivering a comment from an unowned simulator reproducibly exits the whole app** about five seconds
later, with `exit(1)`, no crash report and nothing in the log. Localised and still not root-caused: it is
not the agent spawn on its own, not the ownership cascade (the row is still present), not the pane-swap
timing, and not the same spawn-and-return dance when the pane returned to is a terminal. So the toggle is
withheld. The controller, the shared ladder and an `automation.simulatorComment` verb that drives the whole
flow all stay, because the reproduction is the valuable part. An app that dies is worse than a feature that
is missing, and this is the app hosting the user's terminals.

Ownership was generalised on the way: `adopt` takes simulator rows, `ownedBrowsers` became `ownedSessions`
since it already returned them regardless of kind, and the close confirm names what it will actually close
rather than saying "browser" in front of a simulator.
