# 2026-08-03

## An archived branch always has a way back

Archive was sold as reversible: put a worktree away, and pull it back from ⌘K → Archived when you
want it. Three separate gaps meant a branch could go in and never come out — reported from the real
thing, on `hol-519-…` in the holibob repo, as "I can't add it back, it doesn't show up".

An archived row does not leave `Workspace.branches`. It stays, with `archivedAt` set, so the Archived
list can reach it while `visibleRows` keeps it out of the tree. That one design choice — right in
itself — is what the three gaps grew out of, because every other surface kept treating the row as if
it were live.

**The picker hid it.** ⌘K → New branch filtered its offers against *every* row in the workspace, not
just the live ones. So an archived branch's name was taken: it wasn't in the sidebar, and it wasn't in
the one frame that adds a branch. The "New branch “x”" fallback didn't rescue it either — that only
appears when no git ref of that name exists, and the ref was right there. Typing the exact branch name
returned an empty frame. Now the filter reads `liveBranches`, and an archived match is offered wearing
the archive glyph and its "archived 3d ago" age, so picking it reads as putting the row back rather
than making a second one.

**Restore gave up when the folder was gone.** The sweeper holds a reclaimable folder aside as
`.archived-<name>-<epoch>` and the reaper deletes it once the hold expires. `restoreArchivedBranch`
handled the hold (a rename back) and returned `false` for the reap — and the one caller discarded the
Bool, so ⌘K closed and nothing happened. A silent no-op on the only route back. It doesn't decline
any more: **the branch is a git ref and the checkout is derived from it**, so a row whose folder is
gone gets the worktree cut again at its old path and waits pending exactly like a fresh create. The
reaper prunes as it deletes, so a plain `worktree add` is enough. No session template runs — a restore
that spawned sessions the archived row never had would be a create wearing its name.

**Restart forgot it.** `restore(from:)` drops any branch whose folder is *confirmed missing* (the
parent exists, the folder doesn't) on the reasonable theory that the user deleted the checkout outside
Synth. For an archived row the folder's absence is not evidence of anything — it is the sweeper doing
its job. So the next launch dropped the row: the Archived list forgot the branch, and a folder still
on hold was orphaned with nothing but the reaper's clock left to touch it. Archive state now survives
launch regardless of what is on disk; only live rows are reconciled against it.

What these have in common is worth keeping: the *branch* is the durable thing, the *folder* is a
cache. Every place that read the folder's absence as the branch's absence was wrong, and each one
individually stranded work. The lasting rule is that no gate on the restore path may end in "can't" —
at worst it costs a checkout.

Gate: `t9_archive` grew nine checks — the picker offers an archived branch (once, as a restore, no
create fallback) and picking it puts the row back; and after the reaper has taken a folder, the row is
still archived across a relaunch, restore returns it to the tree, and the re-cut worktree is a real
registered checkout of the branch.

*Rejected:* a "this branch is archived, unarchive it?" confirm in the picker (the pick already says
what it does, and archive is not destructive); dropping the reaped row from the store so the name
frees up in the picker (it loses the row's age and its remembered layout for no gain, and the ledger
of what you archived is the feature); an error toast on a failed restore (the failure was avoidable —
fixing it beats reporting it).
