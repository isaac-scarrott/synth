# 2026-08-12

## synth-md — markdown is a session

Agents write markdown constantly — plans, TODO lists, findings, reports — and Synth had nowhere to put
it. Clicking a `.md` link left the app for whatever had claimed the extension on that Mac. Markdown is
now a first-class session kind: a rendered document you can also edit, in a pane beside the agent that
wrote it.

**A markdown session is a terminal session with a fixed launch command.** Same libghostty surface as
every other row, so PTY lifecycle, reaping, focus, theming and the child-exited signal that closes a row
all come free (ADR-0016). The pane is the bundled `synth-md` TUI, built on OpenTUI — the Zig +
TypeScript engine behind opencode.

**Viewer and editor together, modeless.** The document renders: headings, concealed emphasis markers,
task checkboxes as real glyphs, tables as tables, fenced code with tree-sitter highlighting, YAML
frontmatter as a styled key/value header. Click into a block and *that block* shows its raw markdown
with a cursor; click away and it re-renders. Typing inserts, the mouse places and drags a selection,
shift-arrows extend it, ctrl+Z/ctrl+A work, and there are no modes — Esc closes what is open and
otherwise does nothing. ⌘C/⌘X/⌘V stay ghostty's own, against the real macOS pasteboard.

Why editing was in scope for v1 rather than a viewer first: a viewer alone would have been much less
work, but the documents in question are ones you *act on* — ticking off a plan an agent wrote is the
interaction, and a read-only pane would send you to another editor for it.

**Checkbox click-to-toggle without entering the block.** Clicking `□` flips it to `■` and rewrites that
one line, leaving every sibling byte-identical, and the row never flips to raw under the click. This is
the interaction the whole thing is for.

**Smart structure editing.** Enter continues a list (carrying the checkbox, never the checked state),
an empty item outdents and then breaks out, Tab/Shift-Tab nest and un-nest, ordered lists renumber, and
typing `- ` turns a paragraph into a bullet. Structure edits rewrite the OPEN EDITOR's text rather than
the document: splicing the document mid-keystroke tears down the renderable being typed into, and the
characters after it go nowhere. Renumbering is document-scoped and so happens when the block folds back.

**Autosave, and never clobbering anyone.** Edits debounce to disk. The file is watched, because agents
edit these files underneath you: a clean buffer adopts an external change silently, a *dirty* one keeps
your keystrokes, says "changed on disk", and stops autosaving until you resolve it. A save already armed
when the conflict appears is cancelled — otherwise the debounce lands after the agent's write and
destroys it.

**Reader chrome, and nothing more.** ⌃F incremental search with a match count that wraps, ⌃O for an
outline palette that jumps to a heading. No sidebar, no toolbar.

**Links.** A relative `.md` link navigates inside the viewer with a back stack (⌃] follows, ⌃B goes
back). Everything else is handed back to the app over the control socket as a new `link.open` verb, so
loopback pages still open in the synth browser, other pages in the default browser, and files through
`openFileLink` — one copy of that routing, in `openTerminalLink`, rather than a second in TypeScript free
to drift. ⌃] rather than the ⌃Enter it wants to be: ⌃Enter needs the kitty keyboard protocol, and ⌃[ *is*
Escape at the byte level, which is also why back is ⌃B.

**Two ways in.** Cmd+clicking a `file://` link ending `.md`/`.markdown` in any terminal or agent session
opens a markdown row in that branch (re-clicking the same document focuses the existing row rather than
minting another). And `synth <file>`, installed on PATH in every Synth terminal beside the agent shims,
execs the TUI in place like typing `vim`; anything that is not markdown falls through to `open`.

**Settings → Markdown: three answers, because there are only three.** *Synth* (the default),
*your editor* — any terminal editor found on this machine, in a Synth session — or *Default app*,
which hands the file to macOS. The editor segment carries which editor rather than adding a fourth
control, so a machine with one installed has nothing extra to decide and the segment is simply
absent on a machine with none. Detection reads the login shell's PATH, which is the only thing
that actually knows: on the machine this was built on `nvim` lives in `~/.local/share/bob/nvim-bin`
(the bob version manager), a path no hint list would ever have guessed. The `synth` command bakes
in the same choice, so a click and a typed command never disagree.

**A clicked markdown link used to be able to raise the OS's "The application can't be opened."**
Root cause: markdown routinely has no registered handler at all — it has none on this machine — so
*any* path that hands a `.md` to Launch Services ends in that dialog. `openFileLink` had one, for
the case where no branch could host the row. That is now an in-app toast naming the file, and the
generic hand-off uses the completion-handler form of `NSWorkspace.open` so a file type with no
handler is reported in Synth's own voice rather than by a modal that names nothing.

**Synth now ships a JavaScript runtime**, and that is the decision worth remembering (ADR-0016). The
TUI needs one, and the user's machine cannot be asked — an MCP server that will not start degrades a
capability, but a markdown session that will not start is a broken row in the sidebar. So a vendored Bun,
the bundled TUI and OpenTUI's native assets ride in `Contents/Resources/md`, about 70MB. The Bun *version*
is load-bearing and fails silently: `process.getBuiltinModule` arrived in 1.3, and without it OpenTUI's
tree-sitter worker never registers its message bridge — every paragraph renders blank while tables and
fences still draw. Pinned, with the reason written down. A build that cannot fetch Bun still ships; the
kind stops being offered and `.md` links fall back to the OS.

**Both palettes travel.** Ghostty announces light/dark to the program it runs and re-announces it on a
flip, so the TUI re-themes in place rather than being stuck in the scheme it launched under.

Verified by 110 automated tests — block segmentation and smart-list rewrites as pure functions, a
snapshot suite driving the real app on a real renderer with real keystroke and mouse bytes over a real
file, and a suite running the *shipped bundle* under a real PTY to prove the vendored runtime starts and
finds its assets with no `node_modules` anywhere. In the running app, a `link.open` on a `.md` file opens
a markdown row whose PTY child is the bundled Bun from inside Synth.app running the payload on that file —
and, with the setting switched, the same click opens the same document in nvim instead.

One of those suites is about colour, and it exists because the others could not see the bug it caught. A
terminal cell has no backdrop to blend into, so a low-alpha wash does not tint the card behind it — it
composites against nothing and lands on pure black. Both surface tints were written that way, which in
light mode rendered inline code as black on black. Every frame assertion passed anyway, because they read
characters. So `contrast.test.ts` measures the actual rendered spans, flattening each cell's alpha over
the terminal surface, and holds every glyph to 3:1 and the document's own words to 4.5:1 — in both
appearances, rendered and revealed.

## 0.29.1 ships — the payload 0.29.0 promised

0.29.0's headline shipped disabled: `stage_markdown` ran bun's bundler without ever installing
dependencies, so on a checkout without `md/node_modules` the payload build failed — and dist.sh
treats a missing payload as a warning, which is the right degradation for a dev checkout and a
silent feature amputation in a public release. One warning line in 86KB of build output, and no
downstream check — signature, staple, appcast — ever misses a feature. Two fixes, then the patch:
`stage_markdown` now runs `bun install --frozen-lockfile` before the build, and `release.sh` gains
a guard that dies when the built app lacks `Resources/md/bun/aarch64/bun` — the exact path
`MarkdownSession.runtimeURL` probes. Also proven before shipping, because dev builds sign ad-hoc
and this was the payload's first trip through the hardened runtime: Bun 1.3.14 signed with
`--options runtime` and no JIT entitlement runs fine (JSC falls back to non-JIT), and
`sign_app` already signed bun + libopentui.dylib with the same Developer ID, so library
validation passes. Intel is a non-question — Synth has been arm64-only since 0.1.0, so the
aarch64-only Bun slice subtracts nobody. `CFBundleVersion` 561, tag `v0.29.1`. Verified
quarantined-outsider on dmg and zip (both notarized + stapled), **and the feature itself**: the
payload present in both artifacts with the Bun binary executable, running under its release
signature. Appcast newest item 0.29.1 at `sparkle:version` 561, `edSignature` on all 18
enclosures including 5 deltas. Landing page unchanged — no `synth-site` push. The verification
lesson is stamped into the guard: a release must prove its features are aboard, not just that
its signatures are valid.

## Browser comments outlive the mode, and the composer wins the page it lives in

Two reports from using comment mode on a real app, both about losing work.

**Leaving the mode was deleting the batch.** Press the toolbar's comment button again — or Escape —
and every pin and every word went with it. `working.html` had specified the opposite since the batch
landed (`.cm-island.is-parked`: "Mode off with a queue still standing: the island shrinks to a claim,
never to nothing"), and the host even documented `pendingComments` as "what survives the mode being
left". The overlay never implemented it: `exit()` tore itself down and cleared the queue. So the one
control that looks like a view toggle was the only unlabelled Delete in the app.

Leaving now **parks**: the picker comes off — no veil, no suppressors, no captured keys, the page is
the user's again — and the pins, the composer and the island stay. The island becomes the claim the
design asked for: *2 comments not sent · 2 comments ⌄ · ↺ Resume · Send 2*. Nothing there is a
discard. A comment leaves the page three ways only: sent and confirmed, its row deleted, or a
composer discarded blank. Discard the last one and the overlay leaves with it, rather than lingering
as an empty claim.

Parking is the page's answer, not the host's assumption: `exit()` returns `'parked'` or `'off'` and
the host believes it. `'parked'` keeps the CDP client, the binding, the injected script and the count
alive — the parked island's own Send still has to reach somebody, and ⌘⌥⏎ still sends (it was already
gated on a standing batch, not on the mode). Entering again resumes that attachment instead of
stacking a second one. `exitMode` from the page is now the only path that ends a parked attachment,
because a confirmed send ends one too.

**The batch also outlives the document.** The likeliest thing to replace the page is the agent acting
on the comments — the dev server reloads it. Written comments mirror into `sessionStorage` (this tab,
this origin: it outlives reloads, dies with the session, follows nobody), and while a batch is parked
the injected script's verb becomes `restore` — bring the pins and the island back on the new
document, without turning the picker back on. Each comment re-finds its element by the selector it
was snapshotted with, then by xpath, keeping the fractions it was pinned at, so the pin lands where
it was put. One that cannot be found keeps its words, its row and its frozen snapshot; it just has no
pin to ride, and it takes the pin back the moment a re-render puts the element back. A comment
belongs to the page it was left on, which is what `onCurrentPage` in the payload always claimed and
nothing could previously produce: rows off this page name their own, and clicking one goes there.

**And "I can't click into the comment box."** Two causes, both about living inside someone else's
page, both now covered by the harness:

- *The overlay's own events were reaching the page.* Retargeted to the host, a click on the composer
  reads as a click *outside* to every dismissable-layer and focus-scope implementation there is — so
  the app closed its own dialog and dragged the caret straight back out of the textarea. The
  overlay's press, key and focus events now stop at the host, and a page focus trap never hears that
  focus went to us (its own `focusout` is stopped at the window, before the trap's listener). Cursor
  movement and wheel are deliberately still the page's.
- *The top z-index is not the top.* A page's popover or modal dialog is in the *top layer*, above
  every z-index there is. The overlay is a `popover="manual"` now, and re-promotes itself whenever
  the page promotes something new. A modal `<dialog>` is a harder wall — it inerts everything outside
  itself and its backdrop swallows every hit, and `elementsFromPoint` stops reporting the page at all
  (measured, `overlay-harness`) — so over one of those the overlay mounts *inside* it, the only place
  that is both interactive and able to see the page. Known limit: a dialog carrying a transform makes
  our fixed positioning relative to its box, so the overlay is confined to the dialog. It stays
  usable, and the dialog is all there is to comment on.

**One more thing parking exposed: nobody was answering the send.** The page treats Send as a
request — the batch stands, the island says "Sending 2 comments…", and `confirm()` / `reject()` are
what end it — and the overlay has implemented that since the batch landed. The host never called
either. Delivery told the pane a notice and nothing else, so a batch that *did* reach an agent left
its pins on the page and its count on the toolbar forever, and one that never landed said so only in
a notice that auto-cleared. Barely visible while leaving the mode wiped the queue; unmissable now
that it doesn't. `CommentDelivery` now reports its terminal answer (`onLanded` with the receiving
row's title, `onLost` with a short reason) and the browser turns those into the overlay's own two
verbs — so a landed batch flies its pins out and closes the mode, and a lost one is handed back
whole, saying why, still sendable. The simulator holds nothing between sends and leaves both nil.

Verified both ways. `overlay-harness/verify.js` is at 125 checks: parking with the page live under it,
resume, the store, restore on a reloaded document, an element removed and re-rendered, commenting on
the contents of an open modal dialog, and clicking into the composer while a focus trap fights for
the caret. `harness/agents/t27_comment_parked.py` drives the real build for the host half — the count
survives the toggle, the pins stay, entering again resumes, and the batch is still there after the
page reloads under it.
