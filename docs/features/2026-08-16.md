# 2026-08-16

## No device is the default — `browser_device_mode` says so

From feedback: agents kept dropping the browser into device mode unasked, and landing on the
iPad Pro 13″ when they did. Neither is a default in the code — a controller starts
`deviceModeOn = false`, and `HardwareDevice.initial` is the iPhone 16 — so both were choices the
agent made, and the only surface it made them from is the tool's own description.

Two things in that description were pushing it. The `device` param's examples ended on
`ipad-pro-13`, and a literal in a param description is the value a model reaches for. And the
fleet is six phones and tablets with no desktop member: an agent verifying an ordinary desktop
layout that has decided to use a device at all will take the widest one, because 1032pt is the
only entry that won't trip a mobile breakpoint. The off switch existed but read as an
afterthought — `on: false`, phrased in the negative, at the end of a sentence about persistence.

So the description now leads with the resting state: a session runs with no device, at the
pane's own desktop viewport, and that is the right way to check ordinary work — enter device
mode only when the task itself is about phone or tablet layout, and leave it when that check is
done. It says outright that a desktop viewport is the mode *off*, not the widest device in the
list, closing the substitution the fleet invites. The examples are phones now, and `on: false`
is described by what it gives back (the desktop viewport) rather than what it exits.

No behaviour changed — the verb, the fleet, and the app's own default were already right. The
tool description was the whole bug. Verified over MCP stdio: `tools/list` renders the new
description and params.

## 0.32.1 ships — agents stay at the desktop viewport

Patch release carrying the `browser_device_mode` description fix: agents no longer switch the
browser pane into phone or tablet emulation unless the task is actually about device layout.
That fix lives in the MCP server's tool description, but shipping it matters because the
description travels inside the bundle — installed copies keep serving the old wording until
they update.

`CFBundleVersion` 602, tag `v0.32.1`; dmg + zip notarized, stapled, verified credential-less;
appcast newest 0.32.1 at 602, `edSignature` on all 18 enclosures. The first run died on a
transient `hdiutil: create failed - Device not configured` while building the dmg — after
notarization, before any upload, so nothing shipped — and a plain re-run of `release.sh`
succeeded. No `synth-site` push: the landing page's links are the stable bucket aliases.
