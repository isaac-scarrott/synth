# 2026-08-17

## Custom agents: your own command, hosted by an agent Synth already knows

From feedback: people run more than one install of the same agent — `claude-personal` beside the
work one, a wrapper with its own config, a build kept next to the release. Synth hosted exactly
three commands, and there was no way to add a fourth.

The load-bearing decision is what a custom agent *isn't*. Status, quit, paste delivery and MCP
registration are per-supervisor (ADR-0012: one `AgentDescriptor` plus one `AgentSupervisor` each),
and none of that can be typed into a settings field. So a custom agent is never a new kind of
agent — it is a different **command**, driven by a built-in's supervisor. Every one names a
`base`, and the base is not decoration: it is which machinery reads the session. That is also why
there is no "generic command" option. A command Synth cannot read is a terminal session, and the
template already opens those; offering it as an agent would promise a status light, a quit card
and comment delivery that could never arrive.

Which base is a fact Synth can usually work out, so it does: the user types only the command, and
`AgentProbe` runs `<command> --version` in a login shell (the same PATH a launched agent resolves
under) and matches the answer against each built-in's `versionMarkers` — Claude Code answers
`2.1.9 (Claude Code)`. A recognised answer *sets* the base, and overrules it on a later re-probe:
repointing an agent at another command and leaving it on the old supervisor is a row that says one
thing and runs another. A command that answers but isn't recognised leaves the base alone — that
one is the user's assertion, not Synth's — and says nothing about it, because the picker still
reads "Choose…" and a sentence about what a version string wasn't is a complaint nobody can act
on. A command that doesn't resolve says "Not on your PATH" and, with no base or no command, the
agent is simply not offered anywhere: the same gate an uninstalled built-in has always sat behind.

Everything is edited in place, on the row: the name (a field, with a pencil, because a text field
styled as a label is a field nobody finds), the base (a pop-up button), and the command and its
flags as one launch line in the same dark field a built-in puts its flags in. Adding one opens
nothing — a row appears at the end of the list, empty, and the name follows the command as it is
typed until a name is typed over it. Removing one asks only when a template entry points at it,
and asks on the row: the ask is bolted to the consequence, not to the surface. Sessions already
running carry on, exactly as they do when an agent is switched off.

The registry is what actually changed shape. `AgentRegistry.all` stops being a constant and
becomes built-ins plus the user's own, so every surface that already read the registry — ⌘K, ⌘N,
the split picker, the template add bar, the project tab's launch line, the PATH shims,
`SYNTH_AGENT_BINS` — picks a custom agent up with no changes at all. `supervisor(id)` resolves
through `hostID`, so a custom agent shares its base's supervisor rather than needing one of its
own; `decorate` and `launchCommand` now take the descriptor and the binary, because a supervisor
serving two commands must name each one's real binary and `exec` the right program.

Two seams needed real work. Env var names can't hold a dash, so `SYNTH_REAL_CLAUDE-PERSONAL` is
sanitised to `SYNTH_REAL_CLAUDE_PERSONAL` — and `synth-hook` carries the identical transform,
because the two ends agreeing on that key is the whole handshake. And the hook dispatched on the
name it was invoked as, with the reported agent id hardcoded per role: a `claude-personal` session
would have announced itself as the built-in Claude Code and taken its flags, mark and notification
copy. Both are fixed by a new per-session env line, `SYNTH_AGENT_MAP`, of
`<command>:<role>:<id>` — the three coincide for a built-in and differ for a user's own command —
plus the id baked into every hook command the launch role writes, since an event arrives as its own
later process with nothing but its argv to say who it is about.

Verified in the driven app end to end: a seeded `claude-personal` probed as `2.1.9 (Claude Code)`
and picked up Claude's mark; `oc-nightly` reported "Not on your PATH" in amber and dropped out of
the add bar; and a spawned session came back as kind `custom-seed0001` with the shim resolving
`SYNTH_REAL_CLAUDE_PERSONAL`, taking Claude's launch role (`--session-id` + `--settings`), and
every hook command carrying `custom-seed0001`.

Persisted in `state.json` beside the setup script and the session template rather than in
UserDefaults with the on/off switches: a switch is a fact about this machine, but which agents
exist is setup you typed and would hate to retype. Settings ▸ Synth ▸ **Agent defaults** is
renamed **Agents**, since it now lists agents rather than only their defaults.

One known consequence, unchanged from an uninstalled built-in: a session persisted for an agent
that was later removed restores with its saved name and opens a plain shell, because there is no
supervisor left to launch it.

## 0.33.0 ships — custom agents reach installed copies

Minor release carrying custom agents: Settings ▸ Synth ▸ **Agents** hosts the user's own commands,
and a custom agent turns up wherever a built-in does. A feature bump, not a patch — the registry
grew a new kind of member.

Worth recording is how nearly it shipped as nothing. History had been rebased since the last
release, and the custom-agents commit landed *below* the two 0.32.1 commits — so `git log` reads
as though it were part of 0.32.1, while tag `v0.32.1` points at `c054ba6`, which predates it. The
work was on `main`, looked released, and wasn't in any build. Position in the log is not evidence
a commit shipped; the tag is. Diff against `<last tag>..HEAD`, never against "commits above the
release commit".

`CFBundleVersion` 605, tag `v0.33.0`; dmg + zip notarized, stapled, verified credential-less with
quarantine set — the app inside the image validates on its own, not only the image around it.
Appcast newest 0.33.0 at 605, `edSignature` on all 18 enclosures, and the delta from 602 is 1.1MB
against a 164MB full download. No `synth-site` push: `landing/` is untouched since v0.32.1 and its
links are the stable bucket aliases.

## MCP servers ride the launch, so Synth stops writing into your repo

From feedback: every managed worktree carried three files Synth had put there — `.mcp.json`,
`opencode.json` and `.agents/mcp_config.json` — and no *user* repo ignores those names. They were
untracked in every worktree forever, they were noise in the `git status` the work is judged by, and
one had already been committed by an agent that saw a dirty tree and tidied it (`da7f902`). Synth's
own repo hid the problem from us by gitignoring all three.

They are now handed to each agent as its launch happens, and nothing is written into the tree.
`MCPInstaller.launchEnv` builds the enabled servers in each agent's own schema, `HookEnvironment`
puts them in the PTY's environment, and `synth-hook` — already the thing that intercepts every
agent's command — turns each into the registration that agent understands. All three routes were
measured against the CLIs on this machine before a line was written, because the docs are wrong or
silent about two of them:

- **Claude Code** takes `--mcp-config '<json>'` beside the `--settings` we already inject. The flag
  is repeatable and additive without `--strict-mcp-config`, so a user's own configuration stands.
- **opencode** takes `OPENCODE_CONFIG_CONTENT`. Its loader reads that variable last and merges it at
  project scope, so a user's `opencode.json` still applies. The shim merges rather than sets: the
  login shell may have exported the user's own value moments earlier, and an entry already under one
  of our names is theirs, not ours (the `--settings` rule).
- **Antigravity** has no such flag, and its own docs name only a global config and a per-plugin one,
  both machine-wide — which is why the worktree file existed. But `--add-dir` turns out to carry
  MCP the way it already carries our hooks: measured on agy 1.1.9, a server declared in an added
  dir's `.agents/mcp_config.json` is spawned and its tools listed with that dir nowhere near the
  cwd. The registration moves into the Synth-owned dir the shim already hands agy.

That last measurement is what decided the shape. Had it failed, agy would have kept its file and
needed the repo's `.git/info/exclude` to hide it — which works (measured: a rule in the *main*
repo's exclude file silences the name in every linked worktree, while the per-worktree
`.git/worktrees/<name>/info/exclude` is never read at all) but reaches into the user's `.git` and
hides a `.mcp.json` they wrote themselves in their main checkout. Nothing needs it now.

Three things go with the files. `ArchiveSweeper`'s `userUntracked` carve-out — which existed only
so the sweeper wouldn't refuse to archive a worktree over Synth's own droppings, and which would
have started masking real user files the moment it outlived its reason — is deleted; untracked
means untracked again. The `.gitignore` entries in Synth's own repo go, since there is nothing to
ignore. And a worktree that an older build already dirtied is swept on the next launch:
`removeStrandedConfigs` deletes each file only while `isUnmodifiedSynthConfig` still proves it is
structurally ours, so a config the user has since put their own server into survives untouched.
A stale file left in place would have been worse than untidy — it would register the same servers a
second time, pointing at whatever the toggles said back then.

The cost is named rather than hidden: an invocation the shim deliberately doesn't instrument no
longer sees the servers. `claude -p`, `opencode run`, the management subcommands and a `claude`
started outside a Synth terminal all used to find `.mcp.json` sitting in the worktree. Interactive
sessions — every row Synth hosts — are unaffected.

Claude's folder-trust prompt on a fresh worktree is *not* fixed by this, and it never was Synth's
`.mcp.json` that caused it: trust is recorded per directory in `~/.claude.json` and inherited only
from ancestor directories, and Synth's worktrees live under Application Support rather than under
the user's repo, so a new worktree is always an untrusted path. What does go is the second prompt —
servers passed on the command line are not the project servers Claude asks to approve, and there is
no `.mcp.json` left to ask about.

The gate keeps its teeth through a new automation verb, `automation.mcpLaunchEnv`, which returns
exactly what a launch in that worktree would be handed: `t4a` now asserts the three schemas, the
channel sandbox and the worktree in each, that the planted stranded file is swept while the
planted user file survives, and that a real `opencode serve` connects the browser server off that
env alone. `t8` reads the toggles the same way. 15/15 and 18/18.

## The gate now proves every agent loads the servers, not just that we handed them over

Shipping the launch-config change left a hole worth naming: `t4a` proved the app builds the right
registration and `t4b` proved *one* agent (opencode) drives the browser with it, but for Claude
Code and `agy` nothing asserted past "our registration was on the command line". That was the
claim under test, so it is now `t4c`.

The signal is the server process. An agent that has read our registration spawns
`node <sandbox>/browser-mcp/server.mjs` itself; one that hasn't, doesn't. It costs no model turn,
and it is attributable because each agent runs alone and the channel's sandbox is in the command
line — the stable channel's servers can't be mistaken for the dev channel's. Claude additionally
goes the whole way: it calls `browser_list` and `browser_navigate` and the embedded browser
actually moves.

Two things were learned building it, both of which would have read as product failures to anyone
debugging later. **`agy` starts its MCP servers lazily** — a row that never takes a turn never
spawns one, so the probe is a trivial turn that has nothing to do with the browser; building the
request is what makes it connect. And **`agy` is slow by a different order**: a first attempt drove
it with the same model-facing prompt `t4b` gives opencode and it spent about three minutes on
preamble — reading each server's `instructions.md`, raising a permission prompt of its own — so a
gate that gave up at three minutes killed the app one second before the tool call landed, and the
failure surfaced as our own MCP server reporting "Synth isn't running". That is why the far-end
tool-call assertion is Claude's and `agy`'s is the process: a check whose outcome depends on a
model choosing to call a tool inside a fixed window is a flaky check, not a strict one.

## 0.34.0 ships — Synth stops writing into your repo

Minor release carrying the launch-config change: the three MCP files Synth used to drop in every
managed worktree are gone, the servers ride each agent's launch instead, and worktrees an older
build dirtied get swept when they come up. A feature bump because the change is visible to anyone
who ran `git status` in a Synth worktree, not a quiet fix.

The release proved its own subject. The clean-tree guard tripped on `.mcp.json`, `opencode.json`
and `.agents/mcp_config.json` sitting untracked in this repo — the feature deleted the `.gitignore`
lines that had been hiding them, so the files it removes surfaced as exactly the mess it exists to
end. Deleting them is what the sweeper does on launch; doing it by hand first is the same act, one
build early.

`CFBundleVersion` 609, tag `v0.34.0`; dmg + zip notarized, stapled, and verified credential-less
with quarantine set, the app inside the image validating on its own. Appcast's newest item is
0.34.0 at 609, `edSignature` on all 18 enclosures, an 828KB delta from 605. `landing/index.html`
unchanged since `v0.33.0`, so no `synth-site` push.
