# 2026-08-18

## 0.34.1 ships — Claude opens again

Patch release for a production-only crash in the launch hook introduced by 0.34.0. Moving the
bundled MCP servers onto Claude's command line added an optional argument array to
`runClaudeLaunch`; Swift's release build corrupted that temporary array, so the hook trapped while
assembling the command and Claude never reached the screen. Debug builds and `claude --version`
both passed because neither exercised the optimized interactive path with a non-empty
`SYNTH_MCP_CLAUDE`.

The launch arguments are now built by appending each value directly, with no optional array or
chained concatenation for the optimizer to miscompile. The production binary was driven through a
real pseudo-terminal with the full MCP configuration before release, and reached Claude's prompt.

`CFBundleVersion` 611, tag `v0.34.1`; dmg + zip notarized, stapled, and verified credential-less
with quarantine set, including the app inside the mounted image. Appcast newest 0.34.1 at 611,
`edSignature` on all 18 enclosures, 72KB delta from 609. No `synth-site` push; landing links use the
unchanged stable bucket alias.

## An agent can be named by a shell alias

`claude-personal` in Settings ▸ Agents read "Not on your PATH" for a command the user runs every
day, because it was an alias — `alias claude-personal=claudewho-personal` in their `.zshrc` — and
an alias exists only inside an interactive shell. Nothing Synth spawns is one: `AgentProbe` asked
a login shell (`zsh -l -c`), `resolvedBinary` scanned PATH dirs for a file of that name, and both
correctly found nothing. A wrapper script or a symlink would have fixed the user's machine; it
would not have fixed the feature, whose promise is "type the command you already run".

So the name is now followed before anything is done with it. `ShellEnvironment` already probes a
login **and interactive** shell for its PATH, which is the one place an alias table exists, so it
brings that table back too — read out of zsh's own `$aliases` map rather than parsed back out of
`alias -L`, which would mean unpicking shell quoting to get at the value. `AgentDescriptor`
expands the name against it the way the shell would: re-expand the first word while it names
another alias, and the rest ride along as arguments.

That "and the rest" is the second half of the answer. An alias is as likely to pin a flag
(`alias claude-personal='claude --model opus'`) as to rename a program, and the flag is part of
what the user means by the name. `resolvedCommand` returns both — the program to exec and the
arguments its name carried — and the shim puts the arguments back in front of the user's own,
where the shell would have put them, over `SYNTH_REAL_ARGS_<AGENT>` beside the existing
`SYNTH_REAL_<AGENT>`. They are appended rather than concatenated, because this is the same argv
whose chained `+` the release optimizer miscompiled in 0.34.0.

What is refused is as load-bearing as what is followed. An expansion carrying shell syntax — a
pipe, a substitution, a second command, but also quoting, globs and brace expansion — is a shell
line, not a program: splitting it on whitespace and handing the pieces to `execv` would run
something the user's own shell never would. Those resolve to nothing, and the row says the thing
that is actually wrong ("That alias runs a shell command, not a program") rather than the thing
that isn't ("Not on your PATH"). A row that did resolve through an alias says where it went —
`Claude Code 2.1.9 · alias for claudewho-personal` — because the row otherwise names a command
the user's PATH hasn't got.

The bug underneath was bigger than the custom-agent row. A Synth session sources the user's
`.zshrc`, and an alias beats PATH: anyone who had aliased `claude` at all was reaching the real
binary directly and never the shim in front of it — a session with no `--settings`, no hooks, no
session id and no status light, indistinguishable from Synth being broken. The generated session
`.zshrc` now drops the agent names from the alias table after the user's config has had its say,
one line below the shim-PATH re-prepend that exists for the same reason. Nothing is lost by
dropping them: the app resolved the alias before launch, and the shim puts back both the program
it named and the arguments it carried.

The probe now asks the resolved program rather than the typed name, which is also the more honest
question — the row is meant to describe what a session will actually exec. It does not pass the
alias's arguments to `--version`: which agent a program is, is a fact about the program, and a
wrapper handed flags it doesn't know may answer with an error instead.

`Synth --agent-check <command>` prints the resolution a launch would use (program, leading
arguments, what the name expanded to) and exits nonzero when nothing would — the same shape as
`--browser-check`, and the only way to gate resolution without driving a whole session for each
case. `t28_alias_agent` uses it for the six resolution cases against a throwaway `ZDOTDIR`, then
drives the launch: a custom agent whose command exists *only* as an alias goes live, and live is
set by Claude's `SessionStart` hook, so an alias that had shadowed the shim would run perfectly
and report nothing.

## `claude setup-token` runs again inside Synth

Reported from a Synth terminal: `claude setup-token` answered
`Error: Invalid MCP configuration: MCP config file not found: <cwd>/setup-token`. Two separate
faults, both in the launch shim, and both of a kind that a driven session can never catch —
because a driven session only ever makes the one invocation Synth makes itself.

`--mcp-config` takes a LIST (`<configs...>`, "JSON files or strings, space-separated"), so every
word after its value is read as another config until a flag ends the list. The bundled servers
were injected last, which put the user's own first word — `setup-token` — inside our list. Nothing
about the fix is specific to that word: `--settings` (always injected, and single-valued) now
follows `--mcp-config`, so the list is always closed before the user's arguments begin and no
argument of theirs can be read as ours whatever it is.

The second fault is why the injection was reached at all. Subcommands aren't sessions and pass
through uninstrumented, but the list of them was the one written when the feature landed:
`mcp, config, update, doctor, migrate-installer, install`. Today's CLI answers to far more, and
`claude --help` is not the whole list either — `attach`, `daemon`, `logs`, `remote-control`,
`respawn`, `rm`, `self-hosted-runner` and `stop` are real and hidden. All of them are listed now,
along with `--help`/`-h` beside `--version`. The list errs towards listing on purpose: a name
missing from it gets a session's flags and the command fails outright, while a name listed in
error only costs that one invocation its instrumentation.

Everything else the shim asserts about Claude was checked against the CLI reference and the hooks
reference rather than assumed: `--session-id` wants a UUID (it gets one), `--settings` takes an
inline JSON string as well as a path, `--strict-mcp-config` is what would make our servers replace
the user's rather than add to them (it is not passed), and all ten hook events Synth wires —
`SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`,
`PostToolUseFailure`, `PermissionRequest`, `Notification`, `Stop`, `StopFailure` — exist and
merge with the user's own: "Hook entries merge across settings levels rather than replacing each
other", so a Synth session does not silence the hooks in anyone's `settings.json`.

`t29_claude_argv` gates the command line itself, with no app and no model turn: it runs the shim
against a fake `claude` that prints its argv, asserts every subcommand passes through byte for
byte and that a session's injection ends its own list, then hands the shape to the real `claude`
parser — which is the only authority on what its flags swallow — and asserts the shipped order is
genuinely fatal, so the check can't pass by accident.

## 0.35.0 ships — your own name for an agent works

Minor release carrying alias resolution: an agent's command can be a shell alias, which is the
form most people's second Claude install actually takes, and until now read as "Not on your PATH"
because an alias exists only inside an interactive shell. It carries two fixes that were invisible
until someone typed something unusual into a session — `claude setup-token` dying on the shim's
injected `--mcp-config`, and an alias for an agent's own name silently costing that session its
hooks, its session id and its status light.

`CFBundleVersion` 613, tag `v0.35.0`; dmg + zip notarized, stapled, and verified credential-less
with quarantine set, including the app inside the mounted image. Appcast newest 0.35.0 at 613,
`edSignature` on all 18 enclosures, 1.1MB delta from 611. No `synth-site` push: `landing/` is
unchanged and its Download button points at the stable `Synth.dmg` alias, which now serves this
build.
