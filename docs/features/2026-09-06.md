# 2026-09-06

## The site argues agent-agnosticism, not attention

The 2026-09-04 entry recorded a page built around one claim — that Synth spends your attention
carefully. That is no longer the top of the argument. The claim the page now leads with is that you
can run as many coding agents as you like, of whatever kind, at once, and never be locked to a
vendor or a harness; attention management is demoted to the third beat, where it explains why
running many is survivable rather than being the reason to download anything.

The headline is `Whatever coding agents you run, however many of them, / all at once.` It names no
number and no vendor. The sub carries three claims in three sentences: built around the terminal and
tied to no model or harness; the terminal, browser and simulator are all made to be used by a human
and driven by an agent; you are told when an agent needs you and left alone when none do. The
agent names moved out of the hero prose and live only in the marks row a screen below, where a logo
is more convincing than a list.

Five beats, in order. **No agent to commit to** — whichever agent is best this month is unlikely to
be the one that's best next month, so Synth detects what you have installed and integrates with them
all, making a new model or harness something you adopt rather than migrate to. Its three cells are
arrival (you point Synth at nothing), capability (every agent gets a real browser and a booted
iPhone it can drive, wired up once and never again), and constancy (change agent, keep everything
else). **Many things at once, orchestrated** — work is organised by project and by branch, agents
hand work off to other branches, and however much is in flight it stays one list you can read at a
glance; cells run the lifecycle in order, created then moved between then retired, with archiving
argued as what keeps the glance cheap rather than as disk hygiene. Then attention, then the browser
and simulator, then speed.

Two vocabulary decisions. **"Workstream" is retired** — it was coined to avoid saying "branch" on
the grounds that branches aren't distinctive, but that is an argument about positioning, not about
words, and it cost the page a two-sentence glossary in the very lede that should have been selling.
The page says "branch", which is what the app says, and spends the distinctiveness on what each one
gets instead. **The eyebrow chips are gone** from all five sections and the hero, and the `.eyebrow`
rule with them.

Typographic consequence of a headline that must never wrap: a 53-character line cannot both fit the
1152px content column and outrank a 44px `h2`, so the headline gets its own measure (`--hcol`, up to
1440px) and section headings drop to `clamp(1.5rem, 2.6vw, 2.125rem)`. Above 880px the line is held
on one line at `min(3.5rem, var(--hcol) / 26)`, a divisor measured rather than guessed. Below it the
one-line size would fall under 30px, so the hero wraps and goes left — headline, sub, buttons and
requirements line together, since a left headline over centred everything reads as a bug.

The approval figure said "Create a worktree for fix/toast-timing?", which the app never says:
`Palette.swift` builds that frame as `"Create \(prompt.branchName)?"`. The mock now matches. The
same read found the frame's hint rendering "wants a new worktree off main **and hand** the work off",
which does not agree with `wants`; fixed in `Palette.swift` in the same pass.

`landing/` still serves `synth-site`. Nothing here is published.

## The site is edited in the page, not in the file

Copy work on the page meant an edit, a reload, and a judgement about balance made from memory of
what the last version looked like. `site/devserver.py` and `site/dev-edit.js` remove that loop:
the server injects the editor when it serves the page, so nothing in `index.html` carries markup for
the benefit of a dev tool, and the script refuses to run anywhere but localhost.

A save is an exact string swap rather than a guess about which element was meant. Each editable
element remembers the `innerHTML` it was served with, and the server rewrites `>` + that string +
`</tag>`, requiring exactly one match and refusing the write otherwise. The tag anchoring is not
decoration: matching on text alone made `Free · macOS 14 or later · Apple silicon` ambiguous, because
it is a prefix of the close section's `… · signed and notarised`. Replacements are re-wrapped to 100
columns at the original indent, so the file does not degrade into single long lines, and `&nbsp;` —
which contenteditable emits for any run of two spaces — is stripped before it can reach the file.

Live reload rides the same server: an SSE endpoint watches `index.html` and `dev-edit.js` and the
page reloads on change, restoring scroll position through `sessionStorage`. The server absorbs the
mtime of its own writes so a save doesn't reload the page under you, and a reload arriving while
text is unsaved waits until you stop typing rather than discarding the sentence.

## The champagne loses its yellow

The mark's champagne moves from `#eee0cd` to `#f1ddd7`. The old one read beige: in OKLCH it sat at
hue 75.7, close enough to pure yellow that the brand colour looked like a warm grey that had gone
off. The new one is hue 37.4 at chroma 0.024 — reached by draining chroma as well as rotating,
because rotating alone kept enough saturation that the low hues arrived as blush rather than as
champagne. Lightness is untouched at 0.913, so `--on-accent` needs no revisiting and every
contrast pair that held before holds now.

The candidates were swept as buttons on the real page rather than judged as hex, holding L and C
and moving only hue. Two boundaries came out of that and are worth recording, because both are
arguments against going further. `--error` (`#ff8a80`) sits at hue 26.1, so a champagne below
about 30 shares an angle with the colour that means something broke. And by hue 34 the colour has
stopped reading as champagne at all and reads as blush.

Every derived champagne took the same transform — hue −38.3, chroma ×0.80 — rather than being
re-picked by eye, so the relationships that made them derived in the first place survive. That
covers the update wash (`#eccE9b` → `#f6c7b4`, the chroma-restored one the foot button's 13% tint
needs), the landing page's accent-fill gradient, and the hero halo's shader tint, which is the
same colour expressed as normalised floats and so has to be converted rather than swapped.

One consequence is a comment that no longer has a job. `Theme.working`'s amber carried a note that
it sat 4° off champagne and therefore "stays put and the accent keeps clear of it". The gap is now
35°, so the crowding that note guarded against is gone and the note went with it.

Light's warm pair did not move. Copper (`#a86038`, hue 48.4) and the bronze update-ink (`#7f6130`,
hue 77.9) were both chosen against contrast floors on a near-white panel, not by matching the
mark's angle, and the accent's own comment calls copper "the same warm family" rather than the same
hue. Copper is now 11° off the mark and the bronze 40°. Whether that reads as a family or as a
mismatch is a light-theme question, and it is still open.

The historical entries keep `#eee0cd` where they mention it. They record what was true when they
were written.

## The figures are photographs of the product

Every product figure on the landing page was drawn in HTML, under a comment claiming that a
drawing "cannot drift from the product" because it shared the palette. It had already drifted
twice: the approval card invented a `Project / Base / Handoff` list the app never renders, and the
copper accent it used existed as a raw hex in three places with no link to the app's real token.
The five figures are now captures of the running app, recorded by `site/capture/`.

The rig is a seeded state file plus a socket. `$SYNTH_STATE_DIR` points Synth at a scratch
`state.json`, so a run boots with exactly the projects, branches and sessions the scene names.
`HookServer` takes `{"session":"<uuid>","signal":"needsInput"}` on its unix socket, so a row's
status is staged in one line rather than by waiting for something real to happen. Every invented
word lives in `scenes.py` and nothing else; `capture.py` holds no fiction at all.

Capture happens on screen, not off it. `automation.screenshot` renders the app's own view
hierarchy, which is why the browser pane came back blank and the simulator black: a CEF page runs
in another process and a device screen is a video layer, and neither is in the hierarchy. So a
capture run uses the display — a new `SYNTH_AUTOMATION_VISIBLE` keeps `Automation.park`'s
autosave scrub and drops the concealment, `automation.windowSize` hands back the window-server
number, and `screencapture -l` photographs what a person would see. Gates stay invisible; only a
capture run costs the desktop.

Three product changes fell out of it. `automation.windows` and `automation.front` (which refuses
unless the run is visible, so a gate can never steal focus). And a real regression: `park` sets
`alphaValue = 0`, AppKit reports a fully transparent window as occluded, and
`GhosttySurfaceView.updateOcclusion` therefore stopped the renderer — so every terminal capture
was empty. `t13_termcontrast` had been failing on it before any of this work started.

The agent sessions are real Claude Code. An authored transcript printed by a shell was the first
approach and it worked, but a live agent is the thing being sold, so the hero is a real session
working on this page: it reads `--accent`, finds the copper duplicated across three places, and
stops on its own question about what to do. A live agent is also the non-deterministic part, so a
scene now declares the state its figure depends on (`expect: "needsInput"`) and re-takes when the
agent answers in prose instead of asking — a take that shipped idle under the right filename was
what taught us that.

What a capture will not do is follow the page's theme, so each figure picks one: the hero and the
attention crop are light, where the transcript has the most contrast and the window reads as an
object on a dark page; the browser, simulator and approval figures are dark, because two of them
contain this page and a dark rectangle inside pale chrome reads as a mistake. The attention figure
is cropped to the sidebar and the deck. Uncropped it was mostly the landing page again, which the
browser tab already shows, and the notification card it exists to prove was a corner of it.

Deleting the drawings took 92 CSS rules with them, and with them the copper duplication the hero's
own agent had just found. The bug in the figure was fixed by replacing the figure.

## The page holds one rhythm, measured rather than eyeballed

A full spacing and layout audit, run at thirteen widths from 320 to 1920, first by the author and
then by a sub-agent given the design system's claims but not the author's findings. Four things
the first pass fixed, seven more the independent pass found, and two the author got wrong on the
way and caught by measuring.

`--band`'s comment called it "the one vertical rhythm" and it was not. The hero used `8vw` and the
close band `10vw` against the band's `7vw`, so the three agreed only at the top of their clamps:
at 390px the hero's extra air vanished entirely and at 1440px it was 96px. The emphasis the design
intended existed on desktop and nowhere else. Both are now the band plus a step off the scale, so
the relationship holds identically at every width. The hero also had `padding-bottom: 0` — the only
section that contributed nothing to its own boundary, making the gap below it half of every other
one, and putting the capture's rounded corner against the next section's hairline at exactly y=0.

The headline got **smaller as the viewport got larger**: 44px at 880 and 30.5px at 881, a 31% drop
for one pixel, not recovering until about 1256. One breakpoint was answering two unrelated
questions. Whether the line can be held is arithmetic — at 44px it needs a 1144px measure, and at
880 the wider `--hcol` equals `--col`, so the wider measure buys nothing at precisely the width it
was introduced for. Whether the hero goes left is a judgement about ragged edges. They are separate
now, at 1255 and 880, and the wrapped size is the same 44px the one-line rule reaches at its
threshold, so the size is continuous across both.

Two mistakes worth recording because both looked like fixes. Moving `.head`'s `46ch` cap onto the
`h2` to let the lede's own `58ch` measure fire made it worse: `ch` resolves against the element's
own font-size, so 46ch on a 34px heading is 1030px and caps nothing, where on `.head` it resolves
against 16px and constrains the block. The inert declaration was removed instead. And the tab bar's
alignment override was first written into an earlier media block, where it lost on source order —
the same class of bug the audit had just certified absent, reintroduced while fixing something
else. A media query adds no specificity; an override has to follow what it overrides.

Nine rules went for matching nothing or firing never. Scale violations that remain are deliberate
and now say so: a segmented control needs 3px of inner padding and 2px between segments, and its
7px radius is the enclosing 10px minus that padding, which is how a nested radius is derived rather
than a fourth value invented.

## The figures follow the reader's theme

Each product figure is a `<picture>`: the dark capture under `prefers-color-scheme: dark`, the light
one on the `<img>`. Every pair is dimension-identical, which is what makes one set of intrinsic
`width`/`height` correct for either source and stops the box reflowing as the image loads — a pair
that disagreed by a few pixels would have rendered one variant at the wrong aspect ratio with
nothing to show for it.

Page weight is unchanged in practice. A viewer downloads one variant, so the cost is 529KB against
523KB; the doubling is repository size, not page load. The source selection re-runs when the media
query flips, so changing system theme with the page open swaps the image without a reload — tested
in Chromium, untested in Safari, which is the browser this page's audience most uses.

## OpenCode 2 joins as Synth's fourth hosted agent

A session can now run **OpenCode 2** (`opencode2`, OpenCode's v2 preview CLI) beside Claude Code,
OpenCode and Antigravity — one more `AgentDescriptor` plus one more `AgentSupervisor`
(`Opencode2Supervisor`), same shape ADR-0012 promises. It shares OpenCode's own mark (the block
"o"): it is the same product, wearing a new major version, not a new brand.

v2 is not a drop-in swap for v1's transport, though — its whole server architecture changed, and
every claim below was verified empirically against the real preview binary
(`0.0.0-beta-18414`), not read off documentation, because there wasn't much to read.

**The server moved out of the TUI's own process.** v1's bare `opencode --port <assigned>` is one
process: the port you hand it is the port its own built-in server listens on. v2's bare command has
no `--port` at all — the visible TUI instead talks to a server over `--server <url>`, either a
shared per-machine background daemon (`opencode2 serve --service`, already running before Synth
ever launches anything) or a dedicated one. So `synth-hook`'s launch role for `opencode2` is now a
small two-process supervisor for the run of one row: start `opencode2 serve --port <assigned>
--hostname 127.0.0.1` in the background, block until it actually answers `/api/health` (verified:
`--server` does **not** retry a server that isn't listening yet — it dies immediately with "could
not reach server", so skipping this wait turns every launch into a coin flip), then start the
visible TUI pointed at it. Both processes share Synth's own SIGINT/SIGQUIT-ignoring lifetime (set
before either is spawned, inherited by both via `posix_spawn`) and one process group, so the
existing `killpg` teardown at row-close reaches the background server exactly the way it already
reaches everything else in the tree — no new close path needed.

**Every v2 route is authenticated; v1's isn't.** The server takes HTTP Basic auth (user `opencode`,
a password it normally mints and prints on its own stdout). Rather than have the shim race reading
that line, `Opencode2Supervisor` mints the password itself (alongside the port, the way v1 already
mints a port) and pins it via `OPENCODE_PASSWORD` before either process starts — confirmed this
both works and suppresses the printed line entirely, so there is nothing left to race.

**There is no v2 equivalent of `/tui/append-prompt`.** v1's supervisor fills and submits the TUI's
own prompt box over HTTP because posting to a session id directly wouldn't make the visible TUI
show it. v2 doesn't expose a replacement — verified live: creating a session and prompting it over
the API while a TUI is already open never changes what that TUI displays, `POST .../view` only
acknowledges an idle notification rather than focusing anything, and the internal commands that
would do it (`tui.session.select`, `tui.prompt.append` — real, found by reading the binary's own
event-type strings) are never reachable over HTTP. So `Opencode2Supervisor.deliver` falls back to
the same plain terminal paste-and-submit Claude Code's supervisor already uses — confirmed live
against a real TUI (typed text landed in its prompt box, Enter submitted it, the model answered).
`CommentDelivery`'s existing safety gate — paste only ever reaches a session the supervisor has
confirmed live, on the same reasoning that already protects Claude Code — applies unchanged and
costs nothing new.

**MCP registration moved from an env var to an API call.** v1 hands its bundled MCP servers to
opencode over `OPENCODE_CONFIG_CONTENT`. Correction from an earlier version of this entry: that env
var is *not* ignored by v2 — independent verification caught this. v2 does read it, but its MCP
subsystem initialises lazily, roughly 10–30s after `/api/health` already answers, so a server
injected through it does eventually appear in `GET /api/mcp` — just too late to be live for the
moment the shim needs it (a fresh row's first turn can start well inside that window). `PUT
/api/mcp/<name>` registers one immediately and deterministically instead, so the shim calls that
once `serve` is confirmed healthy and before the visible TUI starts — reusing `SYNTH_MCP_OPENCODE`'s
existing payload rather than adding a second env var, since v1 and v2 want the same three fields for
a local server (`type`, `command`, `environment`) and `MCPInstaller` only ever emits already-enabled
servers regardless of which agent reads them. The PUT survives the config env var's later load
rather than being clobbered by it — confirmed live.

**The event vocabulary changed shape.** v2's SSE envelope is flatter (`{id, created, type, data}`,
no `properties` wrapper) and its lifecycle is explicit outcomes rather than a generic busy/idle
pair: `session.execution.started` (busy), `.succeeded` (idle), `.failed` (error) and a **dedicated**
`.interrupted` — cleaner than v1, which has to string-match `MessageAbortedError` out of a generic
error event to tell a user's own interrupt apart from a real failure. `question.asked` has no
successor by that name (`OPENCODE_ENABLE_QUESTION_TOOL` is gone from the binary); the Form system
generalises it, and opencode2's own UI code classifies `form.created`/`form.replied`/`form.cancelled`
under the same "question" surface `permission.*` already is — verified by reading that
classification straight out of the binary — so `Opencode2Supervisor` treats them the same way.

**Fixed alongside it: `AgentProbe`'s custom-agent detection matched the first signature in
registration order, not the best one.** opencode2's own `--version` answer ("opencode2 v0.0.0-…")
contains v1's marker ("opencode") as a substring, so a custom command wrapping opencode2 would have
been silently recognised as opencode v1 whenever v1's signature happened to be checked first —
exactly the position it's in, right before opencode2's own entry. The fix is general, not an
opencode2 special case: the longest matching marker wins, not the first one scanned.

**Known gap, left open rather than papered over: the light-theme correction doesn't carry over.**
v1 and v2 share a config root (`~/.config/opencode`), and v1's `OpencodeTheme.sync` writes into it
unconditionally, so the hope was that a shared `tui.json` + `themes/synth.json` would theme v2's TUI
for free. Verified empirically that it does not — a v2 TUI launched against Synth's own shipped
theme file rendered pixel-identical colours to one launched with no theme file at all. v2's own
theming has moved (its bundled web UI reads a `localStorage`-keyed `oc-2` CSS theme; the state file
under `~/.local/share/opencode/storage/theme-mode.json` only carries light/dark, not per-key
overrides), and reverse-engineering a preview build's still-moving theme format wasn't worth
committing to. v2 ships its own light and dark themes; a user gets those, unmodified, until v2
either stabilises a theme API or someone measures whether its light half needs the same correction
v1's did.

**Two rounds of independent review, both acted on.** The first caught: `Opencode2Supervisor`'s
delivery retry blind-pasting into a row that had already gone away (its siblings all guard this;
this one didn't — fixed with the same liveness check `AntigravitySupervisor` already has); a
resumed row's first observed event not being guaranteed to be its own conversation's, since v2's
`parentID` is never populated in this preview (fixed with a new `AgentSupervisor.seedResume`,
default no-op for every other agent, called ahead of `attach` on a resume); `upgrade`/`uninstall`/
`--standalone` missing from the shim's pass-through recognition; and the `OPENCODE_CONFIG_CONTENT`
paragraph above claiming the env var is ignored, when it's actually just too slow (see above) — the
first version of this fix corrected the doc but left the identical claim standing, verbatim, in
`synth-hook`'s own source comment. The second round caught that miss, plus two more unverified
copies from v1's list: `update` (the actual v2 spelling of `upgrade`) was missing, and `uninstall`
— copied in during round one without checking the binary — isn't a real v2 subcommand at all (a
bare word falls through to the `[<directory>]` positional). Also added: `-h`/`--help`,
`--completions`, `--wizard` to the one-shot bypass, since none of the three would otherwise stop a
plain `opencode2 --help` from spawning a `serve` and registering MCP servers just to print usage.

**A third round caught `attach`'s own turn as the same mistake** — real for v1 (`opencode attach
<url>`), not for v2 (falls through to the same `[<directory>]` positional `uninstall` does),
carried over anyway. Every subcommand in the set is now checked individually against the installed
binary rather than assumed from v1's list; nothing shortcuts that check twice in the same place.

**Two known, non-blocking edge cases a final review surfaced, neither reproducible on the happy
path.** `serve` prints one `server listening on http://127.0.0.1:<port>` line to the PTY it
inherits before the visible TUI starts — confirmed live; it's a line of scrollback above the TUI's
own screen, not corruption, and never repeats. And `serve` dying *after* startup (reproduced with a
live `SIGKILL` on it, not a normal path) leaves the visible TUI wedged on a spinner rather than
exiting — the row itself stays sound (`killpg` still reaps the group on close, `detach` still tears
the stream down, a delivered comment still gives up cleanly after its 12 retries), but nothing today
notices a wedged row and surfaces it as an error the way a real turn failure would.

## PR state talks to GitHub directly — no `gh` binary dependency

`PRService` shelled out to the `gh` CLI for everything a branch row shows about its pull
request: state, the merge-queue promotion, the clickable `#<number>` chip. That meant a real
external dependency — resolved off PATH plus Homebrew hints, exactly like an installed
coding agent — that a user had to have installed and authenticated (`gh auth login`) before
any of it worked.

**PRService now makes one GraphQL call per branch to `api.github.com`** (`URLSession`,
blocking calls off the main thread, matching the rest of the codebase's git-subprocess
convention). Nothing is installed or resolved on PATH any more.

**Auth comes from git itself, not a Synth-managed token — with a narrow, deliberate
exception.** `GitService.credential(protocol:host:)` runs `git credential fill` (the same
lookup `git push`/`fetch` use — Keychain via osxkeychain, Git Credential Manager, or `gh`'s
own credential helper if that's configured; `GIT_TERMINAL_PROMPT=0` plus a 5s kill guarantees
it fails quiet rather than blocking on stdin nothing will ever answer). `GH_TOKEN`/
`GITHUB_TOKEN` are checked first. Only if all of that comes up empty does `PRService` fall
back to `gh auth token` — a local keyring read, not a network call, tried only when `gh`
happens to be on PATH. This isn't reintroducing the dependency: everything above still works
with `gh` completely absent. It closes a real gap found while testing this against a real
account: someone who ran `gh auth login` and chose SSH as their git protocol has no HTTPS
credential ever cached for `github.com`, so `git credential fill` alone would leave them with
no PR badges despite being fully authenticated.

**Every read is scoped to one branch, via GraphQL's `headRefName` filter — never a bulk
"list everything" call**, which generalises a fix that used to live only in the archive
sweeper's per-candidate path: a repo-wide list silently drops an old branch's PR off the tail
on a busy repo, reading exactly like "no PR." The first working draft used REST's
`pulls?head=owner:branch` filter instead and shipped a real bug: that filter's `owner` must
name the PR's *head* repo owner, which for a fork PR is the fork's owner, not this repo's —
something Synth doesn't know going in, since finding it out is the point of the call. Caught
by testing against a real cross-fork PR (`cli/cli` #14363, head owned by a contributor, not
`cli`) before it shipped. GraphQL's `pullRequests(headRefName:)` takes a bare branch name and
searches correctly regardless of which fork it lives in — confirmed against the same query
`gh` itself sends (`GH_DEBUG=api gh pr list --head <branch>`). The switch also picked up
GraphQL's `PullRequestState` enum (OPEN/CLOSED/MERGED as three real values, not REST's
open/closed plus a separate `merged_at` heuristic) and lets the merge-queue field
(`mergeQueueEntry`) ride the same request — one call in, not two.

**`GitService.checkedOutBranch(at:)` reads `git worktree list --porcelain`** for the folder in
question rather than trusting the branch name the model last recorded, so a `git checkout` run
by hand inside a worktree doesn't leave a stale badge. Its path comparison resolves symlinks
(`resolvingSymlinksInPath()`, not just `.standardized`) — the same `/tmp`-vs-`/private/tmp`
class of bug this codebase has hit before; caught here because the test fixtures happened to
live under a symlinked temp path and every lookup silently read "detached" until fixed.

**Concurrency, tightened after review caught a thread-explosion risk:** a workspace refresh
resolves its auth token once per repo (not once per branch — `git credential fill` is a
subprocess call, possibly a Keychain round trip) and processes branches in chunks of 6
concurrent lookups (`Store.prRefreshConcurrency`) rather than firing one blocking network call
per branch all at once — a repo with 100+ worktrees (this project's own history records one at
118) must not throw that many blocking calls, and the subprocess/thread overhead that comes
with them, at the OS at once. An early draft used `DispatchSemaphore`/`DispatchGroup.wait()`
inside the async closure to bound this instead; both are flagged unavailable-in-async-context
under Swift 6 and were replaced with chunked `DispatchQueue.concurrentPerform` calls, which
block the calling thread (fine — matches how every git subprocess call in this codebase
already works) without tripping the same warning.

**Tested against real GitHub data, not just fixtures**, via a standalone harness (git-native
functions have no `gh`/AppKit dependency, so `GitService.swift` + `PRService.swift` compile
and run outside the full app): merged fork PR, open same-repo PR, open draft PR with a
stacked (non-default) base, closed-but-unmerged PR, a branch with no PR at all, `https://`/
`git@`/`ssh://` remote forms, non-GitHub remotes, no-`origin` repos, a nonexistent repo (404),
and the credential fallback chain with `git credential fill` deliberately suppressed
(`GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null`). 28/28 checks green. The
merge-queue *promotion* itself is verified only structurally (the exact GraphQL query
confirmed against a live repo, since neither `cli/cli` nor this project's own repo currently
has an active merge queue to observe) — worth a real check against a queued PR before fully
trusting that one path.

**Known regression, stated plainly:** GitHub Enterprise / any non-`github.com` host is no
longer recognised — `gh` could point at an Enterprise instance; the direct client is hardcoded
to `api.github.com`. Not something Synth exercised or was asked to preserve; noted so the gap
is a decision, not a silent loss.

**Not exercised by this change:** the full native app can't be built in every environment
this was worked in (a vendored `GhosttyKit.xcframework` archive can be absent, which fails
only the final link step, after every file — including these — has already compiled clean),
so the real `PRChip`/sidebar-badge UI and the `t9_archive` control-socket harness were not
driven end to end here. The service-level behavior they'd exercise is what the standalone
harness above covers instead.

`PRService.ghPath`, and the bulk `pullRequests(at:) -> [String: PRInfo]?` dictionary read, are
both gone. `Store.refreshPullRequests` fans its per-workspace call out per branch instead;
`ArchiveSweeper.relevance` keeps its own per-candidate call, just against the renamed
signature (`pullRequest(branch:at:)`, was `pullRequest(head:at:)`).
