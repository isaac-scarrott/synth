# 2026-09-06

## The conditions bar gains Theme, a fourth axis for what colour scheme the page sees

A page inside Synth's browser has always answered `prefers-color-scheme` off whatever the raw OS
appearance is — not Synth's own. Pin Synth to Light on a Mac set to Dark and every page it hosts
still rendered dark, because nothing told the embedded engine Synth had an opinion of its own.
That's backwards: the one setting a person actually made (Synth's theme, in Settings) should be
the one pages see, with System staying exactly what it already means — no opinion, so the OS
decides.

**Normal now means "follow Synth", not "follow the Mac".** With Theme at Normal, the page's colour
scheme tracks Synth's own — dark app, dark page — and only when Synth itself is set to System does
the OS's raw `prefers-color-scheme` show through, because that's what System is for. Nothing about
the plain page mock actually changed for this: it already read the app's `data-theme`, not a media
query of its own; what changed is stating the rule as the axis's actual meaning, so it stops being
an accident of how the mock happens to be styled and becomes something the real embedded engine
(CEF) has to be told to do explicitly.

**Light and Dark force it, and it's this browser's alone.** The fourth pick sits right after CPU —
Screen, Network, CPU, Theme, the same "what does this axis claim, at Normal" shape as the other
three. Forcing either one flips the page's surface and every skeleton on it regardless of what
Synth or any other browser is doing: the override lives as `data-page-theme` on this browser's own
pane, not on `:root`, so it can win against the app theme (or lose to it, at Normal) without ever
touching it. A device frame keeps its own OS chrome exactly as before — a phone's status bar and
Safari pill stay lit, because a phone has its own appearance setting too — only the page inside it
forces. Opening Conditions still rests all four at Normal, and closing it puts all four back, same
as the other three: a forced colour scheme nobody can see is the same bug report as a throttle
nobody can see.

`THEMES` joins `NETS`/`CPUS` with the identical `{id, name, cap}` shape, `condTheme` rides beside
`condNet`/`condCpu` in the browser's own closure (so it's already per-browser state, no extra
plumbing), and `[data-page-theme]` carries the override at whatever specificity beats both the app
theme's `:root[data-theme]` rules and the "a device stays lit" rule guarding `.dev__screen .skel`.

## Theme's native port: `Emulation.setEmulatedMedia`, and the repaint it doesn't force

The design above ported onto real CDP: `PageTheme` (`DeviceMode.swift`) joins `NetworkCondition`/
`CPUThrottle` as the fourth axis, `BrowserSessionController.pageTheme` rides outside
`conditionsOn` exactly as the mock's `condTheme` does (Normal still has to reach the page with
Conditions shut, so `DeviceEmulator`'s socket now outlives the bar closing — closing used to
close it too, on the theory that nothing else needed it), and `Emulation.setEmulatedMedia`
carries the forced scheme, resolved from `store.colorSchemeOverride` at `.app` exactly like the
mock resolves `data-theme`.

The one thing the mock never had to answer: a colour-scheme-only CDP change schedules a repaint
on CEF 144's own compositor clock rather than forcing one, and a browser pane that isn't the one
someone's looking at can sit on the old colour indefinitely — reproduced by closing Conditions
right after forcing a theme, confirmed stale seconds later with nothing else touching the page,
fixed only by a real navigation. A device-metrics change, by contrast, is a real viewport
transition Chromium always lays out and paints for, so `applyPageTheme()` piggybacks on one:
re-asserts the real screen override when a device is active (measured: a bare re-send repaints
correctly; clearing the override and setting it fresh — the obvious way to "reset then reapply"
— is the one order that doesn't, reverting to the frame from just before the colour change once
Network has been enabled), or sends a throwaway 1×1 override-and-clear (`nudgeRepaint`) when no
screen override is meant to be active.

That nudge turned out not to be reliable *once*, either — measured stuck for 25+ seconds after a
single attempt (never self-correcting; only a second, independent nudge minutes later un-stuck
it), most easily reproduced as the very first thing a session ever does, when the nudge lands in
the same burst as Network being enabled for the first time. `applyPageTheme()` now retries: up to
four attempts over ~1.8s (`kickPageTheme`), each re-reading `pageTheme`/`store` fresh rather than
a value captured at the first attempt, and a nonce lets a newer call (a different pick, Conditions
closing) simply supersede a stale retry instead of fighting it. Verified over repeated stress
cycles (rapid dark/light toggling, screen+theme set together in one `browser.deviceMode` call,
first-ever action on a fresh session) with no remaining failures. `browser.deviceMode` gains
`theme` alongside `network`/`cpu`, read and set the same way.
