Seven changelog lines, drawn from the eighteen ledger entries above this one. The site rebuild,

## 0.41.1 — an OpenCode 2 row opens quiet, quick, and once

A patch release of three fixes, two of them found from a single screenshot of a launch: an
OpenCode 2 row with its own server's log lines printed across the TUI, and `1 MCP failed` in the
status line.

**The log lines were the server writing onto the row's terminal.** v2 splits `serve` out of the
TUI, so `synth-hook` starts it behind the visible process — and started it with no file actions, so
it inherited the shim's own stdin/stdout/stderr, which are the row's PTY. `serve` prints
`server listening on …` at startup and a `spawning process { command: node, … }` line every time
its MCP subsystem starts a local server; all of it landed mid-frame on top of the TUI drawing on
the same terminal. All three streams now go to /dev/null. stdin too, which was the quieter half of
the same bug: the server was sitting on the other end of the keyboard the TUI reads.

**Registering the MCP servers was holding the row closed for someone else's timeout.** A
`PUT /api/mcp/<name>` connects its own server within a fraction of a second, but only *responds*
once the whole MCP set has re-initialised — which is paced by the slowest entry in the user's own
opencode config (~9s here, behind an unreachable remote). Sent one after another under a 3s cap,
every registration past the first timed out (`http.status=499` in opencode's log) and reported
failure for work the server went on to finish, which is indistinguishable from one that never
landed. They now go together, with a short grace window for the answer worth having: a rejected
registration comes back immediately, and `--fail` makes that a non-zero exit rather than the silent
success the old call read it as — it had no `--fail`, so an HTTP 400 had always counted as success.
3.7s to a visible TUI, against 6.7s before and 11.2s for the version that waited the responses out.

**A custom agent that duplicated a built-in's command was offered twice.** Settings had said so on
the row since custom agents shipped ("OpenCode 2 is already one of Synth's agents"), but the
warning was only words — the descriptor still reached `AgentRegistry.all`, so ⌘K carried two of
every "New OpenCode 2" and both started the same binary. `AgentRegistry.clashOwner` is now the one
rule behind both the sentence and the exclusion, and a clashing agent stays in Settings, where the
row explains itself, and out of everywhere that offers it.

Two gates, each confirmed to fail against the pre-fix binaries before being kept: `t36` runs the
shim through a real launch and greps the row's own stdout (the PTY content is not something the
control socket can hand back, so this one drives the shim rather than a Synth row), and `t35` seeds
a clashing custom agent and reads the palette. `t34` still passes whole, its live MCP registration
check included. `t28_alias_agent` check 9 fails on this machine and fails identically on an
unmodified tree — pre-existing, not this work.

`CFBundleVersion` 715, tag `v0.41.1`. Both artifacts notarized separately and stapled, then verified
with no credentials and quarantine set: dmg `accepted / source=Notarized Developer ID`, the app
inside it assessing on its own, same for the zip Sparkle fetches. Appcast newest 0.41.1 at 715,
`edSignature` on all 18 enclosures, 5 deltas at 0.8–1.6 MB against a 164 MB full download. No
`synth-site` push — nothing under `site/` changed since 0.41.0.

The `1 MCP failed` in the same screenshot was not Synth's: a `paper` entry in the user's own
`~/.config/opencode/opencode.json` pointing at `http://127.0.0.1:29979/mcp` with nothing listening.
Worth writing down only because it arrived in the same picture as two real bugs, and the log was
what separated them.

## opencode's pane stops drawing its own edges

A Claude Code row is one surface from the pane's border to its text: ghostty fills the cells and the
23×19pt `window-padding` band around them with `TerminalTheme`'s translucent surface, and the agent
paints ink on top of it. opencode did not. It painted every cell of its own field — `#ffffff` in
light, `#0a0a0a` in dark — so the padding band read as a frame around a rectangle of a different
colour, and an opaque one: the pane also sat out the window translucency every neighbour had. Both
versions did it, and one file fixes both, because v1 and v2 read the same `themes/synth.json`.

The theme hands `background` back to the terminal. opencode documents `"none"` for exactly this —
blend with the terminal's colour scheme — and it works, but not on its own: opencode also *derives*
surfaces from that value, and `"none"` resolves to a zero-alpha black. Measured, that drove the
splash mark's shadow from `#dbdbdb` to `#1c1c1c` in light — two near-black slabs under the wordmark,
which no contrast gate would have caught because they are fills rather than ink. `#f7f8fa00` and
`#12131700` say both things at once: paint nothing, and here is what you are sitting on. 92.8% of a
splash screen now comes back as the terminal's own default in both appearances and both versions;
the remaining 6.7% is opencode's prompt box, which it is entitled to paint, and the derived shadow
lands on `#d5d6d7`. Ink is still judged against that box (`#f5f5f5`), which stays the least forgiving
light surface — the terminal's is lighter.

Those two values are `TerminalTheme`'s own, quoted a second time in a JSON file no Swift reads back.
`t25` parses both out of their files and fails if they drift apart, which is the only thing keeping
the copy honest.

**v2 names its theme somewhere else**, and that closes the gap 2026-09-06 left open — "the
light-theme correction doesn't carry over", concluded from a v2 launched against Synth's theme file
rendering identically to one launched without it. The theme *file* was never the problem: v2 reads
`themes/synth.json` out of the same directory v1 does, and renders it — measured here on both
binaries, whose splash screens come back cell-for-cell identical. What it does not read is
`tui.json`. v2 names its theme in `cli.json` as `theme.name`, and migrates `tui.json` into it exactly
once, only when `cli.json` does not yet exist. A v2 that has already run has a `cli.json` Synth
never wrote to, which is why the file looked ignored.

So Synth claims `theme.name` there too, under v1's rule: adopt nothing-set, `opencode`, `system` or
`synth`, and leave catppuccin or gruvbox alone. `theme.mode` is not touched — it is v2's own
appearance following, and it already works. Unlike `tui.json`, an absent `cli.json` is left absent:
creating it would satisfy the migration's existence check and silently drop every v1 TUI preference
the user had, and waiting costs nothing, because the migration carries `tui.json`'s theme across as
`theme.name` by itself.

`t25` now renders opencode2 as well as opencode and asserts the field in both appearances for both;
the dark-half drift check exempts `background` by name, since it is no longer opencode's to choose.
Nothing in `working.html` changed: the design has always drawn the terminal as one surface, and this
is the app catching up to it.
## Three gates that kept every worktree forever

The sweeper had been archiving correctly and reclaiming almost nothing: 132 of 140 rows archived on
the author's machine, 51 of them still holding a folder, and only four of those clearing the gate
chain. The gates were not being cautious — three of them were wrong, and each was wrong permanently
rather than for a while, which is the difference between a folder that waits and a folder that can
never be reclaimed.

**A generated `.env` is not an original.** `matchesParent` cleared an ignored file only when it
byte-matched the parent checkout's copy. Worktree-create in this repo copies them, so that held —
but a project whose setup script *stamps* `.env.development` out of a committed
`.env.development.demo` produces a file matching no parent copy and never will. Every one of that
project's 45 worktrees read as "local-only config inside — kept", forever. The rule now also accepts
a file whose bytes are already a committed blob in its own directory: the template it came from is
in the object store and on the remote, so the folder holds nothing.

**A fetched dependency is not a nested repo.** `hasNestedRepo` looked four levels down for a `.git`,
skipping only `.git` and `node_modules`. A built SwiftPM package keeps its dependencies as real
clones under `app/.build/checkouts/` — a `.git` at exactly depth four — so every Synth worktree that
had ever been built was `nested` for good. The walk now skips what git ignores, taken from the same
`ls-files --others --ignored --directory` answer B10 already needed. A repo that ignores a path has
declared what is under it disposable; a `.git` down there is an artefact, not work.

**Shape is not ownership.** `removeStrandedConfigs` deletes the `.mcp.json` / `opencode.json` an
older build wrote into every managed worktree, and decided a file was Synth's by its JSON shape.
Holibob has both checked in. So the migration deleted tracked files, leaving ` D opencode.json` in
worktrees that were otherwise clean — which the sweeper then read, correctly, as work in progress
and kept. Synth's own upgrade had been making worktrees unreclaimable. A file git tracks is now
never removed, whatever it contains.

Found by replaying the gate chain over the author's own 132 archived rows rather than by reasoning
about it: 11 kept on the `.env`, 8 on uncommitted changes (4 of those Synth's own deletions), and
the 4 that passed everything else all blocked on `.build/checkouts`. `t9_archive` gains three
scenarios — a nested repo under an ignored path and an `.env` copied from a committed template, both
reclaimable; an `.env` holding something that exists nowhere else, still kept — and drives ticks
until the reclaimable set is through, since `perTickCap` is three. `t4a_mcpconfig` plants a
committed config alongside its untracked ones and asserts it is neither rewritten nor deleted.

Left alone deliberately: the bulk brake. Five eligible folders at once and the tick does nothing at
all and raises a card, so a backlog past five can only ever be cleared by hand — which is its own
decision to make, not a bug in a gate.

## The branch is the last thing to go

The archive path ended one step short. A row was archived, its folder held, then reaped — and its
branch ref stayed behind for good, with the row still in the Archived list pointing at it. Settings
even promised this ("the git branch is never deleted"), which is defensible for a folder that might
still be wanted and indefensible for a branch nothing can reach. On the author's machine: 443 local
branches in one repo, 258 merged, 220 with no checkout, **200 of those already deleted on the
remote**; 180 and 155 in the other. 322 were deleted by hand before the code was written, which is
how the shape of the rule was found rather than guessed.

**The gate is the remote, not "merged".** A merged branch the remote still lists is one somebody is
keeping — a release branch, a base someone forks from. A merged branch the remote has *dropped* was
cleaned up when its PR landed, and every commit on it is reachable from the default branch. That is
the entire claim, and it is why this needs no grace of its own: the folder already served one, and
there is nothing left here to change its mind about. `git branch -d`, never `-D`, so git's own
merged-into-HEAD check sits on top as a free second opinion; a ref it refuses is one worth keeping.

**A row whose branch has gone is dropped, not kept.** `restoreArchivedBranch` re-cuts the checkout
from the ref, so the ref is what makes an Archived row restorable. Retiring it and leaving the row
would leave an entry that can never come back. So `ArchiveSweeper.branchEnd` answers with three
states, not two: `retire` (delete the ref, drop the row), `orphaned` (the ref is already gone —
deleted by hand or by another tool — so there is nothing to delete and the row is a pointer to
nothing), `keep`. The hand cleanup above created 67 orphans on this machine in one afternoon, which
is the case arriving before the code that handles it.

Its own switch in Settings, on by default, worded to say what makes it safe rather than hidden
inside the sentence above it — the parent row's promise that branches are never deleted is gone,
because it is no longer true.

The cap counts rows *looked at*, not rows ended, and the cheap rejections come first: an archived
row that still has a folder is thrown out by a `stat` with no git at all. A settled archive costs
the pass nothing per tick; a backlog drains twenty git chains a tick instead of running hundreds
every time. That ordering was not a nicety — the first version walked every archived row through
five git calls on every tick, which made a tick long enough that `sweepInFlight` began coalescing
the suite's own forced sweeps away, and eight checks failed for a reason that had nothing to do with
what they were testing. `sweep_until` in `t9` now drives ticks until the state it wants, rather than
assuming a fixed number of calls each land as a tick.

`t9_archive` gains both endings: `remote-gone` (merged, pushed, then deleted on origin — ref and row
must both go) and `ref-gone` (its ref removed by hand once archived — the row must go on its own),
with `merged-gone` as the negative that makes the remote the load-bearing gate: same shape in every
other respect, origin still lists it, ref and row both stay. Plus the invariant that a row archived
on a tick is never held on that same tick.
## An OpenCode 2 row can be stopped without being lost, and says when it is asking

Two reports about the same rows: the status marks never move ("when it's working, when it needs a
question"), and OpenCode 2 "keeps on quitting randomly". They turned out to be three separate
faults, each one a thing v1's supervisor already gets right that v2's never carried over.

**ctrl+c was bound to quitting the agent.** v2 ships `app.exit` on `ctrl+c,ctrl+d,<leader>q` and
`session.interrupt` on `escape` alone — the same defaults v1 has, and the same reason
`OpencodeSupervisor` rebinds them. Driven against a real TUI, ^C exits in under a second with no
confirmation, idle and mid-turn alike, and exits *0*: a clean exit, which to Synth is a row that
finished, so it parks on a Reopen card exactly as a deliberate quit does. Nothing random about it —
it is the gesture Claude Code users press to stop a turn, landing on the one agent that reads it as
"close everything".

The fix could not be v1's. v1 writes an overlay and names it with `OPENCODE_TUI_CONFIG`, so it never
touches the user's own file; v2 deleted that variable and shipped no replacement.
`OPENCODE_CONFIG_DIR` moves the whole directory, and a shadow copy of it would quietly swallow the
TUI's writes to `cli.json` — which opencode2 rewrites on every preference toggle, so a theme or
sidebar change made inside a Synth row would evaporate. So the binding is claimed in `cli.json`
itself, the way `OpencodeTheme` already claims `theme` in its sibling file: only where the binding
is still opencode2's own default (or already ours), preserving every other key, refusing outright
on a file it cannot parse, and restoring the 0600 an atomic replace would have widened. A binding
someone chose is one they meant.

**Every question the agent asked was dropped on the floor.** `form.created` — v2's question
surface, the generalisation of v1's `question.*` — nests its payload as `{form: {sessionID, …}}`,
where all fifteen of its siblings put `sessionID` at the top of `data`. Read on the flat shape it
carries no id at all, so the row-matching guard rejected it and the `?` never lit. What made this
invisible to review is that the *reply* and *cancel* events are flat: only the ask is nested, so
half the pair matched and the half that mattered did not. `permission.asked` was never affected,
which is why a permission prompt did light the row and a question did not — the difference nobody
could see from the outside. Now confirmed live in both directions, including a permission answered
at the TUI's own keyboard: working → needs-input → working → idle.

**A server that died left nothing behind.** 0.41.1 sent `serve`'s streams to /dev/null to stop it
printing across the row's terminal. Off the terminal is not the same as nowhere: the TUI outlives
its server (verified — it spins on "event stream connecting" indefinitely rather than exiting), so
a dead server is a permanently hung row with no record of why. stdout and stderr now go to a
per-row file under `/tmp/synth-oc2-<pid>`, reaped with every other per-pid directory. And
`OPENCODE_DISABLE_AUTOUPDATE`, which v1 and Antigravity both set and v2 omitted — an embedded agent
must not replace its own binary mid-session.

Claiming a key in that file has one trap, found before it shipped rather than after: opencode2
folds v1's `tui.json` (and its `kv.json`) into `cli.json` exactly once, and only while `cli.json`
does not yet exist. Writing the file first cancels that silently, and a v1 user's very first v2 row
would come up having lost their theme and every preference with it. So where the migration is
still owed, adoption waits — verified by removing `cli.json` on a machine that has both: the row
went live, opencode2 wrote the file itself with `theme: {name: synth}` carried across, and the
next launch claimed the binding inside it with the theme still there.

That trap was found twice independently — the theme claim landing on main the same day states it
in its own words — so the rule is now written once, as `OpencodeTheme.mayCreateCLIConfig`, and both
claims ask it. Merging also settled which version of it to keep. "Never create the file" is safe
but permanent: on a machine that never ran v1 there is no migration owed and no other reason for
v2 to write `cli.json` until the user changes a preference in it, so a fresh install would wait
forever — for the theme, and for a stop gesture that is not cosmetic. The rule kept defers only
while `tui.json` or `kv.json` is actually standing.

Three gates, each confirmed to fail against the pre-fix build before being kept. `t37` reads the
two bindings back out of `cli.json`, raises a real form on the row's own server mid-turn and waits
for the row's mark to change, then drives the shim through a real launch and writes a bare `\x03`
into its pty (the row's pty is not something the control socket reaches, the same reason `t36`
drives the shim). `t36` gains a fourth check: the server's startup line is absent from the terminal
*and* present in its log. `t34` still passes whole.

**The gate could not be trusted until the harness was.** The first full run came back 31 passed /
10 failed, and most of that was the harness fighting itself: another checkout was running the same
suites at the same time, and `kill_all`'s agent patterns are path-independent of necessity — a
row's `opencode2 serve --port <port>` carries nothing that says whose row it is — so each run
reaped the other's agents mid-test. Its own docstring already warns against exactly this for the
app ("never match on a bare `Synth.app/...` pattern"); the agent lines could not take that advice,
and nothing else stood in for it. `claim_machine` now holds `/tmp/synth-agent-gate.lock`, owned by
`run.sh`'s pid so every suite in one run inherits it, and a foreign run prints one `SKIP:` line and
stops — counted apart from passes, so it can never read as green. Confirmed both ways: turned away
while a live owner holds it, taken over once that owner is gone.

Re-run on a quiet machine, the three opencode2 suites pass whole (18, 4 and 10 checks), as do
`t1`, `t2`, `t5`, `t6`, `t17`, `t19`, `t25` and `t35` — 11 of 11. Eight suites still fail:
`t3`, `t4b`, `t4c`, `t7`, `t10`, `t11`, `t28` and `t30`. All eight were run again against an
unmodified tree, rebuilt from `git checkout` of the three changed sources, and failed identically,
check for check — pre-existing on this branch, not this work. (`t28` check 9 was already recorded
as pre-existing at 0.41.1.) `t4c` and `t7` are the same fault twice: the Claude row reaches its
trust prompt and never goes live, while the opencode and `agy` rows beside it pass every check.

Left alone deliberately: `session.updated`, which the supervisor still matches and which this build
never emits — kept as the forward-compatible half of a pair whose other half is load-bearing. And
compaction, which has its own events (`session.compaction.started`/`ended`) that were not observed
outside an execution this build already reports; mapping them would be a guess, and this file's
comments are a record of what was watched happen.

## The site gains documentation, and two of its pages are read out of the source

Ten pages under `site/docs/`, built from `site/docs-src/` by `site/build_docs.py`. The landing
page argues; these explain. The split is deliberate: the argument stops at the download button,
and a reader past that point wants to be told things rather than sold them.

**Scope.** A spine of eight written pages plus two generated references: Start here, How Synth is
organised, Branches and worktrees, Sessions, Agents, Knowing who needs you, Configuration,
Troubleshooting, and then the keyboard reference and the agent tool catalogue. No recipes layer
and no per-agent pages yet. The research behind the shape (28 competitor and craft-benchmark docs
sites, read in three rounds) found the peer set's median at 16 to 57 pages, but also found that
nobody in it ships a complete keyboard reference or documents a bundled first-party tool surface
at all. Those two were the open ground, so they are in the first landing and the how-to layer is
not.

**A generator, and why the no-build rule bent.** `site/index.html` is still one self-contained
file with no build step. Docs is not, because ten pages sharing a hand-copied style block is two
sources of truth again, and `landing/` was deleted this month for exactly that. So the build
reads `index.html`'s own `<style>` element and inlines it whole into every docs page, then
appends `docs.css`. The landing page stays the one place tokens and components are defined, and
there is no sync step to forget. The style block is located by exact tag and asserted to be
unique rather than matched with a regex, because this file contains prose about HTML.

**Two references that cannot go stale.** The keyboard page is read out of `Shortcuts.swift`, the
same source the in-app `⌘?` sheet renders: 57 bindings in 8 groups. The tool catalogue is read
out of the three MCP servers: 42 tools. Both fail the build rather than drifting, and
`build_docs.py --check` is the pre-deploy guard.

Writing those parsers found a real defect in the first attempt, and it is the ledger's own
recurring one. `Shortcut(keys: ["⌘", "]"], label: "Forward")` was silently dropped, because a
`[^\]]*` capture for the key array stops at the bracket *inside the string*. The page shipped one
binding short and said nothing. Both parsers now scan with quote and depth tracking instead of
matching. The same class of fix resolves shared zod parameters: `ref` and `selector` are
`const`s declared once with `.optional()` on them, so reading optionality from the call site alone
reported every element-addressing tool as requiring both.

**The vocabulary page is the one that had to exist.** Synth hosts three agents it did not write,
and all three use Synth's own nouns for different things. Claude Code says *worktree* for the
folder and keeps *branch* for the ref; Antigravity's `/branch` copies a conversation and touches
no files; every one of them means "a conversation with the model" by *session*, and "a persona
inside this program" by *agent*; Antigravity's *project* groups chat history and has no relation
to a repository. `concepts.html` carries that as a table, under one rule: Synth's words describe
what is on your disk, the agent's words describe what is in its conversation. Only one word is
shared cleanly, and it is shared on purpose. *Needs input* means in Synth exactly what it means in
Claude Code's own agent view.

**What the pages say that competitors' do not.** A sweep of Hacker News threads and the issue
trackers of cmux, Orca and Supacode put the same complaints at the top every time, none of them
about documentation navigation: worktrees are not the isolation people expect, two agents fight
over one port, and nobody can tell whether a given setting belongs to the wrapper or to the tool
inside it. So `branches.html` states plainly what a fresh worktree does not contain and gives the
setup script that fixes it, carries a worked example of deriving a port from the branch name, and
warns about the shared development database before anyone hits it. `configuration.html` opens with
a table answering "which file is this", and lists the three files Synth writes beside your agents'
own. `agents.html` says in one sentence that agents run unsandboxed on your machine as you, which
is the honest mirror of the badge Codex and Devin put on their own most permissive mode.

**The in-page editor follows.** `devserver.py` serves docs pages with `dev-edit.js` injected like
the landing page, but a save is routed to the *fragment* under `docs-src/`, never to the generated
page, and rebuilds in-process before the reload lands. Writing to the built page would have looked
like it worked right up until the next build. `dev-edit.js` gained one field, `page`, which is
what makes the routing possible.

**Not done, and deliberately.** The docs shell has been validated structurally (links, anchors,
images and tag balance all check) but not measured in a real browser, because Synth was not
running and the browser MCP needs it. No `llms.txt` yet: the audit found 11 of 19 comparable
sites serve one and only Warp has the full copy-as-markdown set, so it is a known gap rather than
an oversight. Nothing is deployed to `synth-site`.

## The docs get measured, and four defects fall out

The entry above shipped with "not measured in a browser" as a known gap, because Synth was not
running and the browser MCP needs it. Two comments arrived from the page and closed that gap by
opening it: with a live Synth the pages could be driven and read with `getComputedStyle` and
`getBoundingClientRect` at 390, 860, 861, 900, 1180 and 1440.

**Both reported problems were real, and neither was what it looked like.** The callouts wore a
coloured left edge per kind, taken from the app's status hues. Wrong twice: those hues mean
something specific in the app, where blue is "needs you", and an aside in a docs page is not
asking for anything, so the colour claimed an urgency the content did not have. One hairline box
now. And the selected sidebar row was clipped on its left, not because of padding but because
`.dnav` carries `overflow-y` for short viewports, which forces `overflow-x` to `auto` rather than
leaving it `visible`; the container clipped at its own edge while the row was pulled 8px past it
to bleed its fill. Measured: row left 52 against a clip edge of 60. The scroll box carries that
8px as padding now and takes it back as a negative margin.

**Two more the sweep found that nobody had reported.** The reading measure got *wider* as the
window got narrower: crossing 860 the sidebar leaves and the mobile rule dropped the cap
outright, so the line went 535px to 774px, past the 685px the design tops out at on a desktop.
That is the headline bug of 2026-09-06 in another place, one rule answering a question it was not
asked. And the three-column vocabulary table shrank to fit instead of scrolling, reaching 69px
columns and rows fourteen lines deep at 390px; `.scroller` existed for exactly this and had no
floor to scroll against.

**Then the deploy question found the worst one.** An inlined `@font-face` resolves `url()` against
the document rather than against the file the CSS was written in, so every docs page asked for
`/docs/fonts/Geist-Variable.woff2` and got a 404. Ten pages had been rendering in the system
fallback since the first build, including in the screenshots that came back with the comments on
them. Nothing said so, because a missing font is invisible unless you go looking: the page still
renders, just not as the design. The build rewrites relative `url()` in the borrowed stylesheet
now, and refuses to build when an asset it names is absent from `site/`. Proven by measuring a
test string against Geist and against the system stack rather than by looking at it.

## The docs are legible to an agent as well as to a person

`llms.txt`, `llms-full.txt`, and a `.md` twin of every page, all generated from the same fragments
as the HTML. An audit of nineteen comparable sites put a real `llms.txt` on eleven of them and the
full copy-as-markdown set on one, so this is the floor for a product that calls itself AI-first
rather than a flourish.

The twins are converted from the fragments rather than written again, which is the only version of
this that stays true. Three things the conversion had to get right, each found by reading the
output: a chord is one code span (`⌘K`) but two alternative keys are two (`` `J` `K` ``), and the
only signal separating them is that a chord opens with a modifier; two of the bindings are
`` ⌘` `` and `` ⌘⇧` ``, where the key *is* a backtick and closes its own span, so those take a
longer fence; and the generated tool table's argument line is a block element inside a cell, which
concatenated onto the tool name without a separator.

`.nojekyll` ships with them. GitHub Pages runs Jekyll by default and would render the `.md` twins
into HTML rather than serving the markdown that was asked for.

## The docs were written against a tree 48 commits old

Caught at the deploy, not before it: `add-docs-to-site` branched at `c95d0d5` and `main` had moved
on through 0.41.0 and 0.41.1 while these pages were being written. Six things the docs asserted
were no longer true, and one of them was a safety claim.

The worst was the archive. The pages said the git branch is never deleted, so there is no state a
branch cannot come back from. **The branch is the last thing to go** changed that: once the folder
is reclaimed, the work is merged into the default branch and the remote has dropped the branch,
`ArchiveSweeper.branchEnd` retires the ref and the row goes with it. That is still safe, and the
docs now say why rather than promising something else: the deletion is `git branch -d`, which
refuses anything unmerged, and it has its own switch. A page that overpromises about data is worse
than a page that says nothing.

The other five: PR state is read from GitHub's API rather than the `gh` binary, so the
troubleshooting answer was pointing at the wrong thing entirely; OpenCode 2 is a fourth hosted
agent; the browser's conditions bar has four menus, not three; Settings lost its Experimental
drawer and its Markdown chooser, gained **Integrations**, and moved analytics into About; and Tabs
is no longer an experiment you switch on but one half of **Show sessions in**, which is a choice of
where and never an on or off. The Usage board is now named on the attention page, since a board of
every agent's remaining limits belongs with the rest of what you read at a glance.

**The two generated pages needed no edit at all.** 57 bindings and 42 tools, unchanged across
48 commits of product work, verified rather than assumed by regenerating them against the merged
tree. That is the whole argument for generating a reference: the pages that could go stale did, and
the pages read from source could not.

The lesson worth keeping is about the sequence rather than the content. Writing documentation on a
long-lived branch means writing against a snapshot, and prose has no compiler. Merge first and
regenerate before any deploy, and treat "is this still true" as a build step rather than a memory.

## One nav, one column, and the shift that came from having two

Reported from the page: the gap between Docs and the download button was too tight, the bar
should be the same component on the root and under `/docs`, and it shifted as you crossed
between them. All three were the same problem seen from different sides.

The bar was written twice. The landing page's had a `.nav__link`; the docs shell had a
hand-written header with a `.brand__docs` breadcrumb instead, a different height, and a different
column width. It resembled the original closely enough to look intentional and differed in three
measurable ways, which is exactly what a component written twice does.

`build_docs.py` now borrows `index.html`'s `<header>` the way it already borrows the `<style>`
block, rewriting only the relative URLs, so there is one definition. Two rules cover what the
docs bar needs and the landing bar does not: it is solid from the first pixel, since docs has no
hero for a bare bar to sit over, and the download's spark canvas is hidden, since the script that
draws it is not loaded here.

The shift measured 84px sideways and 8px down. Both came from overrides the docs stylesheet had
no good reason to hold: a 56px bar against the landing page's 64px, and a 1320px wrap against
`--col`'s 1152px. The wider column had been justified as "three columns need more room than one
argument does", which was true and worth less than the cost. Deleting both overrides fixes the
shift, and the content column that falls out is **644px, measured at 68 characters per line** —
the open design note from earlier today, which had the measure at 685px and about 80 characters,
closed as a side effect rather than as its own change.

The gap between the link and the button goes from 16px to 48px, one further step off the scale on
top of the row's own gap, and back to 16px below 560px where the bar is justified apart and every
pixel is measure.

One note on method. The first attempt to measure the shift mounted the other page in an iframe
and reported a 0.75px difference in the link's height. That was the harness, not the page: an
iframe written with `document.write` inherits the parent's base URL, so the landing page's
`url("fonts/…")` resolved against `/docs/` and 404'd, the text fell back to a system face, and
`line-height: normal` resolved differently. The measurement reproduced this morning's font bug
instead of finding a new one. Navigating to each page and comparing gives 0.00px on every box.

## The pane entrance runs once per session, not on every tab flip

Clicking between tabs made the browser flash. Measured on a driven build, one click of the strip
cost a fully blank pane for a frame — no page, no toolbar, nothing but the card — followed by a
220ms fade up to the page: sixteen repaints of the whole pane per switch. With a browser open
beside an agent, which is the layout the product exists for, that is a flash on every click.

The entrance itself is right and stays: working.html's `pane-in`, 220ms fade plus a 4px rise, is
what a pane appearing should look like. The bug is that a tab switch counts as an appearance.
The content leaf is keyed by session id, so selecting another session tears the pane view down
and builds a new one — and the new one starts at opacity 0 over a surface that never went
anywhere. A terminal survives this because its glyphs fade back in over the same dark field; a
browser is a full-bleed page, so the whole pane blinks.

So a pane's entrance now belongs to the session's *first* appearance in the window. `PaneEntrance`
remembers the ids it has shown; the second and every later appearance skips straight to opacity 1.
Opening a session, splitting one off, restoring a layout — all still enter. Flipping back to
something already open is instant, which is what it always looked like it should be.

The same rule went into `working.html` (`.pane--noenter`, set by `renderPane` off a `WeakSet` of
sessions already rendered), because the mock recreates the pane element on every render and so had
exactly the same replay.

Measured after: a switch is one frame, page to page, no blank in between — 257 units of mean-colour
change in a single step where before it went page → 242,243,243 → fifteen fade steps → page.
