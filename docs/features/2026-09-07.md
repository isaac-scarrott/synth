# 2026-09-07

## 0.41.0 ships — Usage, OpenCode 2, and Settings reorganised

The release carrying everything landed since 0.40.0. Three things a person opens the app and sees:
Usage is a board above the project tree showing every hosted agent's limits side by side; OpenCode 2
is a fourth agent you can start a session with; and Settings has lost the "Experimental" drawer that
grouped rows by maturity rather than by what they do, so every row now sits where you would look for
it and every project scope is a tab. The browser's conditions bar gained Theme, PR badges stopped
needing the `gh` binary installed, and the champagne accent lost its yellow.

Seven changelog lines, drawn from the eighteen ledger entries above this one. The site rebuild,
`landing/`'s deletion, the `working.html` collapse and the spacing audit are all in the ledger but
not in the changelog: they change the marketing page and the repo, not the app a person is running.

`CFBundleVersion` 708, tag `v0.41.0`. Both artifacts notarized in separate submissions and stapled;
verified afterwards with no credentials and quarantine set, the way a browser download arrives. The
dmg assessed `accepted / source=Notarized Developer ID`, and so did the app *inside* it on its own —
that is the check that matters, because a dragged-out copy carries no trace of the image it came
from. Same for the zip Sparkle fetches. Appcast newest is 0.41.0 at 708, `edSignature` present on
all 18 enclosures, deltas from 641–663 at 1.4–1.6 MB against a 164 MB full download. No `synth-site`
push: the deployed page already matched `site/index.html`, and the Download buttons point at the
bucket's stable `Synth.dmg` alias, which the release replaced in place.

**Two failed attempts first.** Apple's notary service was unreachable — `notarytool` died at
"initiating connection" with `NSURLErrorDomain -1001 "The request timed out."` against
`appstoreconnect.apple.com/notary/v2/asp`, twice, before uploading a byte. Nothing shipped either
time; the guards held and the bucket kept serving 0.40.0/663. What separated "Apple is down" from
"our credentials are broken" was reaching the endpoint by hand: it answered `401` in 0.3s (correct
for an unauthenticated request) and `notarytool history --keychain-profile synth-notary` returned
the profile's real submission history. Service up, credentials good, so the third attempt was just a
retry rather than a fix — and it passed.

Worth keeping: `./release.sh` was run unpiped with `; echo "RELEASE_EXIT=$?"` appended, and that is
the only reason the first two failures were visible at all. Both ran in the background, and the
*harness* reported each as "completed (exit code 0)" — the exit status of the trailing `echo`, not
of the release. The log said `RELEASE_EXIT=1`. A run that reads as shipped when nothing did is the
exact failure the skill's no-piping rule exists to prevent; backgrounding reintroduces it through a
different door unless the script's own status is printed.

**Known cosmetic mismatch:** `CHANGELOG.json` stamps 0.41.0 as `2026-09-06`, the day the work landed
and the file was written; publication crossed midnight and the appcast's `pubDate` reads
`Mon, 07 Sep 2026 00:08:20 +0100`. Left as-is deliberately — the date is baked into the shipped
bundle, and editing the file now would make the repo disagree with what every user is running.

## 0.41.1 — an OpenCode 2 row opens quiet, quick, and once

A patch release of three fixes, two of them found from a single screenshot of a launch: an
OpenCode 2 row with its own server's log lines printed across the TUI, and `1 MCP failed` in the
status line.

**The log lines were the server writing onto the row's terminal.** v2 splits `serve` out of the
TUI, so `synth-hook` starts it behind the visible process — and started it with no file actions, so
it inherited the shim's own stdin/stdout/stderr, which are the row's PTY. `serve` prints
`server listening on …` at startup and a `spawning process { command: node, … }` line every time
its MCP subsystem starts a local server; all of it landed mid-frame on top of the TUI drawing on
the same terminal. All three streams now go to /dev/null. stdin too, which was the quieter half of
the same bug: the server was sitting on the other end of the keyboard the TUI reads.

**Registering the MCP servers was holding the row closed for someone else's timeout.** A
`PUT /api/mcp/<name>` connects its own server within a fraction of a second, but only *responds*
once the whole MCP set has re-initialised — which is paced by the slowest entry in the user's own
opencode config (~9s here, behind an unreachable remote). Sent one after another under a 3s cap,
every registration past the first timed out (`http.status=499` in opencode's log) and reported
failure for work the server went on to finish, which is indistinguishable from one that never
landed. They now go together, with a short grace window for the answer worth having: a rejected
registration comes back immediately, and `--fail` makes that a non-zero exit rather than the silent
success the old call read it as — it had no `--fail`, so an HTTP 400 had always counted as success.
3.7s to a visible TUI, against 6.7s before and 11.2s for the version that waited the responses out.

**A custom agent that duplicated a built-in's command was offered twice.** Settings had said so on
the row since custom agents shipped ("OpenCode 2 is already one of Synth's agents"), but the
warning was only words — the descriptor still reached `AgentRegistry.all`, so ⌘K carried two of
every "New OpenCode 2" and both started the same binary. `AgentRegistry.clashOwner` is now the one
rule behind both the sentence and the exclusion, and a clashing agent stays in Settings, where the
row explains itself, and out of everywhere that offers it.

Two gates, each confirmed to fail against the pre-fix binaries before being kept: `t36` runs the
shim through a real launch and greps the row's own stdout (the PTY content is not something the
control socket can hand back, so this one drives the shim rather than a Synth row), and `t35` seeds
a clashing custom agent and reads the palette. `t34` still passes whole, its live MCP registration
check included. `t28_alias_agent` check 9 fails on this machine and fails identically on an
unmodified tree — pre-existing, not this work.

`CFBundleVersion` 715, tag `v0.41.1`. Both artifacts notarized separately and stapled, then verified
with no credentials and quarantine set: dmg `accepted / source=Notarized Developer ID`, the app
inside it assessing on its own, same for the zip Sparkle fetches. Appcast newest 0.41.1 at 715,
`edSignature` on all 18 enclosures, 5 deltas at 0.8–1.6 MB against a 164 MB full download. No
`synth-site` push — nothing under `site/` changed since 0.41.0.

The `1 MCP failed` in the same screenshot was not Synth's: a `paper` entry in the user's own
`~/.config/opencode/opencode.json` pointing at `http://127.0.0.1:29979/mcp` with nothing listening.
Worth writing down only because it arrived in the same picture as two real bugs, and the log was
what separated them.

## opencode's pane stops drawing its own edges

A Claude Code row is one surface from the pane's border to its text: ghostty fills the cells and the
23×19pt `window-padding` band around them with `TerminalTheme`'s translucent surface, and the agent
paints ink on top of it. opencode did not. It painted every cell of its own field — `#ffffff` in
light, `#0a0a0a` in dark — so the padding band read as a frame around a rectangle of a different
colour, and an opaque one: the pane also sat out the window translucency every neighbour had. Both
versions did it, and one file fixes both, because v1 and v2 read the same `themes/synth.json`.

The theme hands `background` back to the terminal. opencode documents `"none"` for exactly this —
blend with the terminal's colour scheme — and it works, but not on its own: opencode also *derives*
surfaces from that value, and `"none"` resolves to a zero-alpha black. Measured, that drove the
splash mark's shadow from `#dbdbdb` to `#1c1c1c` in light — two near-black slabs under the wordmark,
which no contrast gate would have caught because they are fills rather than ink. `#f7f8fa00` and
`#12131700` say both things at once: paint nothing, and here is what you are sitting on. 92.8% of a
splash screen now comes back as the terminal's own default in both appearances and both versions;
the remaining 6.7% is opencode's prompt box, which it is entitled to paint, and the derived shadow
lands on `#d5d6d7`. Ink is still judged against that box (`#f5f5f5`), which stays the least forgiving
light surface — the terminal's is lighter.

Those two values are `TerminalTheme`'s own, quoted a second time in a JSON file no Swift reads back.
`t25` parses both out of their files and fails if they drift apart, which is the only thing keeping
the copy honest.

**v2 names its theme somewhere else**, and that closes the gap 2026-09-06 left open — "the
light-theme correction doesn't carry over", concluded from a v2 launched against Synth's theme file
rendering identically to one launched without it. The theme *file* was never the problem: v2 reads
`themes/synth.json` out of the same directory v1 does, and renders it — measured here on both
binaries, whose splash screens come back cell-for-cell identical. What it does not read is
`tui.json`. v2 names its theme in `cli.json` as `theme.name`, and migrates `tui.json` into it exactly
once, only when `cli.json` does not yet exist. A v2 that has already run has a `cli.json` Synth
never wrote to, which is why the file looked ignored.

So Synth claims `theme.name` there too, under v1's rule: adopt nothing-set, `opencode`, `system` or
`synth`, and leave catppuccin or gruvbox alone. `theme.mode` is not touched — it is v2's own
appearance following, and it already works. Unlike `tui.json`, an absent `cli.json` is left absent:
creating it would satisfy the migration's existence check and silently drop every v1 TUI preference
the user had, and waiting costs nothing, because the migration carries `tui.json`'s theme across as
`theme.name` by itself.

`t25` now renders opencode2 as well as opencode and asserts the field in both appearances for both;
the dark-half drift check exempts `background` by name, since it is no longer opencode's to choose.
Nothing in `working.html` changed: the design has always drawn the terminal as one surface, and this
is the app catching up to it.
## Three gates that kept every worktree forever

The sweeper had been archiving correctly and reclaiming almost nothing: 132 of 140 rows archived on
the author's machine, 51 of them still holding a folder, and only four of those clearing the gate
chain. The gates were not being cautious — three of them were wrong, and each was wrong permanently
rather than for a while, which is the difference between a folder that waits and a folder that can
never be reclaimed.

**A generated `.env` is not an original.** `matchesParent` cleared an ignored file only when it
byte-matched the parent checkout's copy. Worktree-create in this repo copies them, so that held —
but a project whose setup script *stamps* `.env.development` out of a committed
`.env.development.demo` produces a file matching no parent copy and never will. Every one of that
project's 45 worktrees read as "local-only config inside — kept", forever. The rule now also accepts
a file whose bytes are already a committed blob in its own directory: the template it came from is
in the object store and on the remote, so the folder holds nothing.

**A fetched dependency is not a nested repo.** `hasNestedRepo` looked four levels down for a `.git`,
skipping only `.git` and `node_modules`. A built SwiftPM package keeps its dependencies as real
clones under `app/.build/checkouts/` — a `.git` at exactly depth four — so every Synth worktree that
had ever been built was `nested` for good. The walk now skips what git ignores, taken from the same
`ls-files --others --ignored --directory` answer B10 already needed. A repo that ignores a path has
declared what is under it disposable; a `.git` down there is an artefact, not work.

**Shape is not ownership.** `removeStrandedConfigs` deletes the `.mcp.json` / `opencode.json` an
older build wrote into every managed worktree, and decided a file was Synth's by its JSON shape.
Holibob has both checked in. So the migration deleted tracked files, leaving ` D opencode.json` in
worktrees that were otherwise clean — which the sweeper then read, correctly, as work in progress
and kept. Synth's own upgrade had been making worktrees unreclaimable. A file git tracks is now
never removed, whatever it contains.

Found by replaying the gate chain over the author's own 132 archived rows rather than by reasoning
about it: 11 kept on the `.env`, 8 on uncommitted changes (4 of those Synth's own deletions), and
the 4 that passed everything else all blocked on `.build/checkouts`. `t9_archive` gains three
scenarios — a nested repo under an ignored path and an `.env` copied from a committed template, both
reclaimable; an `.env` holding something that exists nowhere else, still kept — and drives ticks
until the reclaimable set is through, since `perTickCap` is three. `t4a_mcpconfig` plants a
committed config alongside its untracked ones and asserts it is neither rewritten nor deleted.

Left alone deliberately: the bulk brake. Five eligible folders at once and the tick does nothing at
all and raises a card, so a backlog past five can only ever be cleared by hand — which is its own
decision to make, not a bug in a gate.

## The branch is the last thing to go

The archive path ended one step short. A row was archived, its folder held, then reaped — and its
branch ref stayed behind for good, with the row still in the Archived list pointing at it. Settings
even promised this ("the git branch is never deleted"), which is defensible for a folder that might
still be wanted and indefensible for a branch nothing can reach. On the author's machine: 443 local
branches in one repo, 258 merged, 220 with no checkout, **200 of those already deleted on the
remote**; 180 and 155 in the other. 322 were deleted by hand before the code was written, which is
how the shape of the rule was found rather than guessed.

**The gate is the remote, not "merged".** A merged branch the remote still lists is one somebody is
keeping — a release branch, a base someone forks from. A merged branch the remote has *dropped* was
cleaned up when its PR landed, and every commit on it is reachable from the default branch. That is
the entire claim, and it is why this needs no grace of its own: the folder already served one, and
there is nothing left here to change its mind about. `git branch -d`, never `-D`, so git's own
merged-into-HEAD check sits on top as a free second opinion; a ref it refuses is one worth keeping.

**A row whose branch has gone is dropped, not kept.** `restoreArchivedBranch` re-cuts the checkout
from the ref, so the ref is what makes an Archived row restorable. Retiring it and leaving the row
would leave an entry that can never come back. So `ArchiveSweeper.branchEnd` answers with three
states, not two: `retire` (delete the ref, drop the row), `orphaned` (the ref is already gone —
deleted by hand or by another tool — so there is nothing to delete and the row is a pointer to
nothing), `keep`. The hand cleanup above created 67 orphans on this machine in one afternoon, which
is the case arriving before the code that handles it.

Its own switch in Settings, on by default, worded to say what makes it safe rather than hidden
inside the sentence above it — the parent row's promise that branches are never deleted is gone,
because it is no longer true.

The cap counts rows *looked at*, not rows ended, and the cheap rejections come first: an archived
row that still has a folder is thrown out by a `stat` with no git at all. A settled archive costs
the pass nothing per tick; a backlog drains twenty git chains a tick instead of running hundreds
every time. That ordering was not a nicety — the first version walked every archived row through
five git calls on every tick, which made a tick long enough that `sweepInFlight` began coalescing
the suite's own forced sweeps away, and eight checks failed for a reason that had nothing to do with
what they were testing. `sweep_until` in `t9` now drives ticks until the state it wants, rather than
assuming a fixed number of calls each land as a tick.

`t9_archive` gains both endings: `remote-gone` (merged, pushed, then deleted on origin — ref and row
must both go) and `ref-gone` (its ref removed by hand once archived — the row must go on its own),
with `merged-gone` as the negative that makes the remote the load-bearing gate: same shape in every
other respect, origin still lists it, ref and row both stay. Plus the invariant that a row archived
on a tick is never held on that same tick.
