## Routines — a saved prompt an agent is handed on a schedule (design, `working.html`)

A **routine** is a saved prompt that Synth hands to an agent on a schedule. It runs on this Mac,
only while Synth is open. This entry records the design as it lands in `working.html`; the Swift
port follows once it's approved.

**Why local, and why only while open.** Every cloud product already runs scheduled agents: Claude
Code routines, Cursor Automations, Copilot cloud automations, Devin, Warp Oz and Jules. None of them
can see what only this Mac has: the worktree's browser and simulator, Synth's MCP servers, local
services and anything behind a VPN. A local routine can use all of it. Running only while Synth is
open keeps the archive sweeper's stance (in-process, no launchd, no daemon). A menubar keep-alive or
a launchd/`pmset` wake helper is a separate, later decision, because it reverses that stance.

**The unit.** A routine belongs to one project and is stored in Synth's state, never in the repo
(the 2026-08-17 "Synth stops writing config into your repo" rule). Its fields:

- **Name, Project, Prompt, Agent** (defaults to the project's first agent).
- **Branch**, one of three targets:
  - an **existing branch** row, including `main` at the repo root;
  - **Same each run**, `routine/<name>`: one worktree reused by every run, with commits
    accumulating;
  - **New each run**, `routine/<name>-YYYY-MM-DD-HHmm`: a fresh worktree per run.
- **Schedule**, presets only: Hourly, Daily at, Weekdays at, Weekly on, Once at. There is no cron
  field, because it's a typing trap.
- **Base** and **Extra flags**, folded under **More**. The flags are appended to the project's agent
  flags for this routine only, and the model goes there too, because every agent spells it
  differently.

**A run.** Every run starts a **new agent session**. Resuming a session ("heartbeat") was rejected:
it bloats the context and carries over whatever went wrong last time.

- On an existing or same-each-run branch, the previous run's session is closed when the next run
  starts, but only if it's idle and read, and nobody is holding it: open, in a pane, or under the
  cursor.
- Branches for same-each-run and new-each-run are cut from Base after a fetch. If the fetch fails,
  the run uses the local base and history records that; for an unattended job, a stale start beats
  no start.
- A new worktree gets the setup script and the routine's agent only, like an MCP handoff. It does
  not get the whole session template.
- The agent receives one preamble line: the routine, the scheduled time versus the actual time, the
  target, and whether it's a test. The prompt follows.
- An existing branch that is busy or dirty doesn't stop a run. You picked that branch, and skipping
  silently is how competitors lost trust.
- A run is never skipped for usage.
- **Hard requirement: a run never takes the pane, the focus or a keystroke, even briefly.** Today
  `seedAgent` flashes the session open so its PTY spawns. Routines need an agent spawned without
  mounting its view; that is a prerequisite for the port.

**When runs fire.**

- If a slot arrives while a run is busy, one run waits. At most one waits, and it carries the
  latest slot, so a routine stuck for five hours doesn't then fire five times.
- Catch-up happens on launch or wake: one run, for the latest missed slot, if that slot is within a
  period (an hour for hourly, a day for daily and weekdays, a week for weekly). Otherwise the skip
  is recorded, at the slot's time. A run left waiting when Synth quit is judged the same way at the
  next launch; a start the quit cut off is recorded as didn't start, in history only.
- A missed Once always runs, then reads "Ran" and never fires again. Run now uses a Once up the
  same way; a Test doesn't. A Once can't be given a time that has already passed.
- **Run now** fires immediately.
- **Test** always runs in a throwaway `routine/<name>-test` worktree, whatever the target, so
  trying a routine against `main` never touches `main`. A new Test archives the previous one first,
  unless someone is holding it (open, in a pane, under the cursor); then the new Test is cut beside
  it under a dated name. The test worktree archives when its session is closed; the prototype
  doesn't simulate that step.

**Surfaces.**

- **Sidebar.** A **Routines** entry sits beside Usage, above the tree. Its only signal is a red dot
  while a failed start is unseen.
- **Board.** One board for every project, grouped by project, in the content pane:
  - The list shows the schedule in words, the next run and the last outcome.
  - Selecting a routine opens its detail in place: the editor, Run now / Test / Delete, and
    the last 20 runs.
  - The empty state shows four starters that only prefill the editor.
- **Runs history.** Each run records when it fired versus its slot (these differ on catch-up), the
  target branch, and the outcome.
  - Outcomes: **Ran**, **Running**, **Queued**, **Skipped** (with a reason), **Didn't start**
    (with a reason).
  - Each run jumps to its session.
  - This board says whether a run *fired*. The run's branch row says what it *found*.
- **Keys:** j/k/↑↓ move, l/↩ open, h/⎋ go back one layer, ⌘R runs now. The grilling agreed ⌘↩,
  but ⌘↩ already means "jump to the front card" everywhere.
- **⌘K** only navigates: a Routines item, plus each routine by name.
- **Rows.** Rows a run creates carry a small routine mark, with a tooltip naming the routine and
  when it fired. The mark is stored on the row, so it stays after the routine is edited or deleted.
- **Notifications.**
  - A run starting raises nothing.
  - Done, needs-input and error arrive through the ordinary background routing.
  - **Didn't start** is the one outcome that speaks up by itself: one sticky card, plus the dot.
    This is deliberately the opposite of Codex, whose automations auto-archived failures and were
    distrusted for it.
- **Dated runs** are never auto-archived. Merged ones follow the existing merged-branch sweep.

**Lifecycle.**

- Edits apply from the next run. A queued run holds a slot time, not a snapshot, so it uses the
  current definition.
- Delete removes the routine and its history, never its branches (those have Archive). It is red,
  and it confirms only while a run is busy.

**Analytics:** `routine_created`, `routine_fired`, `routine_skipped`, with properties limited to
trigger, target kind, agent id and skip-reason enums. Never names or prompts.

**Deliberately not in v1:**

- running while Synth is closed;
- event or webhook triggers;
- agents creating routines through a synth-app `routine_create`, approval-gated like
  `worktree_create`;
- heartbeat sessions;
- template variables;
- fallback agents or skipping for usage;
- routines as files in the repo.

**Research behind it.** The competitor survey (Claude Code routines, desktop scheduled tasks and
`/loop`; Codex/ChatGPT scheduled tasks; Cursor; Copilot and gh-aw; Devin; Factory; Jules; Amp;
Warp; Superset; Conductor) found everyone converging on the same core: prompt + trigger + scope +
model, a fresh isolated session per run, and a run history. The differences, and the complaints,
are about what happens around the run: failures that get hidden, runs stalled on a permission
prompt, runs silently lost to sleep, cost surprises. That is where this design spends its
complexity.

## Routines in the app — the board, the engine, and Claude's folder trust

The design above is ported to Swift: the Routines board beside Usage (`RoutinesPane.swift`,
`RoutinesBoard.swift`), the in-process scheduler and runner (`RoutineRunner.swift`), and one API in
`Routines.swift` that every caller goes through — `validate`, `createRoutine`, `updateRoutine`
(both throw `RoutineError` with a sentence for whoever asked), `deleteRoutine`, `fireRoutine`, and
`defaultDraft(in:)`. The board is its first caller; a synth-app `routine_create` tool, approval-gated
like `worktree_create`, is meant to be the next, and gets the same answers the editor does.

**A run starts its agent without ever showing it.** libghostty only spawns a surface's PTY once its
view is in a window, which is why `seedAgent` flashes a session open. A routine's terminal boots in
a hidden, never-key window instead (`TerminalManager.boot`), and moves into the pane with its process
when you open the session later.

**Claude's folder trust.** A folder Claude Code has never seen opens on "Do you trust this folder?",
and a routine has nobody there to answer it. Before a Claude run in a folder Synth cut (same, fresh,
test), Synth copies the repo's own `hasTrustDialogAccepted` onto that folder's entry in
`~/.claude.json` (`$CLAUDE_CONFIG_DIR` when set) — only when you already trusted the repo, touching
only that one key, re-reading just before an atomic write (`AgentTrust.swift`). An untrusted repo
gets nothing written, and the run fails with the sentence that says so and what to do. Claude Code
2.1.280 already treats a worktree of a trusted repo as trusted; the entry keeps that true for a
version that resolves trust differently. Antigravity (and a custom agent on its base) gets the same
treatment in its own list, `trustedWorkspaces` in `~/.gemini/antigravity-cli/settings.json`
(`$SYNTH_AGY_SETTINGS` for gates): `agy` 1.2.9 trusts a folder only by the exact path of its working
directory, so the folder Synth cut is appended as the terminal spells it and as it resolves.

**Deviation:** Synth has no runner for a project's setup script yet, so a routine's new worktree gets
its agent only. `t39_routines` is the gate (88 checks).

## Settings and Usage keep their header in tabs mode

Tabs mode hides a session pane's title bar because the tab strip carries its name and icon. In
`working.html` the rule hid every pane head, so Settings lost its Synth/project tabs and Usage its
title; it now applies to session panes only, and Settings, Usage and Routines keep theirs. The native
app already drew them that way (`SessionPane` is the only head that tabs mode drops).
